## **이 문서의 역할**

Platform팀은 알림·채팅·Form·인증인가 4개 도메인을 엔진으로 제공하고 각 제품팀(이하 **목적팀**)은 이 엔진을 언제·누구에게·어떤 문구로 쓸지 결정한다. 이 문서는 "이건 누가 정하고, 누가 고치나?"에 한 곳에서 답하기 위한 책임 범위 가이드이다.

## **4개 도메인 한눈에 보기**

플랫폼팀은 "어떻게 처리하는가"를, 목적팀은 "무엇을·언제·누구에게"를 책임진다.

| 도메인 | 플랫폼팀이 제공하는 것 | 목적팀이 결정하는 것 | 주 사용처 |
| --- | --- | --- | --- |
| 알림 | FCM 푸시·이메일·웹훅(Discord·Slack·Telegram) 발송, FCM 토큰 관리, 대상 조건 → 실제 수신자 변환 | 발송 여부·시점·대상 정책·문구 | 커뮤니티, Recruiting, 인증, 운영 알림 |
| 채팅 | 채팅방·참여자·메시지·반응·읽음·고정 메시지, 채팅용 WebSocket 전달 기반, 변경 이벤트 | 채팅을 언제·누구에게 제공할지, 초대·강퇴·권한·글자 수 제한 | 커뮤니티 스레드 |
| Form | 폼 구조(섹션·질문·선택지) 관리, 기명·익명 응답 처리, 답변 검증, 범용 투표, 15분 단위 일정 집계 | 허용·필수 질문 범위, 기간, 업무 권한, 지원·선발 정책 | Project, Recruiting, Notice, Feedback |
| 인증·인가 | 로그인(이메일·소셜), 이메일 인증, 토큰·SSO, Spring Security 공통 처리, 역할·권한 판단 | 도메인별 업무 권한 정책(합의 후 반영) | 전 도메인 |

## **공통 원칙**

4개 도메인 문서에 반복해서 나오는 기준이다. 경계가 헷갈리면 이 원칙부터 적용한다.

1. **공통 Outbox는 Messaging Team 공용 소유.** 이벤트 저장·폴링·재시도·처리 상태 기반은 Platform팀 내부 Messaging Team(와나, 라미, 리버)이 함께 소유한다. 변경 시 팀과 영향받는 이벤트 소비 도메인이 함께 검토한다.
2. **문제는 우선 확인 담당이 먼저 보고 원인이 다르면 근거와 함께 넘긴다.** 최초 담당이 끝까지 고치는 것이 아니라, 원인 영역의 담당자에게 연결한다.
3. **엔진 밖 기반은 협업 대상.** 파일은 Storage, 비밀값·네트워크·배포는 Infrastructure, 회원·기수·소속 원천 데이터는 해당 도메인이 소유한다.

## **1. 알림 (Notification)**

> 다른 도메인이 사용자와 운영 채널에 알림을 보낼 수 있도록 FCM·이메일·웹훅 전달 기능과 공통 발송 계약을 제공한다.
>

### **제공 기능**

- **FCM 토큰 관리**: 토큰을 회원·앱 설치 정보에 연결해 등록·갱신·해제하고, 유효하지 않은 토큰을 비활성화한다.
- **토큰 정기 검증**: 검증 대상·주기·배치 크기와 검증 결과의 저장을 관리한다. 토큰 테이블의 제약조건·인덱스·데이터 전환도 포함한다.
- **대상 변환**: 요청에 포함된 회원 ID 또는 기수·지부·학교·파트 조건을 실제 발송 대상과 활성 FCM 토큰으로 변환한다. 조건에 맞는 회원을 계산하되 어떤 조건의 사용자에게 알릴지는 요청 도메인이 결정한다.
- **발송 요청 접수**: FCM 발송 요청을 접수하고 공통 Outbox를 통해 처리할 알림 이벤트를 발행한다.
- **API**: 관리자 발송 API와 토큰 등록·해제 API의 입력 검증·응답 계약·권한 적용·감사 기록 연동을 관리한다. FCM 권한 검사 구현은 담당하되 운영진의 발송 권한 정책은 정책 담당과 협의하고 공통 인가 기반을 사용한다.
- **배치 발송·결과 처리**: 발송 대상을 배치로 나누고 외부 발송 결과를 처리한다. 이벤트 기반 발송에서는 재시도 가능한 실패 토큰을 다시 요청하고 무효 토큰을 비활성화한다.
- **기존 직접 발송**: 기존 직접 발송 경로를 유지보수한다.
- **이메일**: 인증 이메일과 HTML 이메일의 메시지 구성·템플릿 렌더링·외부 발송을 처리한다. SES·SMTP 제공자 설정과 전환 계약, 발신자 설정을 관리한다.
- **웹훅**: 요청받은 운영 알림을 웹훅 채널(Discord·Slack·Telegram)로 전달하고 발송 결과를 기록한다. 선언형 웹훅 연동(`@WebhookAlarm`)과 즉시·버퍼 발송 경로를 관리하며 어노테이션·SpEL 해석·이벤트 수신은 공통 연동 구현에 포함한다.
- **실행 기반**: Firebase 초기화, 알림 전용 비동기 실행기, 채널별 설정 계약과 알림 지표 계측을 관리한다. 공유 설정 파일에서는 알림 관련 부분을 담당하고 비밀값 공급·네트워크·배포 환경은 Infrastructure와 협업한다.
- **레거시 유지·폐기 준비**: 기존 FCM 토픽·`FcmOutbox` 코드와 API·테이블을 유지보수하고 폐기를 준비한다. 신규 연동에서는 제외하지만 잔존 스케줄러·데이터 처리·호환 API의 책임은 제거 또는 인계가 완료될 때까지 유지한다.
- **테스트·문서**: 소유 코드의 테스트·fixture·설정 검증과 사용·운영 문서를 함께 관리한다.
- **장애 원인 확인**: 제공하는 발송 계약과 채널별 실패 처리 방식을 관리하고 알림 전달 문제의 원인을 확인한다. 제품별 요청, 공통 이벤트 처리, 실행 환경, 클라이언트 문제로 확인되면 해당 담당자와 연결한다.

### **누가 결정하나**

| 상황 | 알림 엔진 | 목적팀·협업 담당 |
| --- | --- | --- |
| 어떤 조건의 사용자에게 알릴지 | 조건 → 수신자·활성 토큰 계산 | 요청 도메인: 발송 여부·시점·대상 정책·문구 |
| 인증 메일 | 메시지 구성·렌더링·발송 | 인증: 코드 발급·만료·검증 정책 |
| 제품별 메일 | 메시지 구성·렌더링·발송 | 해당 제품 도메인: 문구·대상·시점 |
| 면접 안내 메일 (`InterviewAvailabilityRequestedEventListener`) | 리크루팅 이메일 연동·템플릿 구현·렌더링 계약 유지 | Recruiting: 제목·문구·변수 의미·발송 여부, 업무상 취소·완료 상태 |
| 커뮤니티 알림 (`CommunityAlarmEventListener`) | 이벤트 수신·수신자 변환·문구 구성·발송 요청 | 커뮤니티: 음소거·멘션 예외·수신 대상·문구 정책 |
| 서버 시작·종료 알림 (`ServerLifecycleAlarmListener`) | 서버 이벤트와 웹훅 연동 | Infrastructure: 알림 환경·시점·채널·내용 협의 |
| 운영 알림(웹훅) | 웹훅 채널 전달, 결과 기록, 선언형 연동 구현 | 해당 도메인: 어떤 업무 상황에서 알릴지, 적용할 업무 메서드, 알림 문구 |
| 기존 직접 발송 대상 (`AudienceNotificationCommand`, `FcmAudienceService`) | 직접 발송 계약과 대상 변환 유지 | Notice: 참조하는 `NoticeTargetInfo`의 공지 대상 정책. 계약 변경 시 함께 검토 |
| 운영진 발송 권한 | FCM 권한 검사 구현 | 정책 담당과 협의, 공통 인가 기반 사용 |
| 설정·자격증명 | FCM·이메일·웹훅 설정과 관련 health 설정 | Infrastructure: 자격증명·비밀값 공급, 네트워크, 배포 환경 |

### **알아둘 점**

- 발송 응답의 `requestId`·`queuedAt`은 **요청 접수**를 나타낸다. 단말 수신 완료를 의미하지 않는다.
- 채널마다 실패 처리 방식이 다르며 모든 알림의 동일한 재시도·중복 방지·단말 수신을 보장하지 않는다.
- 기존 **직접 발송**과 **이벤트 기반 발송**은 실패·재시도 방식이 다르므로 동일한 전달 보장을 제공하는 것으로 취급하지 않는다.
- **FCM 토픽 구독 경로와 `FcmOutbox`는 사용 중단된 레거시**다. 신규 제공 기능으로 안내하지 않는다. `notification` 안의 `FcmOutbox`는 아래 공통 Outbox와 다른 구현이다.
- 현재 Notification에 들어 있는 제품별 알림 연동 코드는 정책 담당 도메인과 협의해 유지보수한다. **코드 위치만으로 정책 결정권까지 Notification에 귀속하지 않으며** 연동 코드 소유가 호출 대상 도메인 모델·서비스의 소유권까지 이전하지 않는다.
- 공통 Outbox의 이벤트 저장·폴링·처리 상태·재시도 기반은 Messaging Team(와나, 라미, 리버) 공용 소유다. Notification 담당자는 알림 이벤트 생성·처리와 발송 채널별 실패 처리를 담당한다.

## **2. 채팅 (Chat)**

> Messaging Team의 Chat 도메인은 목적팀이 대화 기능을 사용할 수 있도록 공통 채팅 엔진과 WebSocket 전달 기반을 제공하고 메시지 저장·읽음·반응·변경 이벤트의 정합성을 책임진다.
>

### **제공 기능**

Chat 담당자는 공통 채팅 기능과 채팅용 WebSocket 전달 기능을 관리한다. 목적팀은 이 기능을 제품에서 언제, 누구에게, 어떤 방식으로 제공할지 결정한다.

- **채팅방 생성·삭제**: 목적팀의 요청에 따라 내부 채팅방을 생성하고 삭제한다. 제품 리소스를 삭제할 때 채팅 기록을 보존할지는 목적팀이 정하고 Chat 담당자가 삭제 방식에 반영한다.
- **참여자 등록·퇴장**: 내부 채팅방의 참여자 정보를 등록하고 퇴장 상태를 반영한다.
- **메시지 생성·수정·삭제 상태 변경**: 채팅방 참여 여부와 작성자를 확인하고 변경을 처리한다. 삭제된 메시지는 식별자와 대화 흐름을 유지하면서 삭제 상태로 표시한다.
- **답장·멘션·첨부 검증**: 답장 대상이 같은 채팅방의 메시지인지, 멘션 대상이 유효한 참여자인지 확인한다. 첨부파일은 Storage가 제공하는 정보로 첨부 가능 여부를 검증한다.
- **반응 추가·취소**: 이모지 반응을 추가·취소하고 사용자별 반응과 반응 수를 제공한다. 같은 반응의 중복 처리, 삭제된 메시지에 대한 반응 추가를 막는다.
- **읽음·미읽음**: 참여자가 어디까지 읽었는지 저장하고 이미 읽은 위치보다 이전으로 되돌아가지 않게 한다. 채팅방별 미읽음 수와 메시지 읽음 정보를 제공한다.
- **조회**: 채팅방 정보, 개별 메시지, 메시지 목록, 채팅방 요약을 제공한다. 목적팀은 이를 사용해 제품 API와 재접속 시 메시지 복구 기능을 구성한다.
- **고정 메시지**: 고정할 메시지가 해당 채팅방에 속하는지 확인하고 고정 상태를 변경한다.
- **재전송·동시 요청**: 같은 `clientMessageId`로 생성 요청이 다시 들어오면 기존 결과를 반환하고 같은 식별자로 다른 내용이 들어오면 충돌로 처리한다. 생성·수정·반응·읽음 요청이 동시에 들어와도 채팅 상태를 일관되게 유지한다.
- **상태 변경 이벤트 발행**: 메시지 생성·수정·삭제, 반응 변경, 읽음 갱신, 고정 메시지 변경을 이벤트로 발행한다. 이벤트의 내용과 발행 시점을 관리한다.
- **WebSocket 연결·공통 전달**: WebSocket 연결, STOMP 처리, 브로커 연결, 요청 제한과 공통 오류 응답을 관리한다.
- **성능·전달 장애 개선**: 채팅 저장·조회 지연, 불필요한 조회, 동시 요청 처리와 공통 WebSocket 전달 문제를 확인하고 개선한다.
- **공개 인터페이스·기존 구현 유지**: 다른 도메인이 쓰는 UseCase, 입력·출력 DTO, 이벤트, 오류 응답을 관리한다. 기능 변경에 필요한 테스트, 저장 구조 변경, 사용 문서를 함께 유지하고 기존 메시지 전송·읽음 처리 경로도 사용 중인 동안 유지보수한다.

| --- | --- | --- |
| 채팅방 생성·삭제 | 내부 채팅방 생성·삭제, 삭제 방식 반영 | 기록 보존 정책, 스레드 ↔ 채팅방 연결 |
| 참여자 | 등록·퇴장 상태 반영 | 초대 대상, 강퇴 조건, 인원 제한, 참여 상태 연동 |
| 다른 사람 메시지 삭제 | 삭제 상태 처리 | 운영자가 삭제할 수 있는 상황 |
| 글자 수·첨부 제한 | 검증 코드 변경을 함께 반영 | 제한 값 결정 (`CommunityChatMessagePolicy`) |
| 고정 | 채팅방 고정 메시지 | 누가 고정할 수 있는지, 목록에서 스레드 고정 |
| 미읽음·마지막 메시지 표시 | 채팅방 미읽음 수 계산 | 화면용으로 별도 저장하는 값 관리 |
| 화면 데이터 조합 | 메시지 조회 제공 | 사용자 이름·파일 정보 조합 |
| 실시간 전달 | 이벤트 내용·발행 시점, 공통 WebSocket | 이벤트 → 실시간 메시지 변환, REST·STOMP 경로, 구독 권한, 수신 대상 |
| 파일 | 첨부 가능 여부 검증 | Storage: 업로드·저장·다운로드 |
| 연결 인증 | 연결 처리 | 인증·인가 담당과 협업 |

### **알아둘 점**

- 현재 커뮤니티 스레드 삭제는 내부 채팅방의 **물리 삭제로 이어지지 않는다.**
- 이벤트를 저장·재시도·전달하는 **공통 Outbox는 Messaging 공동 소유**다. Outbox 저장 완료가 클라이언트의 **수신 완료를 의미하지 않는다.**
- 현재 커뮤니티의 글자 수·첨부파일 제한은 `CommunityChatMessagePolicy`에 구현되어 있다. 정책은 커뮤니티팀이 정하고 검증 코드 변경은 Chat 담당자와 함께 반영한다.
- 커뮤니티 이벤트 변환이나 수신 대상 계산에서 생긴 문제는 커뮤니티팀과 함께, 공통 Outbox에서 생긴 문제는 Messaging 담당자들이 함께 확인한다.
- 연결 과정의 인증 정보 처리는 Identity(인증·인가) 담당자와, 브로커 실행 환경과 네트워크·배포 설정은 Infrastructure 담당자와 협업한다.
- 기존 `SendChatMessageUseCase`, `MarkChatRoomReadUseCase` 경로는 사용 중인 동안 유지보수한다.

## **3. Form**

> Form은 여러 제품 도메인이 재사용할 수 있도록 폼 구조와 응답의 생성·검증·저장·조회, 범용 투표 입력, 일정 응답 집계를 제공한다.
>

### **제공 기능**

- **폼 구조와 상태 관리**: 폼 초안을 만들고 수정·발행·종료·삭제한다. 섹션을 만들고 수정·삭제하며 표시 순서를 관리한다. 질문과 선택지를 만들고 수정·삭제·복제하며 순서를 관리한다.
- **기명 응답**: 임시저장·수정·제출·삭제와 상태 전이를 처리한다.
- **익명 응답**: 같은 생명주기로 처리하고 응답 접근 키(`responseAccessKey`)로 응답자를 확인한다. 키 원문은 생성 시 반환하고 저장소에는 해시를 보관한다.
- **답변 검증·저장**: 질문 유형에 맞는 답변 형식과 선택지 소속을 검증하고 답변을 저장한다. 객관식·주관식·일정·파일·포트폴리오 유형의 공통 답변 모델을 제공한다.
- **제출 시 검증**: 현재 폼 구조와 질문 유형에 맞는지, 필수 질문에 답했는지, 허용된 질문에만 답했는지 검증한다. 허용 질문 범위와 필수 질문 ID는 소비 도메인이 정해 전달한다.
- **범용 투표 구성**: 일반 투표에 필요한 Form·섹션·질문·선택지를 구성하고 제거한다. 투표 기간과 어느 업무 객체에 연결할지는 소비 도메인이 정한다.
- **일정 응답 집계**: 제출된 일정 답변을 15분 단위 슬롯별 응답자 집합으로 계산한다. Form은 가능한 슬롯과 응답자를 집계하고 어떤 슬롯을 고르고 확정할지는 소비 도메인이 결정한다. (사용 예: Recruiting의 면접 가능 시간 조율)
- **파일 답변의 존재 확인**: FILE·PORTFOLIO 답변에 포함된 `fileId`가 존재하는지 Storage의 `GetFileUseCase.throwIfNotExists`로 확인한다. 파일 존재 확인은 Form의 책임이다.

- Form은 현재 파일의 **존재 여부만** 확인한다. 업로드 완료 여부와 회원별 사용 권한은 검증하지 않는다(Storage의 `batchGetUsableByIds`는 아직 호출하지 않음).
- 일정 집계는 "가능한 슬롯과 응답자"까지다. 어떤 슬롯을 고르고 확정할지는 목적팀이 정한다.
- Form은 목적팀의 관리자·업무 권한을 판단하지 않는다.

## **4. 인증·인가 (Authentication / Authorization)**

> 사용자의 신원을 확인하고 로그인 상태를 관리하며 역할·기수·소속·대상 리소스를 기준으로 접근 권한을 판단하는 공통 체계를 제공한다.
>

### **제공 기능**

`authentication`, `authorization`, Spring Security 기반 공통 보안 처리를 담당한다. **각 도메인의 업무 정책은 해당 담당자와 합의하고 인증·인가 담당자는 공통 권한 체계와 보안 적용 기준을 관리한다.**

**로그인 및 로그인 수단 관리**

- 이메일·비밀번호를 검증하고 로그인 성공 시 인증 토큰을 발급한다.
- 비밀번호 형식 정책, 해시 생성·검증, 기존 해시의 갱신 방식을 관리한다.
- 비밀번호 최초 등록·변경·재설정 시 본인 확인과 인증 흐름을 처리한다. 비밀번호 해시의 저장·변경은 회원 도메인의 공개 UseCase에 요청한다.
- 카카오·구글·애플에서 받은 인증 정보를 검증하고 서비스 회원과 연결한다.
- 소셜 계정의 연결·조회·해제를 처리하고 연결 해제로 회원의 마지막 로그인 수단이 사라지는 것을 방지한다.

**이메일 인증**

- 회원가입·이메일 변경·비밀번호 재설정 목적의 이메일 인증 세션을 생성한다.
- 인증 코드 생성·검증, 유효기간, 실패 횟수, 재발송 제한을 관리한다.
- 이메일 인증 결과를 증명하는 토큰을 발급·검증하고 사용 목적을 구분한다.
- 인증 메일 발송을 알림 도메인에 요청한다. 실제 메일 전송과 전달 실패 처리는 알림 도메인이 담당한다.

**토큰 및 SSO**

- Access Token과 Refresh Token을 발급하고 서명·만료·용도를 검증한다.
- Refresh Token을 저장·검증·교체하고 로그아웃 시 폐기한다.
- 로그아웃·비밀번호 재설정·회원 탈퇴 시 적용할 인증 정보 폐기 정책과 연계 처리를 담당한다.
- SSO 브라우저 로그인과 로그인 쿠키의 발급·검증·삭제를 처리한다.
- SSO 클라이언트, 허용된 Redirect URI·Origin을 검증한다.
- SSO Authorization Code 발급·교환과 PKCE 검증을 처리한다.

**Spring Security 및 공통 인증 처리**

- Security Filter Chain과 인증 필터의 실행 순서를 관리한다.
- 요청의 인증 정보를 검증하고 현재 로그인한 회원 정보를 제공한다(`@CurrentMember`).
- 공개 API와 인증 필수 API를 구분하는 공통 처리 방식을 관리한다(`@Public`).
- 인증 실패·접근 거부 응답을 일관되게 처리하고 민감한 내부 정보의 노출을 방지한다.
- 애플리케이션의 CORS·CSRF·인증 쿠키 보안 설정을 관리한다.
- REST·GraphQL·WebSocket에서 사용할 공통 회원 인증 기준을 제공하고 각 진입점에 인증·인가가 적용되는지 점검한다.

**역할 및 접근 권한**

- 챌린저의 운영진 역할을 부여·수정·회수하고 역할 목록을 제공한다.
- 역할과 기수·학교·지부 범위를 기준으로 권한을 판단하는 공통 기능을 제공한다.
- 회원 도메인이 소유한 `SUPER_ADMIN` 정보를 조회하여 전역 권한 판단에 반영한다. 해당 역할의 저장 책임은 회원 도메인에 둔다.
- 리소스별 접근 권한을 검사하는 공통 진입점과 평가기 연동 구조를 관리한다(`@CheckAccess`).
- 백오피스와 클라이언트에 단일·일괄 권한 조회 API를 제공한다.
- 권한 스냅샷과 캐시를 관리하고 역할 변경 시 캐시를 무효화한다.
- 기수별 권한과 의도적으로 기수를 구분하지 않는 권한을 구분하고 기존 정책 변경 시 해당 도메인 담당자와 합의한다.

**보안 검증 및 운영 연계**

- 인증 실패, 토큰 재사용, 권한 없는 접근, 다른 기수·학교 접근을 검증하는 공통 보안 테스트를 관리한다.
- 로그인·이메일 인증의 반복 시도 제한 정책을 정의하고 공통 요청 제한 기능과 연계한다.
- 로그인과 권한 변경의 감사 기록·보안 지표를 남기는 지점을 관리한다. 기록 저장·조회와 모니터링 기반 기능은 해당 담당자와 협업한다.

### **누가 결정하나**

| 상황 | 인증·인가 엔진 | 다른 담당 |
| --- | --- | --- |
| 도메인별 업무 권한 | 공통 권한 체계·보안 적용 기준 | 해당 도메인과 합의 후 반영 |
| 비밀번호 저장·변경 | 인증 흐름, 해시 생성 | 회원 도메인 공개 UseCase로 저장 |
| `SUPER_ADMIN` | 조회해서 전역 권한 판단에 반영 | 회원 도메인이 저장 |
| 인증 메일 | 인증 세션·코드 정책, 발송 요청 | 알림: 실제 전송·실패 처리 |
| 기수 구분 여부 | 기수별 권한과 기수 무관 권한 구분 | 기존 정책 변경 시 도메인 담당 합의 |
| 감사 기록·지표 | 기록 지점 관리 | 저장·조회·모니터링 담당과 협업 |
| WebSocket 연결 인증 | 공통 인증 기준 | Chat과 협업 |

### **알아둘 점**

- 위 목록은 **책임 범위**이며, 모든 보안 고도화 기능이 현재 구현됐다는 의미는 아니다.
- **전체 기기 로그아웃, 여러 서버에 대한 즉시 권한 회수, MFA**는 별도 구현 범위를 합의한다. 기획·디자인에서 이 기능을 전제하지 않는다.
- 역할이 바뀌면 권한 캐시가 무효화된다. FE는 단일·일괄 권한 조회 API로 버튼 노출 여부를 판단할 수 있다.

## **문제가 생기면**

표의 **우선 확인 담당**이 먼저 원인을 보고 다른 영역으로 확인되면 근거와 함께 해당 담당자에게 넘긴다.

| 증상 | 우선 확인 | 함께 볼 곳 |
| --- | --- | --- |
| 푸시·메일·웹훅이 오지 않음 | Platform - 리버 | 요청 도메인, 공통 Outbox, Infrastructure, 클라이언트 |
| 채팅 메시지 저장·조회 오류, 지연 | Platform - 와나, 라미 | 커뮤니티 |
| 실시간 메시지가 일부 사용자에게만 안 감 | Community&Connection(수신 대상·변환) | Chat 엔진(WebSocket), Infrastructure(브로커) |
| 이벤트가 처리되지 않음·중복 처리 | Platform - 와나, 리버, 라미 | 이벤트 발행·소비 도메인 |
| 폼 응답 저장 실패 | Platform - 갈래 | 소비 도메인 |
| 파일 첨부·업로드 오류 | Platform - 갈래 | Form·Chat 엔진 |
| 로그인·토큰·권한 오류 | Platform - 토리 | 해당 도메인(권한 정책) |
