## 1차 리뷰 반영 및 미해결 baseline

코드 후속 후보는 `a166ee76773c38b1dc549aee4c4193c486c70142`다.
전체 읽기에서 목록으로 돌아온 뒤 새 항목을 선택하면 분할로 시작한다.
긴 제출 검색 요약은 두 줄로 제한하고 전체 문자열을 AX/help에 남긴다.
상세 최초 조회 오류와 열린 콘텐츠의 투표/읽음 확인 오류를 구분하고,
후자는 원래 행동 옆에 표시하여 조회가 쓰기 재시도를 대신하는 인상을 없앤다.
오류가 생기면 해당 영역을 스크롤에 드러내며 키보드 포커스는 강제로 이동하지 않는다.

이번 PR에서 회수ID tombstone·재허용 판단·재시도 정책을 변경하지 않았다.
회수 직후 정리 테스트 통과를 회수 후 복구 전체의 통과로 해석하지 않는다.

## 독립 UI fixture와 재현

추가 소유 파일은 [notice_design_fixture.py](../../tools/qa/notice_design_fixture.py)와
[test_notice_design_fixture.py](../../tools/qa/test_notice_design_fixture.py)다.
기본 session_fixture/notice_fixture는 수정하지 않는다. 테스트8건은 HTTP 핸들러를 직접 호출하며
앱·서버 listener·Keychain·실서버를 사용하지 않는다. 전체 tools/qa 테스트18건도 통과했다.

```sh
python3 -B -m unittest discover -s tools/qa -p test_notice_design_fixture.py -v
python3 -B tools/qa/notice_design_fixture.py --port 0 --scenario reading
# 고정 없는 첫 페이지를 확인하려면 reading 대신 late-pin
```

fixture는 자신만의 임시 control 폴더와 OS가 할당한 루프백 포트를 출력한다.
**창 사용 승인 후에만** 같은 SHA의 Debug 앱을 `--local-api-port <출력 포트>`로 실행한다.
기존 Debug 진입은 메모리 FixtureTokenStore를 사용한다. `first@example.test / fixture-only`로
로컬 로그인을 거쳐 공지를 연다. 이는 보기→데이터 미리보기의 내장 데이터와 다른 경로다.
앱 production 분기나 새 세션 우회를 추가하지 않았다.

| 검수 | 조작/자료 | 관측 |
| --- | --- | --- |
| 장문·혼합 | ID21 제목60자 이상·긴 작성자·긴 로컬 URL·사진2장·투표, ID22 부속 없음 | 두 크기/모드·확대·선택·사진 확대·닫기 |
| 사진 첨부 | control의 blue.png/green.png | 파일 선택부터 기존 로컬 업로드·확인·PATCH 경로 |
| 고정0건 다음 페이지 | `--scenario late-pin` 또는 control에 `late-pin` 파일 | 첫20개 비고정, 더 보기 후 고정21; 서버 정렬 계약을 뜻하지 않는 합성 시나리오 |
| 추가 페이지 실패 | 더 보기 전에 `fail-notice-page-once` 파일 생성 | page1 503 후 page1 재시도, 기존 행 유지 |
| 조회·권한·쓰기 실패 | `fail-notice-list-once`, `deny-notice-list-once`, `deny-notice-detail-once`, `fail-notice-read-once`, `fail-notice-vote-once` | 러너 범위, 오류 문구·행동 위치, 투표와 읽음 독립 |
| 게시 결과 미확정 | 게시 전에 `drop-notice-create-once` | 로컬 저장 후503, 게시 결과 확인→후보 선택; 중복 POST 여부 |
| 첨부 부분 실패 | 이미지와 링크 입력 후 `fail-notice-links-once` | 이미지 PATCH 성공→링크 실패→첨부 저장 재시도, 성공 단계 중복 여부 |
| 투표 등록 결과 미확정 | `drop-notice-poll-once` | 투표 저장 후503, detail503으로 결과확인 유지; `block-poll-receipt-read` 삭제 후 결과 확인 |

마커는 출력된 **해당 fixture의 control 폴더에만** 만든다. 다른 실행 중인 fixture·포트를 건드리지 않는다.
`notice-requests.jsonl`에는 method/path/query만 기록해 검색 IME 중0회·제출1회와 목록 N+1을 관측한다.
로그에는 토큰·요청 본문·사진 바이트를 기록하지 않는다. 마커별 실패는 대부분 한 번 소비되며
poll 결과조회 차단만 명시적 삭제까지 유지한다. 재시작 시 새로운 합성 데이터/폴더로 초기화한다.
위 재현 수단의 테스트 통과는 실제 앱의 UI 통과를 뜻하지 않는다.

## 병합 후 삭제 오류 후속 수정

후속 이슈 [#182](https://github.com/UMC-PRODUCT/umc-product-macOS/issues/182)는
삭제 실패가 기본 조회 작업으로 분류되어 ‘다시 불러오기’가 노출되는 잔여 UI 문제를 다룬다.
최신 develop `28aadfb`에서 분기하며 #181의 권한/페이지 복구 정책은 변경하지 않는다.

`NoticeArticleOperation`이 기존 공통 실행 중 상태·실패 분류를 소유하고,
삭제 확인은 `.delete` 작업으로 같은 Repository를 호출한다. 삭제 실패는 상세 관리 영역 옆에
표시하고 조회 재시도를 제공하지 않는다. 다시 삭제하려면 원래 더보기→삭제 확인을 거친다.
capability 기반 메뉴와 서버의 인가 응답 처리, 실패 시 콘텐츠/목록 보존, 성공 콜백을 유지한다.

Presentation 테스트17건에는 삭제 거절·성공·accessDenied·실행 중 중복 차단이 포함된다.
로컬 fixture 테스트9건에는 `fail-notice-delete-once`의 503 후 원본 보존과 명시적 재시도 삭제가
포함된다. 실제 창에서의 삭제 확인·오류·포커스는 아직 미검증이다.
