## 1. 목적과 범위

사용자가 문의를 등록하기 전에 같은 질문의 답을 찾도록 한다. 해결되지 않은 문의는 담당자가 맡고 운영진은 라벨로 분류해 반복되는 문제를 확인한다. 인기 문의는 최근 실제 접수량을 반영한다.

사용자가 요청한 범위는 실시간 인기 문의 조회, 답변을 통한 자가 해결, 담당자 지정, 라벨이다. AI 답변 기능은 사용자 요청으로 제거했다. 답변 생성, 답변 초안, 자동 분류에도 AI를 사용하지 않는다.

이번 설계는 문의 홈, FAQ 상세, 문의 등록, 운영 목록, 운영 상세, FAQ 관리에 적용한다. 앱 코드 구현은 별도 작업이며 이 기획을 검토한 뒤 지정한 Figma 영역의 Light·Dark 화면을 개선한다.

성공 여부는 FAQ를 읽은 뒤 해결했다고 응답한 비율, 같은 질문의 반복 접수 비율, 미배정 문의 수로 확인한다. 출시 전 목표 수치를 임의로 약속하지 않고 첫 운영 기간의 기준값을 확보한다.

## 2. 현재 상태와 이어받는 규칙

2026-09-30에 서버 main의 전체 경로를 조회했다. 문의 ADR은 있지만 inquiry 도메인 구현, FAQ, 담당자 지정, 라벨, 인기 문의 API는 확인되지 않았다. ADR의 상태도 Proposed다. 아래 항목은 구현 완료된 서버 기능이 아니라 기존 합의와 이번 확장 요구다.

- 카테고리는 활성 여부를 관리하는 공통 목록이며 수신 조직을 정한다. 사용자가 담당 조직을 직접 고르지 않는다.
- 문의 등록은 카테고리·본문·첨부로 한다. 제목은 따로 입력하지 않는다.
- 한 문의는 하나의 대화방이다. 접수 → 진행 중 → 종료 상태를 사용한다.
- 종료된 문의에 사람이 새 메시지를 보내면 진행 중으로 다시 열린다. 별도 재오픈 버튼은 두지 않는다.
- 문의 메시지는 수정하거나 삭제하지 않는다. 정정은 새 메시지로 남긴다.
- 문의자는 본인 문의만 보고 응답자는 해당 문의에 응답할 권한이 있는 조직 범위만 본다.
- UMC_PRODUCT 문의는 프로덕트팀을 판별할 수단이 마련된 뒤 연다. 중앙운영사무국 전체로 임시 배정하지 않는다.

근거는 [기존 문의 서버 명세](../server/문의_문의%20채널_서버명세.md), [서버 문의 ADR](https://github.com/UMC-PRODUCT/umc-product-server/blob/main/docs/adr/011-inquiry-domain-with-websocket-stomp.md), [서버 권한 정책](https://github.com/UMC-PRODUCT/umc-product-server/blob/main/docs/guides/프로젝트_권한_정책.md)이다. 권한 정책 문서는 프로젝트 중심이므로 문의 확장의 권한을 이미 지원한다고 해석하지 않는다.

## 3. 문의를 대표 질문에 연결한다

대표 질문은 여러 문의가 같은 문제를 다루는지 구분하는 집계 단위다. 예를 들어 표현이 다른 출석 정정 문의들을 ‘출석이 다르게 표시될 때 어떻게 하나요?’라는 질문에 연결한다. 라벨이 같다는 이유만으로 같은 질문으로 집계하지 않는다.

운영진은 대표 질문을 만들고 문의 상세에서 연결하거나 연결을 해제한다. 한 문의에는 대표 질문 하나만 연결할 수 있다. 잘못 분류한 문의는 대표 질문을 바꿀 수 있으며 변경 전후 집계를 보정한다. 분류하지 않은 문의는 운영 목록의 미분류 필터에서 확인한다.

사용자가 FAQ에서 ‘담당자에게 문의하기’를 누르면 해당 대표 질문을 연결한 상태로 등록한다. 일반 문의 등록에서 추천 답변을 확인한 것만으로는 연결하지 않는다. FAQ 상세에서 문의로 넘어왔다는 명시적인 경로가 있을 때만 연결한다. 운영진이 나중에 다른 질문으로 정정할 수 있다.

문의 원문과 FAQ의 공개용 질문·답변은 별도 데이터다. 개인 이름, 첨부, 계정, 출석 기록, 대화 내용은 FAQ에 자동 복사하지 않는다. 운영진이 공개용 내용을 직접 작성하고 검증한다.

## 4. 실시간 인기 문의

### 4.1 집계와 노출

| 항목 | 규칙 |
|---|---|
| 기본 기간 | 서버 시각 기준 최근 24시간 |
| 보조 기간 | 서버 시각 기준 최근 7일 |
| 집계 단위 | 대표 질문별 고유 문의자 수 |
| 반복 등록 | 같은 문의자가 같은 질문을 여러 번 등록해도 선택한 기간 안에서는 1명 |
| 집계 시점 | 문의 최초 접수 시각. 답변·재오픈·FAQ 조회·검색은 집계를 올리지 않음 |
| 문의 상태 | 접수·진행 중·종료 모두 집계. 스팸 라벨로 제외 처리한 문의는 집계에서 제외 |
| 공개 조건 | 현재 볼 수 있는 발행 FAQ이며 적용 기간이 유효하고 고유 문의자가 3명 이상 |
| 정렬 | 문의자 수 내림차순, 동률이면 해당 기간의 마지막 접수 시각 내림차순, 다시 같으면 대표 질문 식별자 오름차순 |
| 노출 수 | 최대 5개. 부족하면 있는 항목만 노출 |
| 표시 문구 | ‘최근 24시간 · 28명 문의’처럼 단위와 기간을 명시 |

순위는 FAQ의 적용 범위와 연결된 문의의 기수·조직 범위 안에서 계산한다. 공통 FAQ는 해당 기수의 공통 집계, 학교 FAQ는 해당 학교의 집계, 지부 FAQ는 해당 지부의 집계를 사용한다. 서버가 조회자의 공개 범위를 판정하며 클라이언트가 학교 식별자를 임의로 바꿔 다른 범위를 조회할 수 없다.

개인 문의 원문과 문의자 목록은 인기 문의 응답에 포함하지 않는다. 3명 미만인 질문은 공개 순위에서 빠지지만 FAQ 목록에서는 답변을 찾을 수 있다. 같은 기간에 대상이 하나도 없으면 ‘아직 집계된 인기 문의가 없어요’와 전체 FAQ를 보여 준다.

발행 답변이 없는 대표 질문도 내부 집계는 가능하다. 운영진에게 ‘답변 준비 필요’로 보여 주고 공개 순위에는 넣지 않는다. 학교가 다른 질문이나 적용 범위가 다른 질문은 같은 제목이어도 집계를 합치지 않는다.

### 4.2 갱신과 읽기 보호

접수, 대표 질문 변경, 스팸 제외·복원, FAQ 공개 범위 변경을 반영한다. 시간 경과로 집계 기간을 벗어난 접수도 빠져야 하므로 신규 문의가 없는 동안에도 순위를 갱신한다. 변경 후 60초 이내에 조회 결과에 반영하는 것을 서비스 계약으로 한다.

화면을 처음 열면 최신 순위를 조회한다. 연결된 동안 서버 갱신 알림을 받아 새 순위를 준비한다. 사용자가 읽는 중에는 현재 목록을 재배열하지 않고 ‘새 순위가 있어요’ 버튼을 보여 준다. 버튼을 누르거나 기간을 바꾸면 최신 목록으로 교체한다.

갱신 알림의 도착과 현재 표시 데이터의 갱신 시각을 구분한다. ‘마지막 갱신 14:32’는 실제 표시 중인 스냅샷의 서버 시각이다. 연결이 끊기면 ‘실시간 연결이 끊겼어요’와 새로고침을 보여 주며 재연결 시 최신 목록을 다시 조회한다. 60초 계약을 지키지 못하면 실시간 정상 상태를 표시하지 않는다.

## 5. 사용자 흐름

### 5.1 문의 홈과 FAQ 상세

문의 메뉴의 기본 화면은 ‘많이 묻는 질문’이다. 상단에 FAQ 검색과 ‘내 문의’ 전환을 두고 인기 문의 TOP 5와 카테고리별 FAQ를 보여 준다. ‘문의하기’는 검색 결과와 무관하게 접근할 수 있다.

검색은 공개용 대표 질문, 별칭, 검증된 답변을 대상으로 한다. 개인 문의 대화는 검색 대상이 아니다. 결과에는 질문과 카테고리, 적용 범위가 보이고 결과가 없으면 검색어를 유지한 채 문의를 작성할 수 있다.

FAQ 상세에는 질문, 검증된 답변, 카테고리, 적용 대상, 검증한 조직, 수정일, 관련 안내 링크를 표시한다. 개인별 출석 인정이나 환불 승인처럼 담당자의 판단이 필요한 답변은 승인 결과를 약속하지 않고 담당자에게 요청할 방법을 안내한다.

상세 하단의 행동은 ‘해결됐어요’와 ‘담당자에게 문의하기’다. 해결 응답은 동일 사용자가 같은 FAQ 버전에 한 번만 기록할 수 있다. 취소 후 다른 선택을 할 수 있으나 중복 집계하지 않는다. 이 행동만으로 문의를 만들거나 종료하지 않는다.

### 5.2 문의 등록과 내 문의

문의 등록에는 카테고리, 본문, 첨부를 둔다. 카테고리 선택 후 같은 카테고리의 FAQ를 보여 주고 본문 입력 후에는 일반 검색으로 관련 답변을 제안한다. 답변을 읽도록 강제하거나 문의 보내기를 잠그지 않는다.

추천 답변을 열었다 돌아와도 입력 내용과 첨부를 보존한다. FAQ 상세에서 등록한 경우에만 대표 질문 정보를 유지하고 ‘참고한 답변’으로 표시한다. 전송 실패 시 내용은 유지하고 사용자가 다시 보내기를 선택한다. 서버의 중복 접수 방지 계약이 없으면 자동 재전송하지 않는다.

‘내 문의’에는 카테고리, 상태, 내용 요약, 접수일을 표시한다. 문의가 없는 경우에도 많이 묻는 질문을 사용할 수 있다. 답변 도착 여부와 종료 여부를 구분하고 상태 명칭은 접수·진행 중·종료로 통일한다.

## 6. 담당자 지정

카테고리가 정한 수신 조직은 유지하고 그 안에서 담당자 한 명을 선택한다. 초기값은 미배정이다. 담당자 지정 자체는 문의 상태를 바꾸지 않는다. 첫 사람 답변이 접수 상태를 진행 중으로 바꾼다.

운영 목록은 ‘전체 · 내 담당 · 미배정’을 제공한다. 응답 권한이 있는 운영진은 ‘내가 맡기’를 사용할 수 있다. 타인을 지정하거나 담당자를 바꾸는 기능은 서버가 배정 권한을 제공한 운영자에게만 열린다. 후보 목록에도 해당 문의에 실제로 응답할 권한이 있는 사람만 포함한다.

동시에 두 사람이 맡으려 하면 먼저 성공한 한 명만 배정된다. 뒤 요청에는 최신 담당자를 보여 주고 이미 배정됐음을 안내한다. 다른 운영진이 답할 수 있는 기존 조직 권한은 담당자 지정으로 축소하지 않는다. 담당자는 처리 책임을 나타낸다.

운영진은 변경자, 이전 담당자, 새 담당자, 변경 시각을 확인할 수 있다. 담당자가 역할 만료 등으로 응답 권한을 잃으면 자동으로 미배정으로 돌리고 이력을 남긴다. 사용자에게는 담당 조직과 표시용 이름만 보여 주며 내부 변경 이력은 공개하지 않는다.

배정 알림은 새 담당자에게, 해제·변경 알림은 이전 담당자에게 보낸다. 미배정 신규 문의는 수신 조직의 기존 접수 알림을 따른다. 답변 알림은 문의자에게 보낸다. 모든 조직 구성원에게 매번 배정 알림을 보내지 않는다.

## 7. 라벨

라벨은 문의를 처리하기 위한 내부 분류다. 문의에 여러 라벨을 붙일 수 있고 운영 목록에서 라벨로 필터링한다. 카테고리와 대표 질문은 각각 수신 조직과 같은 질문 여부를 정하므로 라벨과 별도로 유지한다.

1차에는 공통 라벨 목록 하나를 사용한다. 예시는 ‘출석 오류’, ‘로그인’, ‘기능 요청’, ‘정보 확인’, ‘스팸’이다. 문의 응답자는 라벨을 부착·제거하고 라벨 관리 권한자는 공통 목록을 생성·이름 변경·비활성화한다. 사용자 화면에는 내부 라벨을 공개하지 않는다.

라벨은 이름만 있고 중첩 구조, 학교별 별도 목록, 라벨별 자동 담당자 규칙은 두지 않는다. 비활성화하면 새로 붙일 수 없고 과거 문의의 표시는 보존한다. 색상만으로 뜻을 구분하지 않고 이름을 표시한다.

‘스팸’은 서버가 관리하는 고정 라벨로 이름 변경·비활성화할 수 없다. 스팸 라벨 부착은 스팸 제외 권한이 있는 운영자만 할 수 있으며 인기 집계에서 제외한다. 제거하면 최초 접수 시각이 집계 기간 안에 있는 문의만 복원한다. 라벨 부착·제거자와 시각을 기록한다. 일반 라벨은 상태나 순위를 바꾸지 않는다.

## 8. FAQ 검증과 발행

운영진은 담당 문의에서 대표 질문을 연결하고 별도의 공개용 답변을 작성한다. FAQ는 초안 → 발행 → 보관 상태를 사용한다. 문의 메시지를 FAQ로 자동 전환하지 않는다.

FAQ에는 대표 질문, 별칭, 답변, 카테고리, 적용 범위, 검증한 조직, 검증자, 수정일을 저장한다. 적용 범위는 기수의 공통 범위, 특정 학교, 특정 지부 중 하나다. 범위를 제한하지 않고 모든 기수에 영구 적용하는 선택지는 1차에 두지 않는다. 종료일은 선택할 수 있으며 종료일이 지나면 공개하지 않는다.

응답자는 자신의 처리 범위 안에서 초안을 작성한다. 서버가 FAQ 발행 권한을 부여한 운영자는 자신의 권한 범위 안에서만 검증·발행한다. 공통 FAQ를 발행할 수 있는 주체와 프로덕트팀 판별은 서버 권한 계약으로 추가해야 하며 클라이언트가 역할 이름으로 추측하지 않는다.

발행 전에 개인정보 포함 여부와 적용 범위, 안내의 정확성을 확인한다. 최초 발행과 발행본 수정에는 명시적인 ‘검증 후 발행’ 행동이 필요하다. 수정 중에는 직전 검증본을 유지하고 새 검증본을 발행할 때 교체한다. 잘못된 답변을 발견하면 즉시 보관해 공개와 추천·순위에서 제외할 수 있다. 답변 버전과 발행·보관 이력을 남긴다.

## 9. 권한과 서버 확장 요구

아래 작업 단위는 신규 계약 제안이다. 경로와 DTO가 구현돼 있다고 가정하지 않는다. 서버팀이 실제 권한 모델과 ADR에 반영한 뒤 API 경로, 필드, 타입, nullable 여부를 확인한다.

| 작업 단위 | 입력과 결과 | 서버에서 확인할 조건 |
|---|---|---|
| 공개 FAQ 조회·검색·상세 | 검색어·카테고리, 공개용 질문·답변·적용 대상·버전 | 현재 사용자에게 유효한 발행본만 반환 |
| 인기 순위 조회·갱신 알림 | 기간, 순위·문의자 수·스냅샷 시각 | 기수·조직 범위, 3명 기준, 공개 여부, 60초 반영 |
| 문의 등록 | 기존 폼, 선택적인 대표 질문 참조 | 카테고리 라우팅, 참조 FAQ 접근 권한, 접수 중복 방지 |
| 대표 질문 연결·변경 | 문의와 대표 질문 참조, 최신 분류 | 응답 권한, 집계 범위 일치, 이전 집계 보정 |
| 담당자 후보·지정·해제 | 문의, 담당자, 현재 배정 버전 | 응답·배정 권한, 후보 적격성, 동시 변경 충돌 |
| 라벨 목록·관리·부착 | 라벨 참조와 변경 내역 | 응답·라벨 관리·스팸 제외 권한 구분 |
| FAQ 초안·검증·발행·보관 | 공개용 질문·답변·범위·버전 | 작성·발행 권한, 버전 충돌, 공개 범위 |
| 해결 응답 | FAQ 버전과 해결 여부 | 인증된 사용자, 동일 버전 중복 방지 |
| 화면 capability | 현재 문의·조직에서 가능한 행동 | 배정·라벨·스팸 제외·FAQ 발행 권한을 명시 |

기존에 제안한 WebSocket·STOMP를 순위 갱신 알림에도 재사용할 수 있는지 서버팀이 검토한다. 공개 집계 알림과 개인 문의 메시지는 권한과 응답 데이터를 분리한다. 구독 권한은 구독 시점과 권한 변경 시점에 검증하고 재연결 때는 전체 최신 스냅샷을 조회한다.

화면은 서버가 내려주는 capability를 사용한다. 버튼을 숨기는 것만으로 권한을 보장하지 않고 모든 변경 요청을 서버에서 다시 검증한다. 기존 프로젝트 capability API가 문의까지 지원한다고 가정하지 않는다.

순위 변경 안내, 검색 결과 없음, 인기 문의 집계 없음, 연결 끊김, 배정 충돌, FAQ 발행 불가 상태는 해당 화면 안에 상태 예시로 표시한다. 모든 상태마다 별도 전체 창을 복제하지 않는다. 화면의 예시 수치는 실제 서비스 데이터가 아니라 시안용 데이터임을 캔버스에 명시한다.

Figma에서는 FAQ·담당자·라벨·문의 접수의 주요 경로를 연결해 검토할 수 있게 한다. 기본 컨트롤을 재사용하고 본문·운영 목록에 불필요한 Glass 효과나 자동 재정렬 애니메이션을 추가하지 않는다. 입력·선택 컨트롤의 이름, 선택 상태, 키보드 탐색 순서를 구분하고 상태는 색상과 문구를 함께 사용한다.

## 11. 수용 기준과 검토 시나리오

- 같은 질문에 4명이 문의하고 한 명이 추가로 3건을 등록해도 공개 집계는 4명이다.
- 24시간·7일 기간 변경, 경계 시각 만료, 재분류, 스팸 제외·복원, FAQ 보관이 집계에 반영된다.
- 학교·지부·기수가 다른 비공개 문의와 FAQ를 검색·순위·구독으로 조회할 수 없다.
- 3명 미만과 발행 답변이 없는 질문은 인기 순위에서 빠진다. 일반 FAQ 탐색은 가능하다.
- 새 순위가 도착해도 읽는 중인 행이 이동하지 않고 사용자의 갱신 행동으로만 교체된다.
- FAQ에서 문의하기를 선택하면 참고한 답변과 대표 질문을 유지한다. 일반 추천 답변 열람만으로는 대표 질문을 연결하지 않는다.
- FAQ 추천 실패·결과 없음 상태에서도 문의를 작성하고 보낼 수 있다.
- 동시에 담당자를 지정해도 한 명만 성공하고 뒤 요청은 최신 배정 상태를 보여 준다.
- 담당자 권한이 사라지면 미배정으로 돌아가고 운영진이 변경 이력을 확인할 수 있다.
- 일반 라벨은 문의 상태와 공개 순위를 바꾸지 않는다. 스팸 제외는 별도 권한과 이력이 필요하다.
- 검증하지 않은 FAQ 수정본은 사용자에게 보이지 않고 기존 발행본이 유지된다.
- 종료된 문의에서 새 사람 메시지를 보내면 진행 중으로 돌아간다. 해결 응답만으로 문의를 종료하지 않는다.
- Light·Dark의 같은 화면에서 텍스트 잘림, 겹침, 대비 부족, 주요 행동의 누락이 없어야 한다.

이 문서 단계에서는 공개 범위·집계·인계 규칙의 모순과 누락을 확인한다. 서버 구현 단계에서는 시간 경계, 권한, 집계 보정, 동시 배정의 실행 가능한 검증을 남긴다. Figma 작업은 화면 연결과 두 테마의 시각 검토로 확인한다.

## 12. 범위 밖

지금은 자동 담당자 분배, 라벨 규칙 엔진, 질문 간 자동 유사도 분류, 별도 분석 대시보드, 응답 SLA 자동 에스컬레이션을 만들지 않는다. 미배정 필터와 수동 분류로 먼저 운영한다. 반복 문의량과 분류 비용이 실제로 커지면 후속 기획으로 다룬다.

기존 앱 전체 기획을 한꺼번에 다시 쓰지 않는다. 문의 확장에는 이 문서를 우선 적용하며 승인 후 기존 PRD의 문의 장과 서버 명세에 필요한 변경만 반영한다. 서버 레포는 읽기 전용으로 조회하고 이 작업에서 서버 레포에 변경 사항을 게시하지 않는다.
