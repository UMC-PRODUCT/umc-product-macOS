## 1. 결정 요약

공지를 **찾기 → 읽기 → 필요한 응답 → 읽음 확인** 순서로 이해하도록 정리한다.
목록은 제목과 선택 상태를 안정적으로 보여 주고, 상세는 읽기 폭과 타이포를 조정한다.
검색 조건은 목록에서 확인할 수 있게 하되, 창 제목 막대의 기존 공지 도구 패널을 유지한다.
새 데이터·필터·권한·API를 추가하지 않고 현재 정보와 행동의 배치·강조만 개선한다.

| 순서 | 우선순위 | 핵심 개선 | 사용자가 얻는 변화 |
| --- | --- | --- | --- |
| 1 | P1 | 전체 목록과 분할 목록의 행 구조 통일 | 같은 제목·고정·선택·읽음을 계속 식별한다. |
| 2 | P1 | 상단 검색과 적용 조건 요약 | 패널을 닫아도 어떤 공지를 보고 있는지 안다. |
| 3 | P1 | 상세 읽기 폭과 제목/본문 비율 | 제목보다 작은 본문을 과도하게 넓은 줄로 읽지 않는다. |
| 4 | P1 | 투표·첨부·읽음 확인의 단계 구분 | 읽기와 제출을 혼동하지 않고 다음 행동을 찾는다. |
| 5 | P2 | 상세 관리·작성·읽음 현황의 행동 계층 | 운영 동작이 본문과 경쟁하지 않고 게시 상태를 이해한다. |
| 6 | P2 | 로딩·빈 목록·오류의 자리와 표현 | 데이터가 없는 이유와 복구 행동을 구별한다. |
| 7 | P1 공통 | 작은 창·다크·긴 한글·키보드 기준 | 위 개선이 창 크기와 입력 방식에 따라 무너지지 않는다. |

P1/P2는 이 문서 안의 적용 순서이며 서버 작업 우선순위를 뜻하지 않는다.

## 3. 목표 레이아웃

앱의 탐색 레일과 제목 막대는 그대로 두고 그 아래 공지 콘텐츠를 정돈한다.
목록 미선택 상태에서 새 빈 상세 열을 만들지 않는다. 선택 후 분할 읽기로 전환하고,
전체 읽기는 기존처럼 목록을 숨긴다. 전체 읽기를 ‘별도 창 열기’로 바꾸지 않는다.

```text
창 제목 막대  [이전][앞으로]                              [기존 공지 도구]
┌──────────────────── 공지 콘텐츠 ─────────────────────────────────┐
│ [공지 목록] [전체 읽기 / 분할 보기]               [공지 작성*]     │
├───────────── 목록 280–340pt ────┬────────────── 상세 ─────────────┤
│ [제목, 내용 검색         ][검색]│ 대상 · 고정       [읽음 현황*][…*]│
│ 챌린저 · 전체 파트 · 전체       │ 제목 (여러 줄 허용)               │
│ 고정 공지 (불러온 개수) ▾      │ 작성자 · 날짜 · 조회              │
│ ┌ 제목 최대 두 줄 ──────────┐ │ ──────────────────────────────── │
│ │ 대상 · 고정    읽음       │ │ 본문: 최대 680pt                  │
│ │ 작성자 · 날짜 / 첨부 표시 │ │ 사진 → 투표 → 링크               │
│ └──────────────────────────┘ │ ──────────────────────────────── │
│ 최근 공지                      │ 읽음 상태               [확인]   │
│ …                              │                                  │
└───────────────────────────────┴──────────────────────────────────┘
* 기존 권한이 허용한 동작만 표시. …는 수정/삭제, 빈 메뉴는 생략.

전체 목록: 같은 행 순서 + 본문 미리보기 2줄, 목록 콘텐츠 최대 960pt.
전체 읽기: 목록/목록 검색을 숨기고 같은 상세 읽기 열을 가운데 배치.
           검색은 기존 제목 막대 공지 도구 패널에서도 계속 이용 가능.
```

분할 목록 폭은 현재 최소/이상/최대 168/280/340pt에서 제안 280/300/340pt로 조정한다.
680pt 읽기 폭과 960pt 목록 최대폭은
**신규 화면 치수 제안**이며 공통 토큰이나 Figma 확정값이 아니다.
도구 패널은 기존 최대 390pt·상단/우측 4pt 배치를 유지한다.

## 4. 우선순위별 상세 설계

### 1) P1 — 제목과 상태가 유지되는 목록 행

**현재 문제:** Board:310은 읽음 전 `.title3Bold` 18pt, 읽음 후 `.headlineRegular` 14pt로 바뀐다.
같은 제목의 크기와 줄바꿈이 확인 전후 달라질 수 있다. 분할 목록은 최소 168pt인데
내부 좌우 20pt·외부 12pt를 제하면 제목과 메타를 위한 폭이 매우 좁다(Board:117·296·340).
고정은 배경·좌측 막대·라벨로, 선택도 배경으로 강조돼 두 상태의 시각 신호가 겹친다.

**결정:** 전체/분할 모두 **제목 → 대상·고정/읽음 → 미리보기(전체 목록만) → 메타·첨부** 순서다.
Figma의 대상 우선 순서를 그대로 옮기지 않고 현재 코드의 제목 우선 순서를 명시적으로 유지한다.
제목은 `.title4Bold` 16pt로 통일하고, 읽음 후에도 크기를 바꾸지 않는다. 읽음은 기존 체크·문구로
표현하며 `readIDs`에 없는 항목을 ‘미확인 서버 읽음 상태’나 ‘안 읽음’으로 새로 판정하지 않는다.

선택 행은 `fillPrimaryStrong200`, 비선택 행은 `Custom.backgroundSurface`를 사용한다.
고정은 `pin.fill` + ‘고정’ 라벨로 충분하며 큰 배경 강조와 좌측 3pt 막대는 제거하는 방향이다.
선택 테두리/접근성 선택 상태, 키보드 포커스, 고정 라벨, 읽음 라벨은 각자 독립적으로 남긴다.
외부 여백 12pt, 행 내부 16pt, 행 간격 8pt, 모서리 12pt를 사용한다.
행 높이는 고정하지 않고 제목 2줄과 메타 줄바꿈에 따라 늘어난다.

목록 전체 화면에서는 폭 960pt 이내로 가운데 정렬한다. 분할에서는 목록 최소 280pt·이상 300pt·최대
340pt를 **화면 치수 제안**으로 둔다. 기존 최소 168pt를 억지로 유지하며 글자를 줄이지 않는다.
고정 수는 현재 불러온 항목 수이며 서버 전체 건수처럼 표시하지 않는다.

### 2) P1 — 검색을 바로 찾고 조건을 잊지 않는 상단

**현재 문제:** Board:219–250의 검색·전체/고정·대상·파트가 모두 도구 패널 안에 있다.
패널을 닫은 목록에서는 조건을 알아보기 어렵고, 검색할 때 목록이 비활성화된다(Tools:41).
이는 #170의 제목 막대 위치 문제가 아니라 검색과 목록을 오가는 비용이다.

**결정:** 전체/분할 목록 상단에 기존 ‘제목, 내용 검색’ 필드와 검색 버튼을 노출한다.
바로 아래 `.calloutRegular`로 적용된 대상·해당 시 파트·전체/고정·제출된 검색어를 요약한다.
사용 중인 `model.keyword`와 입력 중 `search`를 구별해, 아직 제출하지 않은 글자를 결과 조건으로
표시하지 않는다. 검색은 현재처럼 Return/버튼으로 제출하고 자동 실시간 검색을 새로 넣지 않는다.

기존 공지 도구 패널은 초기화·빠른 보기·대상·파트·새로고침을 유지한다.
전체 읽기에서도 찾을 수 있도록 패널의 검색 필드를 유지하되 **같은 입력 상태와 제출 함수**를 쓴다.
두 독립 검색 모델을 만들지 않는다. 상단에 필터 Picker를 모두 복제하지 않는다.
현재 ⌘F는 공통 도구 버튼을 토글하므로 이 설계에서는 그 동작을 유지한다.
직접 검색 포커스로 바꾸는 공통 단축키 개편은 별도 변경 없이 필수 조건에 넣지 않는다.

[기존 버튼 가이드](../Codex/tab-button-guide.md)의 목록 검색 권고는 참고하되,
그 문서의 과거 팝오버/내부 도구 배치 설명보다 #170의 현재 공통 패널 구현을 우선한다.

### 3) P1 — 제목·메타·본문의 읽기 비율

**현재 문제:** Article:116은 32pt/48pt 제목, :127은 12pt/16.8pt 본문,
:173은 최대 980pt 폭이다. 사용자 첨부에서는 짧은 본문에 비해 제목·투표 상자가 크게 느껴진다.
긴 공지에서의 실제 읽기 속도는 측정하지 않았지만 크기 차이와 최대 줄 폭은 코드로 확인된다.

**결정:** 상세 헤더를 **대상과 고정 → 제목 → 작성자·작성일·조회 → 구분선**으로 묶는다.
제목 `.title1Bold` 22pt/28.6pt, 본문 `.headlineRegular` 14pt/19.6pt,
메타 `.calloutRegular` 12pt/16.8pt를 쓴다. 제목을 고정 높이·두 줄로 잘라 버리지 않는다.
구분선 전후 16pt, 제목과 메타 8pt, 본문과 부속 섹션 24pt로 묶음의 크기를 구별한다.

본문·사진·투표·링크·확인 영역을 같은 최대 680pt 열에 놓고 상세 영역 안에서 가운데 정렬한다.
좁을 때는 좌우 24pt를 제외한 가용 폭을 사용한다. 전체 읽기에서도 680pt 상한을 유지한다.
전체 읽기는 더 넓은 한 줄이 아니라 목록을 잠시 감춘 집중 읽기다.
본문 선택·복사, 기존 링크 검증과 줄바꿈 보존은 유지한다.

### 4) P1 — 본문 아래의 사진·투표·링크·읽음 확인

**현재 문제:** Article:135–171에는 사진·투표·링크·읽음 확인이 이어지지만,
투표 안 정보가 한 문자열이고 링크는 URL 그대로여서 긴 값에서 계층이 약해진다.
사용자 첨부의 투표 제출과 읽음 확인은 서로 다른 행동인데 비슷한 버튼 표현이다.

**결정:** 현재 순서 **본문 → 사진 → 투표 → 링크 → 읽음 확인**은 유지한다.
사진은 기존 160×110pt 썸네일·가로 스크롤·확대를 유지한다. 개수와 ‘사진’ 레이블을 섹션 제목으로
묶고 이미지가 없으면 빈 틀을 만들지 않는다. 링크는 제목·OG 데이터를 새로 수집하지 않고
기존 URL과 링크 심벌을 하나의 행으로 묶어 여러 줄을 허용한다.

투표는 중립 표면과 얇은 테두리를 사용한다. ‘진행 중인 투표/투표’ → 질문 → 선택 방식·익명 여부·
참여 수 → 마감 → 선택지 → 제출 순서로 읽힌다. 선택지와 표 수를 구분하되 현재 공개 정보만 쓴다.
체크박스는 공통 `UMCCheckboxStyle`을 유지한다. 선택지 전체 영역의 키보드 조작·상태 낭독을 보존한다.
투표 제출/취소와 비활성 조건, 응답 후 재조회는 현재 코드 그대로다.

**#165 연결:** 마감 날짜·시각은 해당 수정의 로케일·표시 시간대 포맷을 사용한다.
`endsAtExclusive.prefix(10)`를 새 UI에 복제하지 않는다. 목록에는 `hasVote`만 있을 수 있으므로
그때는 ‘투표’ 표시만 두고 마감·남은 시간·참여율을 만들지 않는다. 행별 상세 요청도 추가하지 않는다.

읽음 확인은 본문 끝 구분선 아래 독립 행에 둔다. 기존 확인 버튼과 완료 문구를 유지하고
확인 뒤에는 체크 상태가 드러나게 한다. 투표를 제출했다고 읽음 확인을 자동 실행하지 않는다.
읽음 확인을 화면 하단에 고정해 본문을 덮거나 모든 공지에 새 필수 행동처럼 강조하지 않는다.

### 5) P2 — 운영 동작과 작성 상태를 읽기 흐름에서 분리

**현재 문제:** Article:90의 ‘읽음 현황·수정·삭제’가 동일한 상단 행에 모두 놓인다.
Composer:147은 복구 상태에 따라 여러 버튼이 함께 나타나고, 읽음 현황(Article:330)은
요약·필터·대상·발송·닫기가 같은 세로 흐름에 있어 작업의 끝점이 약하다.

**결정:** 읽음 현황은 허용된 경우 상세 헤더의 보조 버튼으로 남긴다.
수정·삭제는 같은 위치의 더보기 메뉴에 묶고 삭제는 마지막에 파괴적 의미를 유지한다.
`CHECK`·`EDIT`·`DELETE` 조건과 재검증·권한 회수 처리를 그대로 적용하며 빈 메뉴는 숨긴다.
역할 이름이나 Figma 화면 이름만으로 메뉴를 켜지 않는다.

작성/편집은 기존 시트를 유지한다. ‘공지 내용·첨부·투표’ 그룹과 하단 동작 행을 분리하고,
본문 폼은 스크롤되더라도 취소와 현재 완료 동작은 식별되게 한다. 게시·저장·게시 결과 확인·
투표 등록 결과 확인·첨부 저장 재시도 중 **현재 상태의 완료 동작 하나**만 주 강조한다.
‘별도 공지로 작성’·‘이 작성 시도 버리기’는 보조/파괴적 동작으로 구분한다.
이미 저장된 부분·결과 미확정·입력 잠금과 기존 확인 다이얼로그를 생략하지 않는다.

읽음 현황은 제목 → 전체/읽음/안 읽음 요약 → 기존 상태 Picker → 명단 → 상태/더 보기 →
하단 닫기·리마인드 순서로 정돈한다. 요약은 차트나 새 비율 없이 기존 세 수치만 쓴다.
안 읽음 탭에서만 기존 대상 선택과 발송을 노출하고 발송 확인·중복 방지·성공 문구를 유지한다.
선택 인원 표시는 현재 `targets.count`로 표현 가능한 보조 정보이며 새로운 집계를 요청하지 않는다.

### 6) P2 — 비어 있는 이유와 다음 행동이 보이는 상태

**현재 문제:** Board:270–292의 로딩·오류·빈 상태는 목록 끝에 이어진다.
‘고정 없음’과 전체 빈 상태가 조건에 따라 함께 보일 여지가 있다.
과거 오류 캡처의 러너 부재는 해결됐으므로 현재는 오류 설명·재시도·러너의 우선순위를 다룬다.

| 기존 상태 | 표현 제안 | 유지할 동작 |
| --- | --- | --- |
| 첫 목록 로딩, 항목 0 | 목록 상단 위치에 중립 placeholder 행 3개와 ‘공지를 불러오는 중’ 상태 하나. 반짝임 없음 | 현재 요청·취소 흐름. placeholder는 선택 불가·VoiceOver 탐색 제외 |
| 동일 필터의 더 불러오기/기존 데이터 갱신 | 기존 행을 유지하고 목록 끝에 작은 진행 표시 | 페이지 추가와 중복 제거. 필터가 바뀌면 기존 초기화 유지 |
| 실제 빈 목록 | ‘공지가 없습니다’와 현재 대상 요약 | 기존 작성 가능 조건만 사용 |
| 검색 조건으로 비어 있음 | 검색 결과 없음 상태와 기존 초기화 동작 연결 | 검색·필터 모델과 초기화 의미 유지 |
| 현재 페이지에 고정 0건 | 다음 페이지가 있으면 ‘현재 불러온 공지에 고정된 항목이 없습니다’와 기존 ‘더 보기’. 마지막 페이지에서만 고정 없음으로 확정 | `pinnedOnly`는 불러온 페이지에만 적용. 자동 추가 요청 없음 |
| 연결 실패, 항목 0 | 제목·사용자용 오류 설명·다시 시도, 그 아래 기존 편지 배달 러너 | #169의 오류 판별·재시도 페이지·연결 복구 재조회 |
| 동일 필터의 연결/추가 페이지 실패, 항목 있음 | 현재 행 아래 짧은 오류와 다시 시도. 전체 목록을 오류 화면으로 교체하지 않음 | `failedPage` 재시도. 권한 회수에는 적용하지 않음 |
| 권한/검증 실패 | 해당 오류 문구와 기존 복구 동작. 연결 오류나 게임으로 꾸미지 않음 | 목록 권한 회수는 목록 전체, 개별 공지 권한 회수는 해당 항목과 상세·관리 동작 정리 |
| 상세 최초 로딩/실패 | 상세 열 안에서 제목·본문 자리를 유지한 로딩/재조회 안내 | 상세 권한 확인과 기존 재조회 함수 |

상태 영역은 읽기 열과 같은 최대 680pt, 내부 24pt·요소 간격 12pt를 제안한다.
이는 표현 컨테이너 규칙이지 새 오류 모델이나 재시도 정책이 아니다.
오류 설명을 장식용 옅은 글자로 낮추지 않고 `textNeutralMedium600` 이상을 사용한다.
러너는 재시도보다 아래에 두고 자동 포커스·새 자동 시작을 추가하지 않는다.

### 7) P1 공통 — 작은 창과 접근성에서도 같은 순서

앱 최소 창 1040×720pt, 일반 1440×960pt에서 전체 목록·분할·전체 읽기를 확인한다.
창 폭과 글자 크기가 달라도 제목을 작은 글자로 축소하지 않는다. 목록 메타는 작성자/날짜와
조회/첨부를 두 줄로 나눌 수 있고, 제목·선택 표시·고정/읽음이 먼저 남아야 한다.

본문 최대폭은 상한이며 고정 폭이 아니다. 늘어난 글자에서도 가용 폭에 맞춰 줄바꿈하고,
사진만 기존 가로 스크롤을 허용한다. 전체 화면·문장·투표 선택지에는 가로 스크롤을 만들지 않는다.
`GeometryReader`와 측정값의 State/PreferenceKey 환류를 사용하지 않는다.
기본 스택·가용 폭·`containerRelativeFrame`을 우선하고 필요한 경우에만 `Layout`을 검토한다.

Tab/Shift-Tab의 읽기 순서는 내부 작업 → 검색 → 목록 → 상세 관리 → 콘텐츠 행동이다.
행의 전체 제목을 접근성 이름으로 제공하고 선택·고정·읽음·첨부 유무는 상태로 구분한다.
도구가 열리면 뒤 콘텐츠는 현재처럼 입력·VoiceOver에서 제외하고 Esc로 닫으면 트리거에 복귀한다.
메뉴/시트 역시 닫은 뒤 원래 동작으로 복귀하며 항목이 사라졌으면 목록으로 이동한다.

새 장식 모션을 추가하지 않는다. 공통 체크 전환의 Reduce Motion 대체를 유지한다.
기존 러너의 움직임 접근성 문제를 발견하면 #169 후속으로 기록하며 이 문서가 검증 완료를 보증하지 않는다.
색상만으로 상태를 구분하지 않고 Light/Dark·대비 증가·투명도 줄이기에서 포커스와 경계를 확인한다.

## 5. 적용할 토큰과 신규 치수

수치는 기본 글자 배율 1.0 기준이다. `headlineRegular`를 본문에 사용한다는 결정은
토큰 자체를 변경하는 것이 아니다. 실제 글자 크기 환경 설정의 배율을 유지한다.

Figma Mid-fi의 구 변수 값을 현재 asset에 덮어쓰거나 시안의 Noto Sans KR을 새로 추가하지 않는다.

## 6. 기능을 유지하는 적용 순서와 수용 기준

1. **목록 행·읽기 열부터:** 제목 크기, 상태 표현, 폭, 여백을 적용한다. 데이터와 요청 함수를 그대로 두고
   전체 목록 → 분할 → 전체 읽기 → 분할 복귀에서 같은 항목과 기존 필터 상태가 유지되는지 확인한다.
2. **검색 노출과 관리 묶음:** 같은 검색 binding/submit을 재사용하고 조건 요약을 추가한다.
   공통 제목 막대 패널과 ⌘F 동작은 유지한다. 수정·삭제를 메뉴로 옮겨도 권한별 노출·확인 동작은 같다.
3. **본문 부속과 상태:** 사진·투표·링크·읽음 확인, 작성/읽음 현황, 로딩·빈 상태·오류의 위계를 정리한다.
   #165가 병합되면 그 포맷을 참조하고 충돌 시 날짜 표시 코드를 원복하지 않는다.
4. **아래 행렬로 시각·입력 검수:** 실제 앱의 미리보기 데이터와 기존 테스트 시나리오를 사용한다.
   화면만 바꾸기 위한 서버 데이터 생성·읽음 변경·리마인드 발송은 실행하지 않는다.

## 7. 데이터·권한·검증 한계

서버 main [`ea582a17`](https://github.com/UMC-PRODUCT/umc-product-server/commit/ea582a17c74cabfd6f7daeddd8336ae85369d8f2)의
[GetNoticeSummaryResponse](https://github.com/UMC-PRODUCT/umc-product-server/blob/ea582a17c74cabfd6f7daeddd8336ae85369d8f2/monolith/src/main/java/com/umc/product/notice/adapter/in/web/dto/response/query/GetNoticeSummaryResponse.java#L17)와
[NoticeVoteInfo](https://github.com/UMC-PRODUCT/umc-product-server/blob/ea582a17c74cabfd6f7daeddd8336ae85369d8f2/monolith/src/main/java/com/umc/product/notice/application/port/in/query/dto/NoticeVoteInfo.java#L15)를
읽어 목록 요약과 상세 투표 데이터의 차이를 확인했다. 권한 정책 전체를 재감사하지 않았으며
현재 capability 결과와 처리 흐름을 변경하지 않는다. 서버 신규 지원·담당자 작업·일정의 합의를 뜻하지 않는다.

이 산출물은 설계 문서다. 최신 소스·실제 과거 캡처·공식 Figma 렌더와 일부 변수/asset를 대조했고,
문서 링크·출처·토큰·범위 일관성을 검사했다. 앱 코드를 변경하거나 새 빌드·실사용 계정·키보드·
VoiceOver를 직접 검증하지 않았다. 수용 기준은 후속 구현에서 실행할 검사이며 통과 보고가 아니다.
`impeccable`의 Operate/Read·계층·타이포 기준을 참고한 단일 문맥 설계 검토이며,
독립 에이전트 평가와 detector를 갖춘 정식 critique 실행 결과로 주장하지 않는다.

공지 내부 범위에 필요한 개선만 제안하므로 새 PRODUCT.md·DESIGN.md나 전체 디자인 시스템을 만들지 않는다.
기존 색상/행동을 활용하고 신규 치수는 화면 제안으로 제한하므로 지금 다른 팀에 요청할 API·토큰 변경은 없다.
향후 공통 토큰을 바꾸거나 시안을 확정해야 하면 별도 작업에서 Handbook의 당시 담당자를 확인한다.
