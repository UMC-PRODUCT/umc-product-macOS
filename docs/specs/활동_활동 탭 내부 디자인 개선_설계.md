## 1. 결정 요약

활동은 **일정 확인 → 현재 출석 행동 → 결과 확인**, 운영에서는 **일정별 명단 → 사유 확인 → 개별 판정**을 빠르게 수행하는 화면이다. 현재의 상태 카드와 두 일정 목록을 유지하고 시간·결과·선택의 위계를 분리한다. 스터디와 구성원은 검색·행별 행동 중심으로 정돈한다. 공지의 읽기 화면이나 달력을 새로 만들지 않는다.

| 순서 | 우선순위 | 핵심 개선 | 사용자 효과 |
| --- | --- | --- | --- |
| 1 | P1 | 상단 제목·하위 탭·전체 행동의 범위 분리 | 현재 화면과 일정 만들기·새로고침의 대상을 구별한다. |
| 2 | P1 | 일정 시간과 출석 결과를 분리한 상태 카드 | ‘출석 가능 시간’과 ‘내 요청 결과’를 혼동하지 않는다. |
| 3 | P1 | 두 일정 목록의 시간·선택·행 구조 정돈 | 같은 날 여러 일정과 현재 선택을 빠르게 확인한다. |
| 4 | P1 | 출석 검토 명단의 사유·상태·행동 배치 | 긴 사유를 읽으면서 올바른 사람을 승인·거절한다. |
| 5 | P2 | 스터디 도구·커리큘럼·구성원 검색 위계 | 현재 그룹의 도구와 전체 구성원 검색을 구별한다. |
| 6 | P1 | 작성·배정·위치·사유 시트의 입력 그룹과 주 행동 | 필수값과 완료 행동을 찾고 결과 확인 상태를 보존한다. |
| 7 | P1 공통 | 로딩·빈 결과·조회 실패·작업 실패의 분리 | 실패한 요청을 빈 데이터나 성공으로 오인하지 않는다. |

P1/P2는 이 문서의 구현 순서다. API·권한·데이터·출석 정책 변경은 포함하지 않는다.

## 3. 현재 화면·행동 지도와 보존 경계

```text
앱 활동 탭 / 홈의 활동 이동 / 메뉴 막대 ‘활동 열기’
  ├ 출석 체크 → 선택 일정 카드 + 다가오는 일정 + 최근 출석 상태
  │    ├ 비대면: 지금 출석 요청 → 결과·재조회
  │    ├ 대면: 위치 시트 → 명시적 위치 확인 및 출석 요청
  │    └ 사유 제출 시트 / 결과 다시 확인
  ├ 스터디/활동 → 내 커리큘럼 → 그룹 선택 → 그룹 도구 → 멤버 검색·프로필
  │    └ 그룹 만들기 / 그룹 편집 / 멤버·멘토 배정 / 기존 일정과 주차 연결
  ├ 구성원 → 이름·닉네임 검색 + 파트 → 페이지 → 프로필 → 허용된 포인트 관리
  └ 출석 관리 [canReview] → 일정별 명단 → 대기 행 승인/거절 → 확인 Alert
상단 일정 만들기 [canCreate] → ScheduleEditor → 저장·출석 목록 재조회
```

### 시간·날짜·결과의 정확한 경계

Data:118은 `Calendar.current.startOfDay` 기준 ±30×24시간 범위, `isAttendanceRequired=true`로 조회하고 startsAt 오름차순으로 정렬한다. ISO8601 소수초 유무를 처리하며 화면은 현재 날짜 포맷을 사용한다. ‘전체 일정’, 월별 달력, 새로운 시간대 선택을 추가하지 않는다.

Activity:304의 자동 선택은 **선택 ID → 현재 출석 창에 해당하는 첫 일정 → endsAt이 미래인 첫 일정 → 마지막 일정** 순서다. 목록은 `endsAt >= now`와 `status != nil` 역순을 그대로 사용한다. 원래 분류·선택·정렬을 재설계하지 않는다.

Activity:322의 open은 opens/closes 존재, `opens <= now <= closes`, `endsAt >= now`다. 정시/지각은 onTime 경계, 마감은 `(closes ?? endsAt) < now`다. UI 시간 표시는 30초 Timeline 갱신이며 서버 실시간 이벤트가 아니다. ‘LIVE’나 서버 동기화 완료 시각을 붙이지 않는다. 남은 분은 기존 ceil 계산을 유지한다.

시간 필드가 누락된 경우 임의 시간을 채우거나 새로운 판정 규칙을 만들지 않는다. 날짜를 넘기는 일정은 **시작·종료 양쪽 날짜**를 보여 주고, 정시·지각 마감도 시작일과 날짜가 다르면 날짜를 함께 쓴다. 화면에 현재 시간대의 식별자를 보조로 표시할 수 있으나 변환·조회 경계는 변경하지 않는다. 자정·정시·지각 마감의 직전/정각/직후 및 DST 표본은 후속 계약 회귀 검수 대상이다.

## 5. 개선별 구현 결정과 수용 기준

### 5.1 상단: 탐색과 전체 동작의 범위

### 5.2 선택 일정 카드: 시간과 내 결과를 동시에 이해하기

**현재 문제·근거:** Activity:357의 `status(...fallback: phase)`는 결과가 있으면 시간상 phase를 대체한다. :361은 시작 시각과 장소를 한 줄에 연결하며 종료 시각은 표시하지 않는다. :365의 ‘일정 확인’ 체크는 사용자가 확인을 완료했다는 사실의 데이터가 아니다. 구시안 `291:887/291:3830`의 4단계 장식과 LIVE도 구현 사실과 다르다.

**유지·수용:** phase/open/남은 분 계산과 버튼 조건은 §3 그대로다. nil status를 곧바로 결석으로 표현하지 않는다. 온라인 즉시 요청과 대면 위치 시트의 버튼 이름을 구별한다. 사유 제출 조건 `[nil,LATE,ABSENT]`를 임의로 축소하지 않는다. 상태가 있어도 시간 정보를 숨기지 않되 출석 버튼을 다시 노출하지 않는다. 긴 일정명은 무제한 줄바꿈, 전체 장소·마감은 잘리지 않으며 행동은 다음 줄로 이동한다. 링은 중복 AX 탐색에서 제외하고 ‘정시/지각 마감까지 N분’ 정보를 카드의 텍스트로 제공한다. 30초마다 VoiceOver가 전체 카드를 재낭독하거나 포커스를 옮기지 않는다.

### 5.3 일정 목록: 시간, 선택, 결과를 다른 신호로

**현재 문제·근거:** Activity:410–427은 월·일, 이름, status fallback ‘예정’만 나열한다. selectedSchedule을 바꾸지만 선택 테두리/AX 선택값이 없다. 시간은 Domain:24에 이미 있다. 시안 `291:887`의 목록은 날짜·제목·시각을 구분한다.

**결정:** 두 목록을 유지한다. 행 안쪽12pt, 가로 간격12pt, 날짜·시각은 leading의 **최소64pt 신규 화면 치수 제안** 영역에 두고 제목14pt와 방식12pt를 가운데에 배치한다. 제목2줄 뒤 말줄임은 허용하되 전체 이름을 help/AX로 제공하고 선택 카드에는 전부 보인다. 상태는 trailing에 고유 폭으로 두며 공간이 부족하면 제목 아래로 이동한다. 선택된 schedule ID 행은 브랜드 약한 표면+1pt 테두리(신규 화면 치수 제안), AX ‘선택됨’으로 표시한다. 시스템 포커스 링은 별도로 유지한다. 자동 선택된 카드도 같은 ID로 표시한다.

**유지·수용:** 다가오는 목록의 무상태 ‘예정’은 내 출석 결과가 아닌 목록 fallback이다. 카드의 출석 가능 phase와 혼동하지 않도록 AX에서 ‘출석 결과 없음, 일정 목록 표시 예정’처럼 맥락을 준다. 새 상태 정책·검색·달력·필터를 만들지 않는다. 두 목록에 같은 일정이 있으면 같은 ID의 선택 표시를 일관되게 제공한다. 클릭 후 스크롤을 강제로 최상단으로 보내거나 포커스를 카드로 훔치지 않는다. 좁은 폭은 §4에 따라 두 목록을 세로로 놓고 시간·상태·버튼을 보존한다.

**현재 문제·근거:** Activity:449–464는 이름·사유·상태·승인·거절을 한 HStack에 둔다. 긴 사유와 두 버튼이 경쟁할 수 있다. 과거 명단 캡처는 상태가 양끝으로 멀리 떨어지는 구조를 보여 주지만 긴 사유나 승인 버튼의 실제 충돌은 미검증이다. 구시안 `291:1931`의 통계 데이터는 현행 AttendanceReview에 없다.

이번 PR은 설계 문서와 색인 두 파일만 바꾼다. 구현 완료·접근성 통과·서버 지원 완료를 선언하지 않는다. 후속 구현에서는 동작 변경이 없다는 이유만으로 검수를 생략하지 않으며, 권한·데이터 처리 변경이 필요하면 별도 범위와 리뷰를 거친다.
