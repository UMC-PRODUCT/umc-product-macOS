# UMC macOS 앱 PRD

작성일: 2026-09-20
수정일: 2026-09-30
작성자: 제옹(euijjang97)
상태: 프로젝트 작업 공간·앱 내 업데이트 정책 반영 · 연동 검증 전
대상: 프로덕트 · 디자인 · iOS/macOS 개발 · 운영

## 1. 문서 목적

이 문서는 UMC macOS 앱의 제품 요구사항을 정리한 PRD입니다. 디자인 관점에서 이해하고 논의할 수
있도록 기능의 배경, 사용자별 권한, 핵심 흐름, 화면 요구사항과 미결정 항목을 한곳에 모았습니다.

화면 ID는 이 PRD에서 고정해 사용합니다. Figma 프레임에도 같은 ID를 붙여 문서와 디자인을
빠르게 대조합니다. 기존 설계에 없던 매칭 관리 흐름은 `M3`과 `M4`로 확장했습니다.

### 기준 문서

- `docs/specs/macOS앱_전 사용자 데스크톱_설계.md`

세부 API 계약과 구현 구조는 기준 문서를 따릅니다. 이 문서는 사용자가 무엇을 보고 어떤 행동을
할 수 있어야 하는지에 집중합니다.

## 2. 제품 한 줄 설명

UMC 구성원이 공지와 대화를 확인하고 프로젝트에 지원하며 PM·디자인·개발 작업의 자료와
결정 사항을 연결해 구현을 준비하고 이어가는 macOS 데스크톱 앱입니다.

## 3. 배경과 문제

UMC의 주요 활동은 iOS 앱, 웹, 노션, 카카오톡과 디스코드에 흩어져 있습니다. 모바일에서도
처리할 수 있습니다. 다만 긴 글을 작성하거나 표를 비교하고 여러 지원서를 연속으로 검토하는 일은
데스크톱에 더 적합합니다.

팀이 만들어진 뒤에는 요구사항·디자인·개발 이슈가 흩어져 구현 기준을 다시 찾는 일이 반복됩니다.
어떤 정책이 미결정인지, 수정한 화면이 어느 기능과 연결되는지도 확인하기 어렵습니다.
운영진에게 문의할 공식 채널도 없어 처리 과정과 답변 기록이 남지 않습니다.

이 앱은 다음 문제를 해결합니다.

- 공지 작성과 읽음 현황 확인처럼 넓은 화면이 필요한 운영 업무가 모바일에 묶여 있습니다.
- 프로젝트 공고, 지원, 심사를 처리할 때 웹과 모바일을 오가야 합니다.
- 구현 전 자료 탐색과 구현 중 미결정 확인을 도울 공간이 없습니다.
- PM·디자인·개발이 같은 기능의 요구사항과 작업 근거를 연결해 보기 어렵습니다.
- 공식 문의 창구가 없어 질문과 처리 기록이 외부 메신저에 흩어집니다.
- 역할과 프로젝트 관계에 따라 권한이 달라지지만 사용자는 자신이 할 수 있는 일을 화면에서
  즉시 파악하기 어렵습니다.

## 4. 제품 목표

### 4.1 목표

- 챌린저가 맥에서 공지를 읽고 스레드에 참여하며 프로젝트에 지원할 수 있게 합니다.
- 운영진이 공지 작성, 읽음 통계 확인, 지원서 심사를 넓은 화면에서 처리할 수 있게 합니다.
- 기능별 자료·준비 항목·미결정을 정리하고 마지막 작업을 이어갈 수 있게 합니다.
- 한 명만 사용해도 도움이 되며 선택한 자료를 AI 작업 설명으로 편집·복사할 수 있게 합니다.
- 권한이 없는 기능을 숨기거나 비활성화하고 가능한 행동은 이유와 함께 명확하게 보여 줍니다.
- 기능이 추가되어도 사이드바와 전체 화면 구조가 흔들리지 않도록 일관된 탐색 구조를 유지합니다.

### 4.2 1차 범위에서 제외하는 것

- 리크루팅 도메인
- 앱이 꺼져 있을 때 받는 원격 푸시
- 공지 AI 초안과 스레드 자동 분류
- 프로젝트 팀 공유·초대·담당자 전송·다중 기기 동기화
- 자동 누락 점검·변경 감시·원문 양방향 동기화
- 토큰 사용량 대시보드·자동 코드 생성·새 문서 편집기
- AI를 통한 공지와 마감일 조회
- 문의 메시지 편집과 삭제
- 챌린저 문의 목록의 안 읽음 배지
- macOS 26 미만 지원
- App Store 배포

## 5. 대상 사용자

### 5.1 챌린저

공지 확인, 스레드 대화, 프로젝트 작업과 지원이 주요 목적입니다. 운영 기능은 보이지 않습니다.
본인이 참여한 방과 지원 가능한 프로젝트만 다루며 문의는 본인이 등록한 것만 다룹니다.

### 5.2 운영진

운영진은 챌린저 기능을 기본으로 사용하고 필요할 때 `운영진 모드`를 켭니다. 공지 작성과 읽음 통계,
권한 범위의 문의 처리가 추가로 열립니다.

### 5.3 Project PO와 Sub-PO

Project PO는 자신의 프로젝트에 들어온 지원서를 심사하고 팀을 확정합니다. Sub-PO는 제출된
지원서를 조회할 수 있습니다. 하지만 합격과 불합격은 결정할 수 없습니다. 운영진이라는 이유만으로
다른 프로젝트의 합격 여부를 결정할 수 없습니다.

### 5.4 스레드 OWNER와 ADMIN

방 안에서 적용되는 권한은 조직 역할과 별개입니다. OWNER와 ADMIN은 멤버를 초대하거나 강퇴할 수 있고
역할 변경은 OWNER만 할 수 있습니다.

### 5.5 프로젝트의 PM·디자인·개발

같은 기능을 서로 다른 관점에서 봅니다. PM은 목적·완료 조건·미결정 정책을, 디자인은 화면과
상태별 준비 사항을, 개발은 요구사항·시안·이슈·결정 근거를 먼저 확인합니다.
한 사람이 여러 역할을 맡을 수 있어 관점을 전환할 수 있습니다. 관점은 권한이 아닙니다.
1차는 개인 기록이며 다른 팀원에게 자동으로 공유되거나 할당되지 않습니다.

## 6. 제품 원칙

### 6.1 역할이 바뀌어도 탐색 구조는 바뀌지 않습니다

사이드바는 `나만의 공간 · 공지 · 활동 · 스레드 · 프로젝트 · 매칭 · 문의` 일곱 항목으로 고정합니다. 운영진 모드를
켜고 꺼도 항목을 추가하거나 제거하지 않습니다. 권한에 따라 각 화면 안에서 행동과 정보만
달라집니다.

### 6.2 권한은 추측하지 않습니다

매칭 프로젝트의 편집, 지원, 심사 권한은 서버가 전달한 결과를 기준으로 화면을 구성합니다. 권한이
없으면 행동을 숨기거나 비활성화하고 서버가 제공하는 사유가 있다면 설명에 활용합니다.

### 6.3 사용자가 확인한 자료로 작업을 준비합니다

1차 작업 설명은 선택한 발췌와 목적·완료 조건·결정 사항을 정해진 형식으로 구성합니다.
모델 없이 편집·복사할 수 있습니다. 링크만 있는 자료는 읽은 본문으로 취급하지 않습니다.
후속 AI 점검도 근거와 읽은 범위를 표시하고 사용자가 채택해야 기록에 반영합니다.

### 6.4 중요한 결정은 서버 응답 후 반영합니다

지원서 합격과 불합격, 문의 종료는 되돌리기 어렵거나 다른 사람에게 영향을 주는 행동입니다.
처리 중 상태를 보여 준 뒤 성공 응답을 확인하고 화면에 반영합니다.

### 6.5 macOS의 창 사용 방식을 따릅니다

기본 화면은 3컬럼 구조를 사용합니다. 스레드 방은 별도 창으로 열어 다른 작업과 나란히 볼 수
있고 여러 방을 동시에 띄울 수 있습니다.

## 7. 정보 구조

### 7.1 전역 구조

메인 창은 검은색 탐색 레일과 콘텐츠 패널로 구성합니다. 나만의 공간은 하나의 홈 패널을 쓰고 다른 메뉴는 필요한 목록·상세 컬럼을 둡니다.

| 영역 | 역할 |
|---|---|
| 사이드바 | 나만의 공간, 공지, 활동, 스레드, 프로젝트, 매칭, 문의 이동 |
| 목록 | 선택한 도메인의 항목 탐색과 필터링 |
| 상세 | 선택한 항목의 내용과 주요 행동 |

프로젝트는 목록에서 프로젝트와 기능을 탐색하고 상세에서 자료·확인 사항을 봅니다.
P4 자료 열람에서만 목록을 접을 수 있으며 돌아오면 선택과 위치를 복원합니다.

### 7.2 전역 흐름

```text
앱 실행(G0)
├─ 새 버전 있음 → 앱 내 업데이트(G1) → 설치·재실행 → G0 재검증
├─ 서버 점검 중 → 점검 화면(G2)
├─ 로그인 안 됨 → 로그인(G3) → 메인 창(G4)
└─ 로그인됨 → 메인 창(G4)
```

### 7.3 사이드바 구조

| 순서 | 항목 | 기본 대상 | 도입 단계 |
|---|---|---|---|
| 1 | 나만의 공간 | 전체 사용자 | 1 |
| 2 | 공지 | 전체 사용자 | 1 |
| 3 | 활동 | 전체 사용자 | 활동 PRD 참조 |
| 4 | 스레드 | 전체 사용자 | 2 |
| 5 | 프로젝트 | PM·디자인·개발 관점의 챌린저 | 2.5 |
| 6 | 매칭 | 전체 사용자 | 4 |
| 7 | 문의 | 전체 사용자 | 6 |

PM·디자인·개발 관점은 추천 정보만 바꾸며 외부 서비스나 팀 공유 권한을 부여하지 않습니다.

## 8. 권한 모델

화면은 네 가지 권한 축을 구분해야 합니다.

| 권한 축 | 적용 영역 | 화면에서 달라지는 것 |
|---|---|---|
| 조직 역할 + 운영진 모드 | 공지, 운영진 문의 | 작성 버튼, 읽음 통계, 운영진용 문의 표 |
| 스레드 방 역할 | 스레드 | 초대, 강퇴, 역할 변경 |
| 기수별 파트 | 매칭 | 프로젝트 생성, 지원 가능 여부 |
| 프로젝트별 권한 | 매칭 | 편집, 지원, 심사, 팀 확정, 통계 |

운영진 권한이 있는 사용자는 평소 챌린저 화면을 보다가 툴바의 `운영진 모드`를 켜면 운영 기능을
볼 수 있습니다. 매칭 권한은 운영진 모드와 별개이며 프로젝트별 권한을 우선합니다.

## 9. 핵심 사용자 여정

### 9.1 챌린저가 공지를 읽습니다

1. 앱에 로그인합니다.
2. 사이드바에서 공지를 선택합니다.
3. 목록에서 필독 공지와 일반 공지를 구분해 확인합니다.
4. 공지를 선택하면 본문, 대상, 작성자, 날짜, 이미지와 링크가 나타납니다.
5. 공지를 여는 순간 읽음 처리가 기록됩니다. 별도 확인 버튼은 없습니다.

### 9.2 운영진이 공지를 작성하고 읽음 현황을 봅니다

1. 운영진 모드를 켭니다.
2. 공지 화면에서 `작성`을 누르거나 `⌘N`을 사용합니다.
3. 제목, 본문, 대상, 공지 종류, 필독 여부와 알림 여부를 설정합니다.
4. 작성된 공지의 `읽음 통계` 탭으로 이동합니다.
5. 읽음/안 읽음 인원과 비율을 확인하고 범위별로 필터링합니다.

### 9.3 사용자가 스레드에서 대화합니다

1. 스레드 목록에서 고정된 방과 참여 중인 방을 확인합니다.
2. 방을 선택하면 상세 컬럼에 대화가 열립니다.
3. 목록에서 방을 더블클릭하면 같은 대화가 별도 창으로 열립니다.
4. 메시지를 보내면 `보내는 중`, `보냄`, `실패` 상태를 확인할 수 있습니다.
5. 실패 원인에 따라 `다시 보내기` 또는 `고쳐서 보내기`를 선택합니다.

### 9.4 프로젝트 기능을 준비하고 작업을 이어갑니다

1. P1에서 개인 프로젝트를 만들거나 기존 프로젝트를 선택합니다. 매칭 연결은 필요하지 않습니다.
2. P2에서 PM·디자인·개발 관점을 고르고 기능을 추가합니다.
3. P6에서 목적·완료 조건과 관련 Notion·Figma·GitHub 링크를 저장합니다.
4. P3에서 역할별 준비 항목을 점검하고 필요한 자료를 P4로 엽니다.
5. 모호한 내용을 확인 사항으로 기록합니다. 팀의 기존 소통 경로에서 답을 받은 뒤 원문 위치와 함께 남깁니다.
6. P5에서 필요한 발췌와 결정을 선택해 작업 설명을 편집·복사합니다.
7. 다시 앱을 열면 마지막 기능과 자료로 돌아갑니다.

PM은 결정할 정책, 디자인은 보완할 화면, 개발은 구현 기준을 먼저 확인합니다.
미결정이 해결됐다는 표시는 개인 기록이며 팀 전체의 합의나 구현 완료를 뜻하지 않습니다.

### 9.5 챌린저가 프로젝트에 지원합니다

1. 매칭 목록에서 차수와 프로젝트를 확인합니다.
2. 프로젝트를 선택합니다.
3. 지원 권한이 있으면 지원 폼이, 없으면 읽기 전용 상세가 나타납니다.
4. 지원서를 작성하고 제출합니다.
5. 이후 같은 영역에서 지원 결과를 확인합니다.

### 9.6 Project PO가 지원서를 심사합니다

1. 자신의 프로젝트를 선택합니다.
2. 심사 권한이 확인되면 지원서 표가 나타납니다.
3. 지원자와 지원 내용을 검토합니다.
4. 합격 또는 불합격을 선택합니다.
5. 파괴적 결정은 확인 Alert을 거치며 처리 중에는 중복 행동을 막습니다.

### 9.7 Sub-PO가 지원서를 조회합니다

1. 본인이 Sub-PO로 참여한 프로젝트를 선택합니다.
2. 조회 전용으로 지원자 목록과 지원 내용을 확인합니다.
3. 합격과 불합격 판정 버튼은 표시하지 않습니다.

### 9.8 챌린저가 문의하고 운영진이 답합니다

1. 챌린저가 문의 목록에서 `문의하기`를 누릅니다.
2. 카테고리, 내용, 첨부 파일을 입력합니다. 제목 필드는 없습니다.
3. 등록 후 문의 상세에서 메시지를 이어 갑니다.
4. 운영진은 권한 범위의 문의를 상태, 대상, 카테고리로 필터링합니다.
5. 운영진의 첫 답변 이후 상태가 `진행 중`으로 바뀝니다.
6. 운영진이 문의를 종료할 수 있고 새 메시지가 오면 다시 열립니다.

## 10. 화면별 요구사항

### 10.1 전역 화면

#### G1 앱 내 업데이트

- 자체 배포 사이트의 `appcast.xml`과 Sparkle 2로 새 버전을 확인하고 앱 안에서 설치합니다.
  별도 UMC 백엔드 API는 1차 범위에 필요하지 않습니다. 세부 정책은 설계 12장을 따릅니다.
- 앱 실행 시와 실행 중 24시간 간격으로 확인하며 메뉴바에서 수동 확인할 수 있습니다.
  호환되는 새 버전이 있으면 현재·새 버전과 변경 사항을 보여 줍니다.
- `업데이트`를 누르면 다운로드가 시작됩니다. 실제 진행률을 보여 주고 검증·설치 준비·설치
  상태를 구분합니다. 다운로드 페이지나 기본 브라우저로 이동하지 않습니다.
- 설치 준비가 끝나면 작성 중인 내용을 저장하거나 저장 여부를 확인한 뒤
  `설치하고 재시작`으로 진행합니다. 저장한 기록과 인증정보는 유지합니다.
- 다운로드 취소와 실패 시 재시도를 제공하며 검증에 실패한 파일은 설치하지 않습니다.
- `나중에`를 선택하면 현재 버전의 인증·점검 확인 흐름을 이어 갑니다. 같은 실행에서 같은
  버전의 안내를 반복하지 않습니다. 재실행 후에는 G0에서 인증정보와 점검 상태를 다시 확인합니다.
- 자동 확인 실패는 앱 진입을 막지 않습니다. 1차에는 강제 업데이트와 사용자 동의 없는
  자동 설치가 없습니다. 최초 설치만 자체 사이트에서 DMG를 받습니다.

#### G2 점검 화면

- 서버 점검 중에는 앱 전체를 덮습니다.
- 서버가 제공한 점검 제목, 설명, 시작과 종료 시간을 표시합니다.
- 점검 종료를 기다리는 별도 행동은 두지 않습니다.

#### G3 로그인

- 카카오, Apple, Google 로그인을 제공합니다.
- 카카오 로그인은 시스템 인증 창으로 이동할 수 있습니다.
- 세션이 만료되면 로그인 화면으로 돌아갑니다.

#### G4 메인 창

- 주요 창은 1440×960을 기준으로 디자인하고 검은색 56px 탐색 레일을 유지합니다. 점검·로그인 창은 1280×800을 유지합니다.
- 운영진 권한이 있는 계정에만 툴바의 운영진 모드 토글을 표시합니다.
- 메뉴바 단축키는 새 공지 `⌘N`, 새로고침 `⌘R`, 검색 `⌘F`, 프로젝트 보조 패널 `⌘⌥I`(P3·P4)입니다.
- 전역 오류 Alert은 현재 사용자가 보는 활성 창에 표시합니다.

#### H1~H8 나만의 공간과 게임

- 시작 검증을 마치면 H1에서 오늘 일정·공지·최근 작업을 간단히 확인합니다.
- 블록 점프·벽돌 깨기·타이밍 탑 쌓기 중 하나를 고르고 한 판 더 또는 게임 선택으로 돌아갑니다.
- 게임별 최고·누적 점수와 500/1,500/3,000점 기록 단계를 계정별 로컬 저장소에 기록합니다.
- 이미 열린 앱에서 인터넷 연결이 끊겨도 게임은 작동합니다. 최초 로그인과 시작 검증 정책은 유지합니다.
- 규칙·점수·상태·저장 실패·접근성 수용 기준은 [나만의 공간 · 홈과 세 가지 미니게임 PRD](나만의%20공간_홈과%20세%20가지%20미니게임_PRD.md)를 따릅니다.

### 10.2 공지

#### N1 공지 목록

- 현재 활동 기수를 기본으로 선택하되, 사용자가 다른 기수로 바꿀 수 있게 합니다.
- 기본 탭은 `챌린저 공지`입니다. 운영진 모드에서는 운영진 공지 3종 탭도 제공합니다.
- 선택한 기수와 공지 탭은 목록 상단에서 언제든 확인할 수 있어야 합니다.
- 필독 공지는 일반 공지와 구분해 목록 위쪽에서 알아볼 수 있게 합니다.
- 각 행에는 제목, 작성자, 날짜, 대상 요약을 보여 줍니다.
- 로딩, 비어 있음, 오류 상태는 현재 선택한 기수와 공지 탭 범위에 적용합니다.
- `작성` 행동은 운영진 모드에서만 제공합니다.

#### N2 공지 본문

- 필독 여부, 제목, 작성자, 날짜, 조회 수, 대상, 본문, 이미지, 링크를 표시합니다.
- 읽음 처리는 화면을 열 때 자동으로 이루어집니다.
- 운영진 모드에서는 `본문 | 읽음 통계` 탭을 표시합니다.

#### N3 읽음 통계

- 전체, 읽음, 안 읽음 인원과 읽음 비율을 한눈에 보여 줍니다.
- 읽음/안 읽음 전환과 범위 필터를 제공합니다.
- 이름, 파트, 학교, 지부를 표로 보여 주며 정렬과 다중 선택을 지원합니다.
- 다중 선택 후 수행할 행동은 아직 정하지 않았습니다.

#### N4 공지 작성

- 제목, 본문, 기수, 지부, 학교, 파트, 공지 종류의 입력을 지원해야 합니다.
- 필독과 알림 보내기 여부를 선택할 수 있어야 합니다. `알림 보내기`는 기존 서버와 iOS 알림
  채널을 이용해 수신 대상에게 공지 알림을 요청하는 작성 옵션입니다. macOS 앱이 종료된 상태에서
  알림을 받는 기능과는 별개입니다.
- 함께 선택할 수 없는 대상 조합은 비활성화하고 그 이유를 알 수 있게 표시합니다.
- 시트, 새 창, 상세 컬럼 중 어떤 방식으로 열지는 디자인 논의가 필요합니다.

### 10.3 스레드

#### T1 스레드 목록

- `고정됨`과 `참여 중` 구역을 나눕니다.
- 각 행에는 방 아이콘, 이름, 최근 메시지, 보낸 사람, 시각, 안 읽음 수를 보여 줍니다.
- 고정과 알림 끔 상태를 표시합니다.
- 검색과 새로고침을 제공합니다.
- 더블클릭하면 별도 창 T3이 열린다는 동작을 사용자가 알아볼 수 있어야 합니다.

#### T2 스레드 방

- 방 이름, 인원, 메시지 타임라인과 입력창을 제공합니다.
- 나가기와 신고는 모든 참여자에게 제공하며 초대와 강퇴는 OWNER·ADMIN에게 제공합니다.
- 역할 변경은 OWNER만 할 수 있습니다.
- 방 머리의 인원 수를 누르면 멤버 목록을 엽니다. 각 행에는 프로필, 이름과 현재 역할을 표시합니다.
- OWNER·ADMIN은 멤버 행에서 강퇴를 선택할 수 있으며 OWNER는 역할 변경도 선택할 수 있습니다.
- 강퇴는 대상과 결과를 다시 확인하는 Alert을 거칩니다. 역할 변경은 새 역할을 고른 뒤 확인합니다.
- 멤버 관리 요청 중에는 해당 행의 행동을 잠급니다. 실패하면 행 가까이에 오류와 다시 시도를 표시합니다.
- 메시지는 보내는 중, 재시도 가능 실패, 재시도 불가 실패, 쿨다운 상태를 구분합니다.
- 방에서 강퇴되면 해당 방을 닫고 목록을 갱신합니다.

#### T3 스레드 방 창

- T2와 같은 대화를 독립된 520×720 창으로 엽니다.
- 여러 스레드 창을 동시에 띄울 수 있습니다.
- 메인 창에서 다른 기능을 사용하는 동안에도 대화를 유지합니다.

### 10.4 프로젝트 작업 공간

UMC 로그인과 G2 전체 점검 정책을 따릅니다. 개인 로컬은 팀 공유 계약 없이 저장한다는 뜻이며
비로그인·점검 중 독립 진입까지 제공한다는 뜻은 아닙니다.

#### P1 프로젝트 목록/시작

- 개인 프로젝트 이름을 입력해 시작하거나 저장된 프로젝트를 선택합니다.
- 최초에는 프로젝트 생성 안내를 보여 줍니다. 팀원 설치·매칭 참여·외부 계정 연결을 강제하지 않습니다.
- 개인 로컬 기록임을 표시합니다. 프로젝트 이름만 같다고 팀 공간으로 합치지 않습니다.
- 프로젝트 삭제는 영향 범위를 확인한 뒤 로컬 하위 기록까지 삭제하며 외부 원문은 유지합니다.

#### P2 프로젝트 홈

- 현재 프로젝트의 기능 목록, 최근 작업, 미결정과 준비 항목을 보여 줍니다.
- PM·디자인·개발 관점을 전환할 수 있고 관점별 우선순위만 바뀝니다.
- PM은 목적·완료 조건·정책, 디자인은 정상·빈 상태·오류 화면, 개발은 이슈·시안·결정 근거를 점검합니다.
- 역할 체크리스트는 수정 가능한 수동 보조 항목입니다. 전체 기획이 완성됐다는 점수는 표시하지 않습니다.
- `기능 추가`는 P6을 엽니다. GitHub 이슈가 없어도 만들 수 있습니다.

#### P3 기능 상세

- 기능 이름·목적·완료 조건, 연결 자료, 준비 항목, 확인 사항을 표시합니다.
- 확인 사항은 질문·관련 자료·미결정/해결 상태·답·결정 원문 위치를 기록합니다.
- 해결 표시에는 답을 요구하고 원문 위치는 있으면 연결합니다. 다시 미결정으로 바꿀 수 있습니다.
- 개인 기록의 변경은 자동 공유되지 않습니다. 다른 사람에게 보냈다는 표시나 담당자 알림을 제공하지 않습니다.
- 자료 추가·편집은 P6, 자료 열람은 P4, 작업 설명은 P5로 이동합니다.
- 연결 자료를 삭제하면 관련 질문은 보존하고 연결 해제 상태를 표시합니다.

#### P4 자료 열람

- GitHub·Figma·Notion을 앱 안에서 열람합니다. 서비스별 실제 지원 범위는 선행 검증 후 확정합니다.
- 로그인 필요·권한 없음·로딩 실패를 구분하고 `원문 열기`로 동일 URL을 기본 브라우저에서 엽니다.
- 외부 브라우저 로그인 세션이 앱으로 자동 전달된다고 가정하지 않습니다.
- 목록을 접어 넓게 볼 수 있고 돌아오면 기능 선택과 위치를 복원합니다.
- 웹 로그인과 자료 연결은 원문 접근 권한을 부여하지 않습니다.
- 자동 본문 추출은 1차 필수가 아닙니다. 발췌는 사용자가 복사해 붙여넣고 출처와 저장 시각을 남깁니다.

#### P5 AI 작업 설명 초안

- 포함할 목적·완료 조건·자료 발췌·확정 결정·미결정을 사용자가 선택합니다.
- 선택 내용으로 모델 호출 없이 초안을 구성합니다. URL만 있는 자료는 참고 링크로 표시합니다.
- 각 발췌의 출처와 저장 시각을 표시하고 미결정을 확정 조건으로 바꾸지 않습니다.
- 생성된 초안을 직접 편집한 뒤 복사할 수 있습니다. 앱이 외부 AI로 자동 전송하지 않습니다.
- 미입력 항목은 그대로 표시하고 자료 본문을 확보하지 못한 경우 붙여넣기 입력을 제공합니다.
- 초안은 현재 앱 세션에서만 유지합니다. 앱 종료·로그아웃·세션 만료 시 제거되므로 필요한 내용은 복사합니다.
- 클립보드 내용은 로그아웃 후에도 남을 수 있음을 복사 도움말에 알립니다.

#### P6 기능·자료 연결 편집

- 기능 이름·목적·완료 조건과 자료 제목·종류·HTTPS URL·선택 발췌를 입력하는 시트입니다.
- 기능 이름은 필수입니다. 자료를 추가할 때 URL은 필수이며 서비스 호스트와 형식을 검사합니다.
- 검증 오류는 입력 가까이에 표시합니다. 저장 실패 시 입력과 기존 저장본을 보존합니다.
- 취소는 변경을 반영하지 않습니다. 원문 문서와 이슈는 수정하지 않습니다.

#### 1차와 후속의 구분

1차는 계정별 로컬 작업 공간입니다. 팀 공유·초대·담당자 전달·다중 기기 동기화·매칭 연결은
서버 계약 확인 후 추가합니다. AI 누락 후보 점검·변경 영향 안내·데모데이 점검·회고와 포트폴리오
초안도 후속입니다. 자동 점검은 읽은 자료의 범위와 근거를 표시하고 사용자가 채택해야 반영합니다.

### 10.5 매칭

#### M1 매칭 목록

- 차수와 프로젝트를 탐색할 수 있어야 합니다.
- Plan 파트 사용자에게 프로젝트 생성 행동을 제공합니다.
- 지부장 이상 권한에는 차수 개설 행동을 제공합니다.
- 차수와 프로젝트를 한 목록에 둘지 단계로 분리할지는 디자인 논의가 필요합니다.

#### M2-읽기 읽기 전용 상세

- 프로젝트 소개, PO, 학교, 모집 파트와 인원, 일정과 현재 단계를 표시합니다.
- 지원하거나 심사할 권한이 없을 때 기본으로 보여 줍니다.
- 지원한 사용자는 같은 상세 화면에서 지원 상태와 최종 결과를 확인합니다. 결과 공개 전에는 `대기`,
  공개 후에는 `합격` 또는 `불합격`을 표시합니다.

#### M2-지원 지원 폼

- 서버가 정의한 지원 질문에 답하고 제출할 수 있어야 합니다.
- 필수 여부와 입력 오류를 각 문항 가까이에서 알려 줍니다.
- 제출 전 실제 지원 프로젝트와 파트를 다시 확인할 수 있어야 합니다.
- 제출 중에는 입력과 제출 버튼을 잠급니다. 성공하면 M2-읽기의 지원 상태로 전환합니다.
- 제출에 실패하면 작성 내용을 유지하고 오류와 다시 시도를 제공합니다.

#### M2-심사 심사 화면

- 지원자 목록과 지원 내용을 함께 비교할 수 있게 합니다.
- 합격과 불합격을 처리할 수 있습니다.
- 불합격처럼 파괴적인 동작은 확인 Alert을 거칩니다.
- 처리 중에는 결과를 먼저 바꾸지 않고 로딩 상태를 표시합니다.
- Sub-PO에게는 `M2-심사 · 조회 전용` 변형을 제공합니다. 지원자 목록과 지원 내용은 같지만
  합격·불합격 버튼을 숨기고 조회 전용임을 표시합니다.

#### M3 프로젝트 생성과 공고·지원 폼 관리

- Plan 파트 사용자가 자신이 PO인 프로젝트를 만들 때 진입합니다.
- 프로젝트 생성은 `초안 생성 → 기본 정보 → 파트별 정원 → 제출 → 공개` 순서로 진행합니다.
- 기본 정보에는 프로젝트 이름, 설명, 외부 링크, 썸네일과 로고가 포함됩니다.
- 파트별 모집 정원을 설정하고 임시 저장과 제출을 구분합니다.
- Project PO는 공고 내용과 공통·파트별 지원 질문을 구성하고 공개할 수 있습니다.
- 필수 질문, 문항 유형, 선택지와 첨부 파일 여부를 설정할 수 있어야 합니다.
- 저장 또는 공개 처리 중에는 중복 행동을 막습니다. 실패하면 입력을 보존한 채 다시 시도할 수 있게 합니다.
- 제출한 프로젝트를 곧바로 공개할지, 공고와 지원 폼 검토를 거쳐 별도로 공개할지는 Figma에서
  두 흐름을 비교한 뒤 확정합니다.

#### M4 팀 확정과 결과 공개

- Project PO가 M2-심사에서 지원자 판정을 마친 뒤 진입합니다.
- 파트별 선발 인원과 합격자를 확인하고 누락이나 정원 초과를 알려 줍니다.
- 팀 확정 전에는 합격·불합격 판정을 바꿀 수 있습니다. 확정 후에는 결과를 지원자에게 공개합니다.
- 확정은 되돌리기 어려운 행동이므로 영향 범위와 공개 시점을 확인하는 Alert을 거칩니다.
- 처리 중에는 중복 확정을 막습니다. 실패하면 기존 판정과 선택 상태를 유지합니다.
- 결과 공개 후 지원자는 M2-읽기에서 자신의 결과를 확인합니다.

### 10.6 문의

#### Q1 문의 목록

- 챌린저는 본인이 작성한 문의만 봅니다.
- 목록이 비어 있으면 `문의하기`를 주요 행동으로 보여 줍니다.
- 제목 필드가 없으므로 문의 행은 `카테고리 · 상태 · 내용 앞부분 · 날짜`로 구성합니다.
- 내용 앞부분은 두 줄까지만 보여 주고 넘치는 내용은 말줄임표로 줄입니다.
- 운영진은 권한 범위의 문의를 표로 보고 상태, 대상, 카테고리로 필터링합니다.
- 운영진 표는 안 읽음, 상태, 카테고리, 내용 요약, 작성자와 날짜 순으로 보여 줍니다.
- 안 읽음 정보는 운영진 목록에만 표시합니다.

#### Q2 문의 상세

- 상태, 메시지 타임라인과 입력창을 제공합니다.
- 종료 행동은 처리 권한이 있는 운영진에게만 표시하고 챌린저에게는 표시하지 않습니다.
- 상태는 `접수`, `진행 중`, `종료` 세 가지입니다.
- 메시지는 수정하거나 삭제할 수 없습니다.
- 1차에는 수동 `재오픈` 버튼을 제공하지 않습니다. 종료된 문의에도 입력창을 유지하며 챌린저나
  운영진이 새 메시지를 보내면 자동으로 다시 엽니다.
- 전송에 실패해도 자동으로 다시 보내지 않으며 사용자가 재전송 여부를 결정합니다.

#### Q3 문의 등록

- 카테고리, 내용, 첨부 파일을 입력합니다.
- 제목 입력은 제공하지 않습니다.
- 카테고리가 문의 대상을 결정하므로 사용자가 대상을 직접 고르지 않습니다.
- 시트, 새 창, 상세 컬럼 중 어떤 방식으로 열지는 디자인 논의가 필요합니다.

## 11. 공통 상태와 피드백

### 11.1 목록과 상세

모든 주요 목록에서는 다음 상태를 고려합니다.

- 로딩
- 데이터 있음
- 비어 있음
- 불러오기 실패와 다시 시도
- 선택한 상세 항목 없음

### 11.2 입력과 처리

- 필수 입력 누락과 형식 오류는 해당 입력 가까이에 표시합니다.
- 제출 중에는 버튼을 중복으로 누를 수 없게 합니다.
- 되돌리기 어려운 행동은 확인 Alert을 사용합니다.
- 권한이 바뀌어 서버가 행동을 거절하면 화면 정보를 다시 불러오고 사용자에게 알립니다.

### 11.3 실시간 메시지

- `보내는 중`, `보냄`, `실패`를 메시지 가까이에 표시합니다.
- 재시도할 수 있는 실패에는 `다시 보내기`와 `고쳐서 보내기`를 제공합니다.
- 재시도할 수 없는 실패에는 `고쳐서 보내기`만 제공합니다.
- 전송 제한 중에는 남은 시간을 보여 주고 다시 보내기를 비활성화합니다.
- 성공 응답이 늦게 오면 실패 표시를 보냄 상태로 바꿉니다.

### 11.4 세션과 개인정보

- UMC 로그아웃이나 세션 만료 시 외부 웹 세션·선택 내용·임시 작업 설명을 제거합니다.
- 계정별 로컬 저장소를 닫아 잠그고 다른 계정에 이전 목록·자료·발췌가 보이지 않게 합니다.
- 사용자가 저장한 프로젝트 기록은 보존하고 같은 계정으로 다시 로그인하면 복원합니다.
- 영구 삭제는 별도 확인 행동입니다. 원문과 다른 계정의 데이터는 삭제하지 않습니다.

## 12. 디자인 요구사항

### 12.1 기본 방향

- macOS 26 네이티브 패턴을 우선합니다.
- `NavigationSplitView`, 시스템 툴바, 시트, Alert의 익숙한 동작을 유지합니다.
- 미드파이는 [UMC 디자인 시스템의 컬러](https://www.figma.com/design/U3pRZp6BjQBW5aMljCBwo9/?node-id=2117-4956)를 사용합니다. 주요 행동에는 Teal을, 바탕과 글자에는 Neutral 시맨틱 토큰을 적용합니다.
- 오류와 파괴적 행동에는 Error 시맨틱 토큰을 사용하고, 색만으로 상태를 구분하지 않습니다.
- 미드파이에서는 라이트·다크 모드에 최신 IA의 같은 화면·상태를 두고 확인합니다. UMC 컬러를 유지합니다. 다크 모드에는 기존 Grey·Teal 팔레트의 로컬 시맨틱 매핑을 사용합니다. 일러스트, Liquid Glass 재질과 모션은 하이파이 단계에서 정합니다.

### 12.2 접근성과 사용성

- 텍스트만으로 권한과 상태를 이해할 수 있어야 하며 색만으로 구분하지 않습니다.
- 클릭 영역과 키보드 포커스는 macOS 사용 방식에 맞아야 합니다.
- 표는 정렬 상태, 선택 상태와 빈 상태가 분명해야 합니다.
- 오류 메시지는 문제가 생긴 위치와 다음 행동을 함께 알려 줍니다.
- 운영진 모드로 전환한 뒤에도 현재 선택과 사용자의 위치를 가능한 한 유지합니다.

### 12.3 Figma 프레임 명명

프레임명은 `{IA ID} {이름} · {상태 또는 권한}` 형식을 사용합니다.

예시:

- `N2 공지 본문 · 운영진 모드`
- `T2 스레드 방 · MEMBER`
- `P4 자료 열람 · 권한 없음`
- `M2-심사 심사 화면 · 판정 중`

## 13. 성공 지표

### 13.1 제품 지표

- macOS 앱 주간 로그인 사용자 수
- 주요 기능별 주간 활성 사용자 수
- 공지 열람, 스레드 메시지 전송, 프로젝트 지원과 심사 완료 건수

macOS 로그인 사용자를 따로 집계하려면 서버의 클라이언트 유형에 `MACOS`가 추가되어야 합니다.
목표 수치는 운영과 협의해 정합니다.

### 13.2 프로젝트 지표

| 지표 | 정의 | 확인하려는 것 |
|---|---|---|
| 자료 탐색 시간 | 작업을 시작해 요구사항·시안·결정 근거를 찾기까지 걸린 시간 | 구현 준비가 빨라지는가 |
| 등록·갱신 부담 | 기능당 자료 등록 시간과 중복 입력 횟수 | 관리 비용이 가치보다 크지 않은가 |
| 작업 재개 | 같은 기능의 자료로 돌아와 작업을 이어간 사례 | 개인 한 명에게도 반복 사용 가치가 있는가 |
| 역할별 재사용 | PM·디자인·개발 관점별 재사용 사례 | 특정 파트에만 가치가 몰리는가 |
| 미결정 처리 | 팀 공유 후 질문부터 답 반영·작업 재개까지 걸린 시간 | 역할 간 인수인계가 개선되는가 |
| AI 유효 제안 | 후속 점검에서 사용자가 채택해 원문에 반영한 제안 비율 | AI가 실제 빈틈을 찾는가 |

진행 중인 3~5개 팀에서 2주간 검증하는 실험을 제안하며 규모는 모집 후 정합니다.
초기에는 동의를 받은 관찰·인터뷰로 기존 흐름과 비교합니다. 비공개 원문·URL은 분석 로그에
수집하지 않습니다. 목표 수치는 기준선 측정 후 정하고 후속 지표를 1차 출시 조건에 섞지 않습니다.

## 14. 단계별 출시 범위

| 단계 | 범위 | 완료 판단 |
|---|---|---|
| 1 | 로그인, 역할·파트 동기화, 나만의 공간·로컬 게임 3종, 공지 열람 | 홈에서 정보를 확인하고 게임별 기록을 저장하며 공지를 읽을 수 있음 |
| 2 | 스레드 목록, 방, 별도 창 | 스레드 방을 별도 창으로 열고 대화할 수 있음 |
| 2.5 | 프로젝트 개인 작업 공간 | 자료 연결·열람·수동 점검·작업 재개·설명 복사 가능 |
| 3 | 운영진 모드, 공지 작성, 읽음 통계 | macOS에서 작성한 공지가 iOS에도 표시됨 |
| 4 | 매칭 공고, 차수, 지원, 심사, 팀 확정 | 공고 등록부터 팀 확정까지 완료할 수 있음 |

팀 공유·담당자 전달·다중 기기 동기화는 후속 서버 계약 이후 진행합니다. 매칭 연결은
4단계 완료와 내 참여 프로젝트 조회·연결 권한 확인이 필요하며 개인 MVP의 선행 조건은 아닙니다.

## 15. 수용 기준

### 15.1 전역

- 로그인 여부와 서버 점검 여부에 맞춰 올바른 시작 화면이 나타납니다.
- 사이트에 게시한 새 버전을 앱 안에서 받아 설치하고 재실행하며 인증정보와 저장한 기록을 유지합니다.
- 업데이트 진행률·취소·실패·재시작 상태를 구분하고 검증 실패 시 설치를 막습니다.
- 역할에 관계없이 검은색 사이드바의 일곱 항목과 나만의 공간의 첫 위치가 유지됩니다.
- 세 게임의 시작·종료·클리어·재시작과 게임별 기록이 동작하며 같은 판을 중복 저장하지 않습니다.
- 운영진 권한이 있는 사용자만 운영진 모드를 사용할 수 있습니다.
- 세션이 만료되면 웹 세션·임시 초안을 지우고 저장소를 잠근 뒤 로그인 화면으로 이동합니다.

### 15.2 공지와 스레드

- 사용자가 기수와 공지 탭을 바꾸면 해당 범위의 목록과 빈 상태가 나타납니다.
- 챌린저가 공지를 열람하고 읽음 처리를 완료할 수 있습니다.
- 운영진은 공지를 작성하고 읽음 통계를 확인할 수 있습니다.
- 스레드 방을 메인 창과 별도 창에서 열 수 있습니다.
- OWNER·ADMIN은 멤버 목록에서 강퇴할 수 있고 OWNER는 역할을 변경할 수 있습니다.
- 네트워크가 끊겼다가 돌아와도 같은 메시지가 중복 등록되지 않습니다.

### 15.3 프로젝트 작업 공간

- 매칭이나 팀원 설치 없이 개인 프로젝트와 기능을 만들 수 있습니다.
- PM·디자인·개발 관점을 바꿔도 같은 기능과 기록이 유지되며 권한이 달라지지 않습니다.
- 원문 열람의 로그인·권한·오류 상태를 구분하고 같은 URL을 외부에서 열 수 있습니다.
- URL만 있는 자료를 작업 설명에서 읽은 본문으로 표시하지 않습니다.
- 선택한 발췌·출처·확정 결정·미결정을 보존해 모델 없이 편집·복사할 수 있습니다.
- 재실행 후 마지막 작업으로 돌아오며 저장 실패 시 기존 데이터와 입력이 보존됩니다.
- 로그아웃 후 다른 계정에 이전 자료가 보이지 않고 같은 계정 재로그인 시 저장 기록이 복원됩니다.
- 영구 삭제는 별도 확인을 거치고 외부 원문을 삭제하지 않습니다.

### 15.4 매칭과 문의

- 프로젝트 권한에 따라 읽기, 지원, 심사 화면 중 올바른 화면이 나타납니다.
- Project PO만 합격과 불합격을 결정할 수 있습니다.
- Sub-PO는 지원자 목록과 지원 내용을 조회할 수 있지만 합격과 불합격은 결정할 수 없습니다.
- Plan 파트 사용자가 프로젝트 초안을 만들고 PO가 공고와 지원 폼을 공개할 수 있습니다.
- Project PO가 파트별 판정을 검토해 팀을 확정하면 지원자가 결과를 확인할 수 있습니다.
- 챌린저는 본인의 문의만 보고 운영진은 권한 범위의 문의를 필터링할 수 있습니다.
- 문의 메시지는 수정하거나 삭제할 수 없고 종료된 문의는 새 메시지로 다시 열립니다.

## 16. 디자인 논의가 필요한 항목

아래 항목은 기능 요구사항은 있으나 위치나 표현 방식이 확정되지 않았습니다. Figma에서 대안을
나란히 비교해 결정해야 합니다.

| 항목 | 결정할 내용 | 권장 출발점 |
|---|---|---|
| 계정 · 설정 · 로그아웃 | 메인 창 어디에 둘지 | 사이드바 하단 계정 메뉴 |
| 공지 작성 | 시트, 새 창, 상세 컬럼 중 선택 | 독립 작업을 유지하는 시트 |
| 공지 범위 선택 | 기수와 운영진 공지 탭을 툴바·목록 중 어디에 둘지 | 목록 상단 고정 조건 줄 |
| 문의 등록 | 시트, 새 창, 상세 컬럼 중 선택 | 짧은 폼이므로 시트 |
| 차수 개설 | 시트, 새 창, 상세 컬럼 중 선택 | 필드 수 확인 후 시트 또는 새 창 |
| 매칭 목록 | 차수와 프로젝트를 한 목록에 둘지 단계로 분리할지 | 두 안을 같은 데이터로 비교 |
| 프로젝트 제출과 공고 공개 | 제출 즉시 공개할지, 공고·지원 폼 검토 뒤 공개할지 | M3에서 두 흐름 비교 |
| 팀 확정과 결과 공개 | M2-심사 안에서 이어갈지 M4로 분리할지 | 별도 단계 M4부터 검증 |
| 공지 통계 다중 선택 | 선택 후 어떤 행동을 제공할지 | 운영 요구 확인 전 행동 없음 |
| 스레드 멤버 관리 | 멤버 목록을 시트·Popover·상세 교체 중 무엇으로 열지 | 인원 수를 진입점으로 한 시트 |
| 프로젝트 보조 패널 | 자료·확인 사항·작업 설명의 전환 방식 | P3 상세와 P5 편집 패널 비교 |
| 점검 화면 | 수동 새로고침이나 재시도 버튼 필요 여부 | 서버 동작 확인 전 버튼 없음 |

## 17. 선행 조건과 리스크

### 17.1 서버 의존성

- macOS 로그인과 플랫폼별 지표를 위해 `ClientType.MACOS`가 필요합니다.
- 문의 채널은 서버에 문의 도메인이 구현된 뒤 착수할 수 있습니다.
- 문의 메시지 중복을 막으려면 `clientMessageId` 지원이 필요합니다.

### 17.2 프로젝트 선행 검증

- 서비스별 웹 로그인·비공개 자료 접근·세션 유지·원문 열기를 실제 macOS 앱에서 확인합니다.
- 로컬 저장 실패·재실행 복원·계정 전환·영구 삭제 범위를 검증합니다.
- 저장한 발췌가 최신 원문과 다를 수 있어 출처와 저장 시각을 표시합니다.
- 팀 공유와 매칭 연결에는 내 참여 프로젝트 조회·멤버십·접근 권한 계약이 필요합니다.
- 현재 서버의 프로젝트 조회·멤버 관리 기능만으로 작업 공간 공유가 가능하다고 가정하지 않습니다.

### 17.3 도입과 운영 리스크

- 팀 전원의 설치를 전제로 하지 않습니다. 개인이 자료를 모으고 작업을 이어가는 가치를 먼저 검증합니다.
- PM 한 명에게 자료 등록과 갱신이 몰리면 입력 구조를 조정합니다.
- 개인 기록은 팀 합의와 구분하며 원문을 통해 다른 팀원과 작업을 이어갈 수 있어야 합니다.
- AI 점검은 잘못된 질문을 제안하거나 누락을 놓칠 수 있어 근거 확인과 채택 단계를 둡니다.

### 17.4 기기 제약

- 앱은 macOS 26 이상을 지원합니다.
- 개인 작업 공간과 작업 설명 편집·복사는 Apple Intelligence 지원 여부와 관계없이 동작해야 합니다.
- 출시 전 팀별 맥 사용 인원과 macOS 26 지원 비율을 확인합니다.

## 18. Figma 제작 순서

1. 전역 구조와 G 프레임을 만듭니다.
2. 공통 컴포넌트와 로딩, 빈 상태, 오류, 처리 중 상태를 정의합니다.
3. N 공지와 T 스레드로 기본 3컬럼 패턴을 검증합니다.
4. P1~P6 프로젝트에서 개인 시작·역할 전환·자료 열람·작업 설명 복사·저장 실패를 검증합니다.
5. M 매칭의 두 가지 목록 구조와 `생성 → 공고·폼 공개 → 심사 → 팀 확정 → 결과` 흐름을 검증합니다.
6. Q 문의의 챌린저와 운영진 화면 차이를 검증합니다.
7. 16장의 미결정 항목을 별도 페이지에 모아 대안을 비교합니다.
8. 결정된 내용을 이 PRD와 설계 문서에 반영한 뒤 하이파이를 진행합니다.
