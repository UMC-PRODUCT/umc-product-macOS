## 1. 무엇을 만드나

UMC 구성원 전체가 쓰는 데스크톱 앱입니다. 운영진 전용 도구가 아닙니다.

챌린저는 공지를 읽고 스레드에서 대화하고 프로젝트에 지원합니다. 운영진은 거기에 더해
공지를 쓰고 읽음 현황을 보고 지원서를 심사합니다. 같은 앱에서 역할에 따라 보이는 게 달라지는 구조로,
iOS 앱이 이미 이렇게 동작합니다.

데스크톱을 따로 만드는 이유는 폰에서 하기 나쁜 일들이 있기 때문입니다. 공지를 길게 쓰고
읽음 통계를 표로 훑고 지원서 수십 장을 넘겨 가며 심사하는 일은 운영진 쪽에 몰려 있습니다.
챌린저 쪽에도 있습니다. 노트북으로 과제하다가 스레드를 확인하려고 폰을 집어드는 일이 없어집니다.

필수 기능은 셋입니다.

- **공지** — iOS 앱의 Notice 피처와 같은 도메인
- **스레드** — iOS 앱의 Community 피처와 같은 도메인
- **프로젝트 매칭** — 웹 v2 레포에 있는 기능. iOS 앱에는 없습니다

여기에 문의 채널을 하나 더 붙입니다. 서버가 아직 안 만들어 순서는 뒤인데, 5장에 따로 적었습니다.

프로젝트 작업 공간을 추가합니다. PM·디자인·개발자가 기능별로 Notion 요구사항,
Figma 화면, GitHub 이슈를 연결하고 구현 전 준비 사항과 진행 중 미결정을 확인합니다.
개인 한 명도 자료를 모으고 마지막 작업을 이어갈 수 있어야 합니다. 상세는 6장입니다.

성공은 주간 로그인 수와 함께 자료 탐색 시간, 작업 재개, 등록 부담으로 확인합니다.
플랫폼별 집계에는 `ClientType.MACOS` 지원 여부를 서버와 확인해야 합니다(14장).
팀 공유 단계에서는 미결정이 해결된 뒤 작업을 이어가는 시간도 측정합니다.

## 2. 역할과 권한

권한 축이 셋입니다. 공지는 조직 역할을 타고 스레드는 방 단위 관계를 타고
매칭은 파트와 프로젝트 단위 관계를 같이 봅니다.

**조직 역할 — `ManagementTeam`.** 서버 `roleType`과 1:1로 대응하는 11단계 enum입니다.
superAdmin(110)부터 challenger(0)까지 레벨이 매겨져 있고 권한 판정은 레벨 비교로 합니다.

```swift
public var canAccessAdminMode: Bool { level >= Self.schoolEtcAdmin.level }
public var canAccessStaffNotice: Bool { level >= Self.schoolPartLeader.level }
```

`UserSessionManager`는 `@Observable` 객체로 현재 역할과 보유 역할 목록,
운영진 모드 활성화 여부를 들고 있습니다. 운영진 권한이 있는 사람도 평소에는 챌린저 화면을 보다가
모드를 켜면 운영 기능이 나타납니다. macOS에서도 같은 방식으로 가되 토글은 툴바에 둡니다.

**파트 — 기수마다 다릅니다.** 서버 `SubjectAttributes`는 회원 하나에 `GisuChallengerInfo`
리스트를 물고 있고 `part`는 그 안에 들어 있습니다. 9기에 디자인이었다가 10기에 기획일 수 있다는
뜻이라 파트를 전역 스칼라로 잡으면 안 됩니다. 값은 `ChallengerPart` 8종
(`PLAN`·`DESIGN`·`WEB`·`ANDROID`·`IOS`·`NODEJS`·`SPRINGBOOT`·`ADMIN`)입니다.

파트가 여는 문은 둘뿐입니다. Plan 파트는 본인이 PO인 프로젝트를 만들 수 있고 나머지 파트는
지원 폼이 허용한 파트에 들어 있으면 지원할 수 있습니다. 나머지 매칭 운영 기능은 파트가 아니라
다른 축이 정합니다.

**프로젝트 단위 관계.** 지원서 합불은 그 프로젝트의 `Project PO`만 결정합니다. 서버 권한 정책
문서에 "운영진이 별도로 합불을 결정할 수 없습니다"라고 못이 박혀 있습니다. Sub-PO는 제출된
지원서 조회까지고 지원자는 본인 지원서만 봅니다. 반대로 매칭 차수 개설·수정·삭제와 자동 선발
실행은 지부장 또는 중앙운영사무국 총괄단 이상이라 여기서는 `ManagementTeam` 레벨을 봅니다.

즉 매칭 화면을 파트 하나로 분기할 수 없습니다. 서버도 이걸 예상하고 화면 분기 전용 API를
따로 열어 뒀습니다. 컨트롤러 설명에 "프로젝트 화면 분기용 capability를 조회합니다"라고
적혀 있습니다.

```
GET /api/v1/projects/permissions?ids=1,2,3
```

프로젝트 id를 최대 100개까지 넘기면 프로젝트마다 capability 묶음이 돌아옵니다.
항목 하나하나가 boolean이 아니라 `{ allowed, reasonCode, reason }` 객체입니다
(`ProjectPermissionCapabilityInfo`). `canEditInfo`·`canDelete`,
`applicationForm.canCreate`·`canPublish`, `application.canCreate`·`canDecide`,
`member`·`statistics`가 모두 같은 모양입니다. 권한이 없어도 에러가 아니라
`allowed: false`와 사유가 옵니다. 없는 id는 `exists: false`로 옵니다.
버튼 노출은 `allowed`만 보고 정합니다. 클라이언트에서 권한 규칙을 다시 구현하지 않습니다.

부르는 시점도 정해집니다. 프로젝트 목록은 한 페이지 20건이 기본입니다
(`ProjectQueryController`의 `@PageableDefault(size = 20)`). 페이지를 받을 때마다
그 페이지의 id로 한 번 부르면 100개 한도에 걸리지 않습니다.

방 단위 권한은 원칙은 같지만 물어볼 API가 다릅니다. 인가 모듈의 리소스 권한 API에는
스레드가 없습니다(`ResourceType`). 대신 스레드 상세(`GET /api/v1/community/threads/{threadId}`)가
`isJoined`와 `myRole`(`OWNER`·`ADMIN`·`MEMBER`)을 줍니다. 초대·강퇴는 `OWNER`와 `ADMIN`,
역할 변경은 `OWNER`만 합니다(`CommunityThreadMembershipCommandService`).
`ManagementTeam`과는 무관합니다. 버튼은 `myRole`로 가르고 최종 판정은 서버 거절에 맡깁니다.

## 3. 화면 구조

`NavigationSplitView` 3컬럼입니다.

```
┌─────────┬──────────────┬────────────────────┐
│ 사이드바 │   목록        │       상세          │
│         │              │                    │
│ 공지     │ 공지 목록     │ 공지 본문 / 읽음 통계 │
│ 스레드   │ 스레드 목록    │ 스레드 방           │
│ 프로젝트 │ 기능 목록      │ 자료 / 확인 사항     │
│ 매칭     │ 매칭 목록      │ 지원서 / 지원 폼     │
└─────────┴──────────────┴────────────────────┘
```

사이드바는 공지 · 활동 · 스레드 · 프로젝트 · 매칭 · 문의 순서로 고정합니다.
프로젝트는 작업 공간이고 매칭은 모집·지원·심사 공간입니다.
달라지는 건 각 항목 안쪽입니다.
챌린저에게는 공지 목록에 작성 버튼이 없습니다. 운영진 모드를 켜면 작성 버튼과 읽음 통계 탭이 붙습니다.
매칭 상세는 모드와 상관없이 서버가 준 capability로 갈립니다.
`application.canDecide.allowed`면 심사 화면, `application.canCreate.allowed`면 지원 폼,
둘 다 아니면 읽기 전용 상세입니다.

사이드바를 역할에 따라 늘렸다 줄였다 하지 않는 이유는, 운영진 모드를 껐다 켤 때마다
사이드바가 흔들리면 어디에 있었는지 잃어버리기 때문입니다.

스레드 방은 목록에서 더블클릭하면 별도 창으로 뜹니다. 스레드를 보면서 다른 일을 하는 상황이
흔한데 3컬럼 하나로는 그게 안 됩니다. 창을 떼면 됩니다.

읽음 통계와 지원서 목록은 `Table`을 씁니다. 정렬과 다중 선택이 공짜로 따라옵니다.
메뉴바에는 새 공지(⌘N), 새로고침(⌘R), 검색(⌘F)을 겁니다. 새 공지는 권한이 없으면 비활성입니다.

## 4. 기능 범위

| 도메인 | 챌린저 기본 | 추가로 열리는 것 | 무엇으로 판정하나 |
|---|---|---|---|
| 공지 | 목록·상세 열람, 읽음 처리 | 작성, 대상 지정, 읽음 통계 | `ManagementTeam` + 운영진 모드 |
| 스레드 | 참여, 대화, 나가기, 신고 | 초대·강퇴(`OWNER`·`ADMIN`), 역할 변경(`OWNER`) | 스레드 상세의 `myRole` |
| 매칭 | 차수 확인, 지원, 결과 확인 | 프로젝트 생성(Plan 파트), 폼 관리·심사·팀 확정(PO), 차수 개설(지부장 이상) | 파트 + 프로젝트 capability + `ManagementTeam` |
| 프로젝트 | 기능별 자료 연결·열람, 확인 사항, 작업 설명 복사 | PM·디자인·개발 관점 전환 | 개인 계정별 저장. 외부 원문 권한과 팀 공유 권한은 별도 |

1차에서 빼는 것은 이렇습니다.

- **리크루팅 도메인** — 웹에 코드는 있지만 배포되지 않았습니다. 서버 상태가 확정되면 봅니다
- **자동 생성·분석** — 공지 AI 초안, 스레드 자동 분류, 프로젝트 AI 누락 점검은 후속입니다.
  1차 작업 설명은 선택 자료를 정해진 형식으로 구성하며 모델 없이 편집·복사할 수 있습니다
- **원격 푸시** — 앱이 꺼져 있을 때의 알림입니다. 1차는 앱이 켜져 있는 동안의 실시간만 봅니다.
  공지 도달에 걸리는 문제라 운영이 확정합니다(14장)
- **macOS 26 미만** — 패키지 최소 버전(7장)과 SwiftUI `WebView`가 macOS 26입니다.
  인텔 맥은 2019~2020년 일부 모델만 올라갑니다(Apple 지원 문서 122867)

매칭 공고 등록은 4단계에 넣습니다. 공고를 올리는 사람과 지원서를 심사하는 사람이 같은 PO라
심사만 넣으면 그 사람이 맥과 웹을 오가게 됩니다. 차수 개설도 같이 넣되 순위는 뒤입니다.
쓰는 사람이 지부장 이상으로 좁고 한 기수에 몇 번 없는 작업입니다. 대가는 폼 길이입니다.
필드가 많고 검증 규칙이 붙어서 4단계가 눈에 띄게 무거워지는데, 이건 감수합니다.

## 5. 문의 채널

챌린저가 운영진에게 물어볼 공식 창구가 앱 안에 없습니다. 지금은 카카오톡이나 디스코드로 흘러갑니다.
누가 답했고 무엇이 처리됐는지가 남지 않습니다. 맥 앱에서 문의를 열고 답을 받는 데까지 넣습니다.

다만 순서가 있습니다. 서버에 문의 도메인이 아직 없습니다.

### 서버 현황

`docs/adr/011-inquiry-domain-with-websocket-stomp.md`가 문의 도메인을 통째로 설계해 뒀지만
Status가 `Proposed`입니다. 코드는 없습니다. 서버 소스에서 `Inquiry`를 검색하면 ADR 문서와
chat·websocket 인프라 파일만 걸리고 30개 도메인 패키지 어디에도 `inquiry`가 없습니다.

대신 그 아래 깔릴 것은 이미 서 있습니다. ADR-026이 채팅 엔진과 소비 도메인을 분리해 뒀고
Status가 `Accepted`입니다. 채팅 엔진(`chat`)은 인바운드 웹 어댑터가 없습니다. 방을 소유하고
접근 규칙을 정하는 쪽은 소비 도메인입니다. 커뮤니티 스레드가 이 구조로 이미 돌고 있습니다
(`community/adapter/in/` 아래 web·websocket·event가 다 있습니다). 문의도 같은 자리에 끼웁니다.

채팅 기반은 갖췄고 문의 도메인만 없는 상태입니다.

### 확정된 계약 (ADR-011 기준)

ADR이 `Proposed`라 바뀔 수 있습니다. 그래도 화면을 그려 두기에는 충분합니다.

기획이 ADR에 고쳐 달라고 요청한 것도 있습니다(`docs/server/문의_문의 채널_서버명세.md`).
화면에 걸리는 것은 넷입니다. 대상은 카테고리가 정하고 클라이언트는 보내지 않습니다.
등록 폼에 제목이 없습니다. 카테고리 필터는 `categoryId`입니다. `UMC_PRODUCT`는
프로덕트팀이 받습니다. 아래 표는 이 요청이 받아들여진다는 전제로 적었습니다.

REST 1차 범위:

| Method | Path | 쓰임 |
|---|---|---|
| GET | `/api/v1/inquiry-categories` | 등록 폼의 활성 카테고리 목록. `sort_order` 순으로 조회 |
| POST | `/api/v1/inquiries` | 문의 등록. `categoryId`·`content`·`fileIds[]` |
| GET | `/api/v1/inquiries` | 목록. `status`·`target`·`categoryId`·`unreadOnly` 필터 |
| GET | `/api/v1/inquiries/{id}` | 상세. 운영진에게는 작성자 정보가 같이 옴 |
| GET | `/api/v1/inquiries/{id}/messages` | 메시지 목록, `createdAt` 오름차순 |
| POST | `/api/v1/inquiries/{id}/messages/read` | 미읽음 일괄 처리 |
| POST | `/api/v1/inquiries/{id}/close` | 종료 |
| POST | `/api/v1/inquiries/{id}/reopen` | 재오픈 |

실시간은 둘뿐입니다. `/app/inquiry/{inquiryId}/message`로 보내고
`/topic/inquiry/{inquiryId}`를 구독합니다. 페이로드는 `{ content, fileIds[] }`입니다.

역할도 둘입니다. 문의를 연 사람이 `INQUIRER`, 대상 운영진이 `RESPONDER`입니다. 본인이 쓴 문의를
본인이 처리할 권한까지 가진 경우에는 `INQUIRER`가 이깁니다. 대상은
`CENTRAL`·`CHAPTER`·`SCHOOL`·`UMC_PRODUCT` 넷이고 카테고리가 정합니다.
ADR은 `UMC_PRODUCT`를 중앙운영사무국 전체로 임시 매핑했지만 서버 명세는
프로덕트팀으로 보내고 그 판별 수단을 선행 과제로 뒀습니다.

상태는 셋입니다.

```
RECEIVED ──운영진 첫 메시지──▶ IN_PROGRESS ──운영진 종료──▶ CLOSED
                                                        │
IN_PROGRESS ◀──작성자나 운영진의 새 메시지──────────────────┘
```

화면에 바로 걸리는 제약이 둘 있습니다.

- **메시지 수정·삭제가 없습니다.** 분쟁 처리 기록으로 쓰려고 서버가 막아 뒀습니다. 잘못 보낸 건
  다음 메시지로 정정합니다. 컨텍스트 메뉴에 편집·삭제를 만들지 않습니다
- **미읽음은 운영진 쪽만 1차 범위입니다.** 문의자 화면에는 안 읽음 배지가 없습니다

### 맥에서의 모양

3컬럼에 그대로 들어갑니다. 사이드바 여섯 번째 항목이고 목록은 필터가 붙은 문의 목록,
상세는 메시지 타임라인과 입력창입니다.

역할에 따라 목록의 성격이 갈립니다. 챌린저에게는 본인 문의만 오니 대개 한두 건이고
비어 있으면 문의하기 버튼만 남습니다. 운영진에게는 권한 범위의 문의가 전부 쌓이니
상태·대상·카테고리로 거르는 `Table`이 필요합니다. 스레드보다 공지 읽음 통계에 가까운 화면입니다.

STOMP 커넥션은 9장의 것을 같이 씁니다. 다만 구독 방식이 다릅니다. 스레드는 사용자 큐
하나로 모든 방의 이벤트를 받습니다. 문의는 ADR대로면 문의마다 `/topic/inquiry/{inquiryId}`를
따로 구독합니다. 문의 상세를 열 때 구독하고 닫을 때 끊습니다. 잠자기에서 깨어난 뒤
`GET /api/v1/inquiries/{id}/messages`로 채워 넣는 것은 스레드와 같습니다.

낙관적 업데이트는 메시지 전송에만 씁니다. 그런데 ADR의 페이로드 `{ content, fileIds[] }`에는
멱등 키가 없습니다. 응답을 못 받은 메시지를 다시 보내면 같은 글이 두 번 남을 수 있고
문의 메시지는 지울 수도 없습니다. 스레드처럼 `clientMessageId`를 받도록 서버에
요청합니다(14장). 받아들여지기 전까지는 자동 재전송을 하지 않습니다. 실패 표시만 하고
다시 보낼지는 사용자가 정합니다. 종료는 9장의 심사 판정과 같은 이유로 서버 응답을 보고 반영합니다.

### 언제 붙이나

로드맵 6단계입니다. 서버 진행에 따라 두 토막으로 나눌 수 있습니다. ADR-011의 Phase 4
(메시지 REST)까지 끝나면 실시간 없이도 화면을 열 수 있습니다. 열 때와 ⌘R에 새로고침하는
정도면 됩니다. 문의는 스레드만큼 즉시성이 필요한 대화가 아닙니다. Phase 6(WebSocket)이
끝나면 구독을 붙입니다.

지금 당장 할 일은 클라이언트 쪽에 있습니다. 2단계에서 스레드 실시간을 만들 때
구독을 '앱 시작 때 하나'로 굳히지 않는 것입니다. 구독을 열고 닫는 자리와 재전송 규칙(9장)을
스레드 전용 타입에 묶지 않으면 서버가 준비됐을 때 화면만 그리면 됩니다.

## 6. 프로젝트 작업 공간

### 목적과 범위

팀이 확정된 뒤에도 챌린저가 매일 사용할 공간입니다. 구현할 기능의 요구사항·디자인·개발 작업을
한곳에서 찾고 정해지지 않은 내용을 기록하며 작업을 이어갑니다. 동아리 스터디나 단기 프로젝트도
개인 작업 공간으로 등록할 수 있습니다. UMC 매칭 참여는 1차의 선행 조건이 아닙니다.

UMC 로그인과 전체 점검 정책은 유지합니다. 개인 로컬은 팀 공유 계약 없이 저장한다는 뜻이며
비로그인·점검 중 독립 진입을 뜻하지 않습니다.

개인 로컬 MVP를 먼저 제공합니다. 팀원 초대·공유·담당자에게 전달·다중 기기 동기화는 서버 계약을
확인한 후 추가합니다. 개인 기록을 팀 공용 기록처럼 표시하거나 자동 공개하지 않습니다.
매칭 프로젝트 연결은 4단계 이후이며 연결만으로 자료 공유 권한이 생기지 않습니다.

### 역할별 사용 목적

| 관점 | 구현 전 | 구현 중 |
|---|---|---|
| PM | 목적·완료 조건·미결정 정책 확인 | 결정할 질문과 변경 근거 정리 |
| 디자인 | 정상·빈 상태·오류 상태와 화면 연결 확인 | 보완할 화면과 수정 이유 정리 |
| 개발 | 이슈·요구사항·시안·확정 결정 확인 | 마지막 자료로 복귀하고 AI 작업 설명 구성 |

관점은 추천 항목과 정렬을 바꾸는 개인 설정입니다. 복수 역할을 오갈 수 있고 권한을 부여하지 않습니다.
체크리스트는 수동 점검 보조이며 완료 표시가 설계의 완전성이나 개발 완료를 뜻하지 않습니다.

### 정보 단위와 원문

| 단위 | 1차에 저장할 내용 |
|---|---|
| 개인 프로젝트 | 로컬 식별자, 이름, 선택한 관점, 최근 기능 |
| 기능 | 프로젝트 식별자, 이름, 목적, 완료 조건, 연결 자료, 준비 체크리스트 |
| 연결 자료 | 제목, 서비스 종류, URL, 사용자가 붙여넣은 발췌, 발췌를 저장한 시각 |
| 확인 사항 | 질문, 관련 자료, 미결정/해결 상태, 사용자가 기록한 답과 원문 위치 |
| 작업 설명 | 선택한 입력과 편집 중인 초안. 현재 앱 세션에서만 유지하며 필요하면 복사 |

로컬 식별자는 서버 프로젝트 ID와 구분합니다. GitHub 이슈가 없어도 기능을 등록합니다.
원문은 각 서비스에서 관리하며 앱에서 요구사항 문서나 이슈 보드를 다시 만들지 않습니다.
저장한 발췌는 특정 시점의 사본입니다. 저장 시각을 표시하고 최신 원문과 같다고 보장하지 않습니다.
1차에는 이슈 상태를 자동 동기화하지 않고 원문 열람으로 확인합니다.

### 화면과 흐름

사이드바는 유지하고 `목록 | 상세`에서 프로젝트와 기능을 탐색합니다. 자료를 넓게 볼 때만
목록을 접습니다. 이전 선택으로 돌아오면 목록과 기능 위치를 복원합니다.

| ID | 화면 | 역할 |
|---|---|---|
| P1 | 프로젝트 목록/시작 | 개인 프로젝트 만들기, 기존 프로젝트 선택 |
| P2 | 프로젝트 홈 | 기능 목록, 관점 전환, 최근 작업과 미결정 확인 |
| P3 | 기능 상세 | 원문 연결, 준비 체크리스트, 확인 사항과 결정 근거 |
| P4 | 자료 열람 | GitHub·Figma·Notion 웹 콘텐츠, 원문 열기, 로그인·권한 안내 |
| P5 | AI 작업 설명 초안 | 선택 자료로 작업 설명 구성, 검토·편집·복사 |
| P6 | 기능·자료 연결 편집 | 기능 이름·목적·완료 조건과 자료 URL 입력 시트 |

`P1 → P2 → P3 → P4 → P3`으로 자료를 확인하고 `P3 → P5 → 복사`로 작업을 이어갑니다.
P1에서 이름을 입력해 개인 프로젝트를 만들며 P2의 기능 추가와 P3의 편집에서 P6을 엽니다.
P6 저장이 성공해야 시트를 닫고 실패하면 입력과 기존 데이터를 보존합니다.

예를 들어 검색 기능에 요구사항과 Figma 화면을 연결합니다. 개발 관점에서 결과가 없을 때의
동작을 확인 사항으로 남깁니다. 팀의 기존 소통 경로에서 답을 확인하고 원문에 반영된 위치를
기록한 뒤 해결로 바꿉니다. 1차 앱은 이 질문을 다른 사람에게 자동 전송하지 않습니다.

### 외부 자료 열람

서비스별 웹 로그인·비공개 문서·재실행 세션·링크 이동을 먼저 검증합니다. 공식 임베드가 있는
서비스는 이를 후보로 삼되 실제 macOS 웹뷰에서 확인한 범위만 지원 목록에 적습니다.
로그인 실패, 접근 권한 없음, 로딩 실패를 구분하고 원래 URL을 유지한 채 `원문 열기`를 제공합니다.
인증을 외부 브라우저에서 마쳐도 웹뷰에 세션이 자동 전달된다고 가정하지 않습니다.

등록 URL은 HTTPS와 지원 서비스 호스트를 검증합니다. 사용자 정보가 포함된 URL과 실행 스킴은
거절합니다. 외부 호스트 이동은 기본 브라우저로 넘기고 서비스 인증 도메인은 검증 후 허용합니다.
원문 접근 권한은 외부 서비스가 판정합니다. UMC 역할이나 링크 소지만으로 접근을 허용하지 않습니다.

링크를 저장했다고 본문·Figma 화면·코드를 읽은 것으로 취급하지 않습니다. 1차는 사용자가 직접
붙여넣은 발췌와 작성한 목적·완료 조건·결정만 작업 설명 입력으로 씁니다. URL은 참고 링크로 남깁니다.
Figma 선택 텍스트나 전체 코드 자동 추출은 요구하지 않습니다.

### AI 작업 설명과 후속 AI 점검

P5는 1차에 모델 호출 없이 정해진 형식으로 초안을 만듭니다. 사용자가 입력 자료를 골라 목적,
요구사항 발췌, 디자인 링크, 완료 조건, 확정 결정, 미결정을 순서대로 구성합니다.
자료별 출처와 저장 시각을 포함하고 빈 항목은 미입력으로 표시합니다. 미결정을 확정 요구로 바꾸지 않습니다.
초안을 직접 편집하고 복사할 수 있으며 앱이 외부 AI 도구로 자동 전송하지 않습니다.
클립보드에 복사된 내용은 앱 로그아웃 후에도 남을 수 있음을 복사 도움말에 안내합니다.

후속 AI 점검은 사용자가 선택한 자료에서 빠진 상태나 서로 다른 설명을 확인 질문으로 제안합니다.
읽은 범위와 근거를 표시하고 `연결된 자료에서 찾지 못함`과 `실제로 없음`을 구분합니다.
사용자가 채택해야 확인 사항에 저장하며 원문을 자동 수정하지 않습니다. 모델·실행 위치·비용·입력 한도는
후속 검증 대상입니다. 토큰 절감이나 완벽한 누락 탐지를 제품 약속으로 두지 않습니다.

### 저장·계정·삭제

계정별 로컬 저장소에 사용자가 저장한 프로젝트·기능·자료·확인 사항을 보존합니다.
재실행 시 같은 계정의 마지막 기능과 자료 선택을 복원합니다. 저장 실패 시 기존 파일을 유지하고
작성 중 내용을 화면에 남깁니다. 저장은 원자적으로 교체하며 취소한 편집은 기존 데이터에 반영하지 않습니다.

로그아웃과 세션 만료 시 외부 웹 세션, 화면의 선택 내용과 임시 작업 설명을 제거하고 계정 저장소를
닫아 잠급니다. 저장된 프로젝트 기록은 삭제하지 않으며 같은 계정으로 다시 로그인한 뒤 복원합니다.
계정이 바뀌면 이전 계정의 목록·웹 콘텐츠·발췌가 나타나지 않아야 합니다.
영구 삭제는 별도 확인을 거치며 해당 개인 프로젝트와 하위 로컬 기록만 지웁니다. 원문은 삭제하지 않습니다.

### 모듈과 의존성

`Features/ProjectWorkspace`에 Presentation·Domain·Data를 둡니다. Domain은 개인 프로젝트,
기능, 자료, 확인 사항과 작업 설명 구성을 다룹니다. Data는 계정별 로컬 저장을 담당합니다.
웹뷰는 원문 열람을 맡고 도메인 객체가 웹 세션을 소유하지 않습니다. 외부 서비스 통합 API와
서버 공유 Repository는 실제 계약이 필요해지는 단계에서 추가합니다.

2026-09-27에 서버의 `ProjectQueryController`와 `ProjectCommandController`를 읽어 프로젝트
목록·상세·팀원 조회와 멤버 관리 경로를 확인했습니다. 작업 공간의 기능·확인 사항·결정 공유 계약은
이 두 컨트롤러에서 확인하지 못했습니다. 서버 전체에 없다고 단정하지 않습니다.
`/api/v1/projects/me/managed`는 일반 챌린저에게 빈 페이지를 반환하므로 내 참여 프로젝트 목록으로
그대로 사용하지 않습니다. 조회 범위·멤버십·capability는 공유 단계 전에 별도 확인합니다.

### 검증과 성공 기준

| 검증 | 통과 기준 |
|---|---|
| 개인 시작 | 매칭 연결이나 팀원 설치 없이 프로젝트와 기능을 만들고 자료를 연결 |
| 역할 전환 | 같은 기능에서 PM·디자인·개발 관점을 바꿔도 데이터와 권한이 바뀌지 않음 |
| 자료 열람 | 서비스별 로그인·권한·오류 경로가 구분되고 실패 시 원문 URL을 열 수 있음 |
| 작업 재개 | 재실행 후 같은 계정의 마지막 기능으로 복귀 |
| 저장 실패 | 입력과 이전 저장본을 보존하고 다시 저장 가능 |
| 계정 분리 | 로그아웃 후 다른 계정에 이전 데이터가 보이지 않으며 원계정 재로그인으로 복구 |
| 작업 설명 | 선택한 발췌만 포함하고 출처·미결정을 보존하며 모델 없이 편집·복사 가능 |

초기에는 진행 중인 3~5개 팀에서 2주간 사용해 보는 실험을 제안합니다. 실험 규모는 모집 후 확정합니다.
자료를 찾는 시간, 기능당 등록·갱신 시간, 작업 재개 빈도를 기존 흐름과 비교합니다. 원문 내용과
비공개 URL을 분석 로그로 수집하지 않으며 초기 검증은 동의를 받은 관찰·인터뷰로 진행합니다.
팀 공유 단계에서 미결정 체류 시간과 해결 후 작업 재개를 추가합니다. 목표 수치는 기준선 측정 후 정합니다.

### 후속 범위

팀 공유·담당자 전달과 매칭 연결, 원문 기반 AI 확인 질문, 검증된 서비스의 변경 안내,
데모데이 준비 점검, 회고·포트폴리오 초안을 순서대로 검토합니다. 자동 생성보다 실제 자료 연결과
작업 재개가 반복 사용되는지 먼저 확인합니다. 서비스 전체 자동 감시·양방향 동기화·토큰 대시보드는
1차 범위에 넣지 않습니다.

## 7. 공유 패키지 — UMCNetworkKit

iOS 레포와 겹치는 네트워크 배관을 처음부터 별도 레포의 SPM 패키지로 뺍니다.
복사본으로 시작했다가 나중에 추출하는 방법도 있지만 두 앱이 동시에 자라는 동안
복사본이 서로 갈라지는 쪽이 더 비쌉니다. 0단계에서 패키지 추출을 끝내는 편을 택했습니다.

SPM 원격 의존성은 **레포 루트의 `Package.swift`만** 인식합니다. iOS 레포 안에 `Packages/` 폴더를
만들어 참조하는 방식은 동작하지 않습니다. 그래서 별도 레포가 사실상 강제입니다.

### 패키지 구성

레포는 `UMC-PRODUCT/umc-product-apple-network`입니다. 공개 레포로 만들었고
아직 비어 있습니다(2026-09-07 생성).

```
umc-product-apple-network/
├── Package.swift              ← 루트. 여기만 원격에서 보인다
└── Sources/UMCNetworkKit/
    ├── Base/       APIResponse, BaseTargetType, NetworkEnvironment
    ├── Client/     NetworkClient, MoyaNetworkAdapter, DefaultAuthenticationPolicy,
    │               TokenPair, TokenStoreProtocol, TokenRefreshServiceImpl
    ├── Realtime/   StompFrame, StompConnection
    ├── Identity/   ManagementTeam
    └── Error/      NetworkError, RepositoryError, ErrorSeverity
```

`platforms: [.iOS(.v26), .macOS(.v26)]`, 외부 의존성은 Moya 하나입니다.

`ManagementTeam`을 넣은 건 두 앱이 같은 권한 판정을 해야 하기 때문입니다. 서버 `roleType`
문자열과 레벨 표가 어긋나면 한쪽 앱에서만 버튼이 보이는 사고가 납니다. 이 파일은 189줄에
`import Foundation`뿐이라 그대로 옮깁니다.

### 안 넣는 것

`Core/Network` 아래에 있어도 패키지로 가지 않는 폴더가 있습니다.

- `Auth/` — 소셜 로그인 매니저. 12개월 커밋 6건으로 이 폴더가 가장 자주 바뀝니다
- `Member/`, `Authorization/` — `CoreDomain`에 의존합니다. 도메인을 끌고 오면 패키지가 아니라 앱이 됩니다
- `Storage/`, `DI/AuthSystemFactory` — 앱마다 다르게 씁니다

`UserSessionManager`도 패키지에 넣지 않습니다. `@Observable`이라 화면 계층과 붙어 있고
운영진 모드 토글의 의미가 두 앱에서 같으리라는 보장이 없습니다. macOS에서는 새로 만들되
`ManagementTeam` 판정 로직은 패키지 것을 씁니다.

DTO와 도메인 모델, 화면 코드도 전부 각 앱에서 따로 갑니다.

### 끊어야 할 연결 세 군데

공유 대상 파일 중 다섯 개가 `UMCFoundation`을 import합니다. 실제로 쓰는 심볼은 넷뿐이고
전부 끊어낼 수 있습니다.

| 지금 | 왜 문제인가 | 바꿀 것 |
|---|---|---|
| `NetworkConfig` → `Config.API.baseURL` | `Config`가 `Bundle.main.infoDictionary`를 읽고, 없으면 `fatalError`. 패키지가 앱 번들 구조를 알면 안 됩니다 | `NetworkEnvironment(baseURL:defaultHeaders:)`를 앱 시작 시 한 번 주입 |
| `NetworkClient.swift:81` → `AppStorageKey.clearSessionScopedValues()` | 패키지가 앱의 UserDefaults 키를 압니다 | `SessionResetting` 프로토콜을 주입받아 호출 |
| `NetworkError`·`RepositoryError`가 `UMCFoundation`에 있음 | 패키지가 `UMCFoundation`을 import하면 Alert·AppFlow·Location까지 딸려옵니다 | 에러 타입 셋을 패키지로 이동 |

세 번째가 제일 큽니다. iOS 레포에서 이 타입들을 이름으로 쓰는 파일이 `Core/Network` 바깥에 64개,
`ManagementTeam`을 쓰는 파일이 33개입니다. 백 개 가까운 파일에 import를 넣는 대신
`UMCFoundation`에 typealias 세 줄을 남깁니다.

```swift
public typealias NetworkError = UMCNetworkKit.NetworkError
public typealias RepositoryError = UMCNetworkKit.RepositoryError
public typealias ManagementTeam = UMCNetworkKit.ManagementTeam
```

`AppError`가 앞의 둘을 case로 감싸고 있으니 `UMCFoundation`이 패키지를 import하게 됩니다.
의존 방향이 뒤집히는 셈인데 연결을 끊고 나면 패키지 쪽은 `UMCFoundation`을 더 이상 import하지 않으므로
순환은 생기지 않습니다. 대신 `UMCFoundation`이 더는 의존 그래프의 바닥이 아니게 됩니다.

### 버전과 인증

- 태그 `v0.x.y`를 발행하고 `exact:`로 핀을 겁니다
- `branch: "develop"` 핀은 금지합니다. 어제 되던 빌드가 오늘 깨집니다
- 개발 중에는 Xcode에 로컬 패키지를 끌어다 원격 참조를 덮어써도 됩니다. 다만 PR 전에 되돌려야 하고
  `Package.resolved`가 로컬 경로를 가리키면 CI가 막습니다
- 공개 레포라 SPM이 인증 없이 받습니다. SSH 키나 deploy key를 등록할 일이 없습니다.
  대신 비밀값은 넣지 않습니다. `baseURL`도 앱이 주입하므로(위 표) 걸릴 것이 없습니다

### 0단계 작업 순서

0단계는 macOS 화면을 한 장도 만들지 않습니다. iOS 앱이 멀쩡한 채로 패키지를 물게 만드는 것까지가 끝입니다.

1. 패키지 레포에 `Base`/`Client`/`Realtime`, `ManagementTeam`, 에러 타입 셋을 옮기고
   위의 연결 셋을 끊습니다. 테스트도 함께 옮깁니다 — `APIResponseTests`, `NetworkClientTests`,
   `TokenPairTests`, `DefaultAuthenticationPolicyTests`, `StompFrameTests`, `StompConnectionTests`,
   `Tests/Support/`. `swift test`가 macOS에서 통과하는지 여기서 확인합니다
2. `v0.1.0` 태그 발행
3. iOS 레포: 옮긴 파일을 지우고 `Tuist/Package.swift`에 패키지를 추가합니다.
   `Core/Network/Project.swift`의 의존성에 `.external(name: "UMCNetworkKit")`를 넣고
   `UMCFoundation`에 typealias 세 줄, 앱 부트스트랩에 `NetworkEnvironment`와 `SessionResetting` 주입을 붙입니다
4. iOS 전체 빌드와 테스트가 통과한 뒤에 머지합니다
5. macOS 레포에서 같은 패키지를 참조합니다

3번이 iOS 레포를 건드리는 PR이라 리뷰가 붙습니다. macOS 작업을 시작하기 전에 이게 머지되어 있어야 합니다.

## 8. 앱 아키텍처

템플릿의 Clean Architecture를 그대로 씁니다.

```
View ←→ ViewModel(@Observable) → UseCase(Protocol) → Repository → DataSource
                                     ↑ DIContainer 주입
```

모듈 구성은 이렇습니다.

```
UMCDesk (app, .macOS)
Core/       Foundation · DesignSystem · UIComponents · DI
Features/   Auth · Notice · Community · Matching · ProjectWorkspace
```

`ProjectWorkspace`는 계정별 로컬 저장을 담당하는 Data 레이어가 있습니다(6장).
개인 MVP는 Community 전송이나 매칭 API에 의존하지 않습니다.

로그인은 iOS와 같은 경로로 갈 수 없습니다. 카카오 iOS SDK는 macOS에서 빌드되지 않습니다.
`Package.swift`의 플랫폼이 iOS뿐이고 `KakaoSDKAuth/auth/Auth.swift`가 UIKit을 조건 없이
import합니다(`kakao/kakao-ios-sdk`). 대신 서버에 authorization code 로그인이 따로 있습니다
(`POST /api/v1/auth/login/kakao/code`, `authorizationCode`·`redirectUri`).
맥은 시스템 웹 인증 세션으로 코드를 받아 이 API를 부릅니다.

애플 로그인은 서버가 `clientType`으로 client_id를 고르는데 `MACOS` 값이 없습니다.
구글도 같은 `clientType`을 받습니다. 맥에서 세 로그인이 모두 되는지는 서버와 함께
확정합니다(14장). `Auth/`는 패키지에 넣지 않으므로 로그인 매니저는 macOS 레포에서 따로 만듭니다.

`Matching`은 iOS에 없는 신규 피처입니다. 웹 v2와 같은 서버라 토큰도 그대로 씁니다.
`BaseTargetType`은 `baseURL`을 호스트 루트로만 두고 Router가 전체 path를 들고 있습니다.
프로젝트 API는 전부 `/api/v1/projects` 아래라 iOS Router와 prefix가 같습니다. 매칭 차수만
`/api/v1/project/matching-rounds`로 단수형이라 여기서 오타를 내기 쉽습니다.

권한 게이팅은 화면마다 흩어 두지 않습니다. `UserSessionManager` 상당물을 `Core/Foundation`에 두고
ViewModel이 그걸 관찰해 버튼 노출 여부를 결정합니다. 기수별 파트 목록도 여기서 같이 들고
있습니다. 다만 매칭 화면의 버튼은 세션이 아니라 `projects/permissions` 응답을 봅니다.
세션은 지원 자격까지, 그 뒤부터는 서버 capability입니다.

### 템플릿에서 고쳐야 할 것

`Project+Core.swift`의 `coreProject`는 `destinations` 파라미터가 이미 열려 있어 그대로 쓸 수 있습니다.
문제는 `Project+Feature.swift`입니다. Domain 레이어만 `domainDestinations`로 열려 있고
Data와 Presentation은 `.iOS`가 박혀 있습니다(62·76·108·122행). 세 레이어 모두 파라미터로 열어야 합니다.

Presentation은 두 앱이 공유하지 않습니다. macOS 공지 목록은 `Table` 정렬 키가 붙는데 iOS는 그럴 일이 없고
스레드 방은 아예 별도 창입니다. 네트워크는 공유하지만 화면 구성은 다릅니다.

## 9. 데이터 흐름과 실시간

STOMP 커넥션은 앱 생애에 하나입니다. 창이 몇 개든 하나입니다. actor로 격리하고
각 화면은 `threadId`로 필터링해서 자기 이벤트만 받습니다. iOS의
`CommunityThreadRealtimeClient`가 이미 이 구조입니다. 스레드 이벤트는 방마다 구독하지 않고
사용자 큐 하나(`/user/queue/community/threads/events`)로 모두 옵니다. 에러는
`/user/queue/errors`로 옵니다. 같은 이벤트가 두 번 올 수 있어 `eventId`로 거릅니다
(서버 `docs/guides/community-thread-client-contract.md`).

맥에서 새로 생기는 문제는 잠자기입니다. 노트북 덮개를 닫으면 커넥션이 끊기고 열면 재연결됩니다.
STOMP는 끊긴 동안 놓친 이벤트를 다시 주지 않으므로 재연결 직후 REST로 메시지를 한 번 채워 넣어야 합니다.
iOS에서도 같은 처리를 하지만 맥은 이 상황이 훨씬 자주 옵니다.

매칭 심사의 합격·불합격 판정은 낙관적 업데이트를 하지 않습니다. 화면에 먼저 반영했다가
서버가 거절하면 되돌려야 하는데 심사 결과는 되돌리는 사이에 심사자가 다음 지원자로 넘어가 버립니다.
서버 응답을 확인하고 반영합니다.

역할이 바뀌는 경우도 있습니다. 임기가 끝나 권한이 빠지거나 새로 붙는 상황인데
앱을 켜 둔 채로 바뀌면 화면과 실제 권한이 어긋납니다. 서버가 403을 주면
`UserSessionManager`를 다시 동기화하고 화면을 갱신합니다. 스레드의 403은 예외입니다.
조직 역할이 아니라 방 참여나 방 역할의 문제라 동기화하지 않고 방 상세를 다시 받습니다.
강퇴됐으면 그 방을 닫습니다. 둘은 에러 코드로 가릅니다.

### 메시지 전송과 재전송

스레드 메시지는 STOMP로만 만듭니다. 보낼 때마다 `clientMessageId`를 새로 만듭니다
(소문자 UUID). 서버는 방·보낸 사람과 이 값을 묶어 멱등 키로 씁니다. 같은 키에 같은 내용이면
기존 결과를 돌려주고 내용이 다르면 409(`CHAT-0014`)입니다.

- 한 번 보낸 메시지의 내용과 `clientMessageId`는 얼립니다. 재전송은 둘 다 그대로 씁니다
- 고쳐서 다시 보내면 새 메시지입니다. `clientMessageId`도 새로 만듭니다
- 끊긴 동안에는 타임아웃을 세지 않습니다. 재연결되면 대기 중인 메시지를 같은 id로
  한 번 다시 보냅니다. 서버가 이미 받았으면 중복으로 걸러 줍니다
- 15초 안에 `message.created`도 에러도 오지 않으면 실패로 표시합니다. iOS와 같은 값입니다
- 에러는 `retryable`을 따릅니다. 서버는 5xx에서만 참을 줍니다(`CommunityStompErrorMapper`).
  참이면 [다시 보내기]와 [고쳐서 보내기]를, 거짓이면 [고쳐서 보내기]만 보여 줍니다.
  429만 예외로, 보내기에 쿨다운을 걸었다가 풀리면 [다시 보내기]를 켭니다.
  409는 같은 id를 다른 내용에 쓴 클라이언트 버그의 신호라 로그로 남깁니다
- 실패로 표시한 뒤에 `message.created`가 늦게 와도 보냄으로 바꿉니다

재연결 직후의 재전송이 iOS와 다른 점입니다. iOS는 기록 조회로만 공백을 메우는데
기록(`GET …/messages`)에는 `clientMessageId`가 없어 내 대기 메시지와 짝을 짓지 못합니다.
맥은 같은 id로 다시 보내 ACK의 `messageId`로 짝을 짓습니다. ACK는 best-effort라 못 받을 수
있습니다. 그때는 실패로 남지만 사용자가 다시 보내도 서버가 거르므로 같은 글이 두 번 올라가지는 않습니다.

## 10. 에러 처리

세 갈래를 그대로 씁니다.

- **Loadable** — 화면 안 인라인 상태. 목록 로딩, 검증 실패
- **ErrorHandler** — 흐름을 끊는 전역 Alert. 세션 만료, 권한 없음
- **AlertPrompt** — 확인·취소 다이얼로그. 지원서 반려처럼 되돌리기 어려운 작업

맥에서 정해야 할 건 하나입니다. 창이 여러 개일 때 전역 Alert이 어디에 뜨는가.
활성 창 기준으로 띄웁니다. 백그라운드 창에서 발생한 오류라도 사용자가 보고 있는 창에 뜨는 편이 낫습니다.

세 갈래 밖에서 처리하는 것이 둘 있습니다.

- **서버 점검** — 503(`MAINTENANCE-0001`)은 Alert 대신 점검 화면으로 덮습니다.
  공개 API `GET /api/v1/system/status`가 `inMaintenance`와 현재 점검 창(`current`)을 줍니다.
  앱을 켤 때 한 번, 503을 받았을 때 한 번 부릅니다
- **실시간 실패** — 메시지 전송 실패는 메시지 옆 표시로 끝냅니다(9장). 재연결 실패는
  사용자가 시작한 동작이 아니라 Alert을 띄우지 않습니다

## 11. 테스트

패키지 테스트는 iOS와 macOS 양쪽에서 돌아야 합니다. 패키지 레포 CI에서 `swift test`로 macOS를 확인하고
iOS는 앱 레포의 Tuist 테스트가 커버합니다. 옮긴 테스트 중 `KeychainTokenStoreTests`는
entitlements가 필요해서 그대로는 안 돌아갑니다 — 이건 앱 레포에 남깁니다.

앱 테스트는 UseCase와 Repository 위주입니다. 권한 분기는 테스트를 붙입니다.
역할별로 어떤 기능이 보여야 하는지가 이 앱에서 제일 틀리기 쉬운 부분입니다.
축이 둘이라 더 그렇습니다. 레벨은 challenger인데 파트가 Plan인 계정이 대표적인 함정입니다.

프로젝트는 URL 검증, 계정별 저장·복원, 저장 실패 시 보존, 명시적 삭제 범위와 작업 설명의
입력 선택을 검사합니다. 링크만 있는 자료를 읽은 본문으로 취급하지 않는지도 확인합니다.
웹뷰 인증·비공개 자료 접근·원문 열기는 서비스별 수동 검증 기록을 남깁니다.
스레드 재전송은 같은 id·본문을 유지하고 수정 후 전송은 새 id를 쓰는지 검증합니다.

## 12. 배포

App Store에 올리지 않고 공증 DMG로 나갑니다. 샌드박스가 강제되지 않는 대신
Developer ID 서명과 `notarytool` 공증이 필요하고 CI에서 서명하려면 인증서와 앱 암호를
시크릿으로 등록해야 합니다. 5단계에서 이 파이프라인을 만듭니다.

자동 업데이트 프레임워크는 넣지 않습니다. 앱을 켤 때 최신 버전을 확인해 알림만 띄우고
다운로드는 링크로 넘깁니다. Sparkle은 배포가 잦아져서 손이 아파질 때 붙이면 됩니다.
최신 버전을 어디서 확인할지와 강제 업데이트 여부는 14장에 권장값을 적어 두었습니다.

## 13. 로드맵

| 단계 | 내용 | 끝났다고 볼 기준 |
|---|---|---|
| 0 | SPM 패키지 추출 + iOS 마이그레이션 | iOS 앱이 패키지를 물고 전체 테스트 통과 |
| 1 | 템플릿 셋업, 로그인, 역할·파트 동기화, 공지 열람 | 챌린저 계정으로 로그인해 공지를 읽는다 |
| 2 | 스레드 목록·방·별도 창 | 스레드 방을 떼어 놓고 대화한다 |
| 2.5 | 프로젝트 개인 작업 공간 | 6장 수용 기준 통과. 자료 연결·작업 재개·설명 복사가 가능하다 |
| 3 | 운영진 모드, 공지 작성·대상 지정·읽음 통계 | 맥에서 쓴 공지가 iOS 앱에 뜬다 |
| 4 | 매칭 공고 등록·차수 개설·지원·심사·팀 확정 | PO가 맥에서 공고를 올리고, 챌린저가 지원해 팀이 확정된다 |
| 5 | 메뉴바·단축키·창 상태 복원·서명·공증 | 공증 DMG로 설치된다 |
| 6 | 문의 채널 (서버 문의 도메인이 올라온 뒤) | 챌린저가 맥에서 문의를 열고 운영진이 답한다 |

챌린저 기능을 앞에 뒀습니다. 1·2단계만 끝나도 챌린저에게는 쓸 만한 앱이 되고
운영 기능은 그 위에 얹힙니다. 반대로 하면 3단계까지 가야 아무도 쓸 수 있는 게 없습니다.

## 14. 확인이 필요한 것

사람이 정할 것은 권장 기본값을 같이 적었습니다. 정해지기 전까지 설계는 기본값을 가정합니다.

### 정할 것

| 항목 | 권장 기본값 | 결정 | 기한 |
|---|---|---|---|
| 프로젝트 목표 수치 | 자료 탐색 시간과 등록 부담을 기준선 측정 후 결정 | PM + 운영 | 2.5단계 파일럿 전 |
| 서비스별 앱 내 열람 | 로그인·비공개 자료·원문 열기 검증 후 지원 범위 확정 | macOS | 2.5단계 구현 계획 전 |
| 팀 공유와 매칭 연결 | 개인 MVP 이후 계약 확인. 단계 4 완료만으로 공유를 자동 활성화하지 않음 | PM + 서버 | 후속 계획 전 |
| AI 확인 질문 | 선택한 내용만 분석하며 모델·실행 위치·비용은 후속 검증 | PM + macOS | AI 점검 착수 전 |
| 원격 푸시 | 1차 없음. 앱이 켜져 있는 동안만 실시간(4장) | 운영 | 1단계 착수 전 |
| 업데이트 확인 출처 | macOS 레포(공개)의 GitHub Releases 최신 릴리스. 강제 업데이트는 1차 없음. 필요해지면 iOS 원격 설정(`umc-product-iOS-remote-config`)의 `minimumVersion` 방식을 맥에도 둡니다 | iOS + 운영 | 5단계 착수 전 |
| Developer ID 인증서와 공증용 Apple 계정 보유자 | — | 운영 | 5단계 착수 전 |

### 서버에 요청할 것

| 항목 | 요청 | 결정 | 기한 |
|---|---|---|---|
| 맥 로그인 | `ClientType`에 `MACOS` 추가. 애플 client_id 매핑과 플랫폼별 트래픽 구분(1장)에 필요합니다. 카카오 코드 로그인에 맥용 `redirectUri` 등록(8장) | 서버 + iOS | 1단계 착수 전 |
| 문의 메시지 멱등 키 | 문의 메시지 페이로드에 `clientMessageId` 추가. 같은 키에 다른 내용이면 409(5장) | 서버 | ADR-011 Phase 6(WebSocket) 착수 전 |
| 문의 도메인 착수 | ADR-011 구현 일정과 서버 명세 변경 요청의 수락 여부. 6단계가 통째로 걸려 있습니다 | 서버 | 6단계 계획 전 |

### 확인할 것

| 항목 | 방법 | 담당 | 기한 |
|---|---|---|---|
| 외부 열람·저장 검증 | 통과 기준은 6장 표 | iOS | 2.5단계 구현 계획 전 |
| 챌린저 맥 현황 | macOS 26 사용 가능 비율과 팀에서 맥을 쓰는 인원을 설문으로 확인합니다 | 운영 | 1단계 착수 전 |
