# 앱 문의 채널과 서버 연동 범위

작성자: 제옹(euijjang97)  
작성일: 2026-11-17  
상태: 디자인·설계 준비도 검토 및 서버 협의용 — Figma 시안과 서버 ADR의 차이를 정리한다.

## 1. 전달 목적과 결정할 범위

UMC Desk의 Figma에는 **앱 내부 문의 등록·운영 목록·상세와 담당자·라벨을 다루는 Mid-fi 설계**가 있다. 이 문서는 그 설계와 서버 ADR-011을 대조하여 서버 담당자가 사용자 흐름과 작업 범위를 이해하고, 개발 착수 전에 남은 계약을 확인하도록 돕는다. 구현 여부와 디자인·설계 준비도는 별도로 판단한다.

앱은 문의 작성·조회·대화와 운영 화면의 상호작용을 맡고, 서버는 합의된 문의 데이터·권한·담당 배정·라벨·실시간 계약을 제공한다. 운영 담당은 접수·응답·이관 정책을 결정한다. **담당자 지정과 라벨은 디자인에 이미 있으며 서버 ADR에서 충분히 설명되지 않은 항목**이다. PRODUCT 내부 팀 설명·선택과 실시간 세부 계약은 아래 준비도 표에서 구분한다.

| 구분 | 범위 | 이 문서의 판단 |
|---|---|---|
| 내부 문의 | 문의 등록·대화·운영 목록·담당자·라벨·처리 상태 | 이번 디자인·설계 대조의 중심 범위. Figma와 ADR의 차이를 맞춘 뒤 계약 확정 |
| 외부 채널 안내 | 로그인할 수 없는 사용자의 공식 접수 경로 | 보조 경로 제안. 내부 문의를 대체하는 1차 출시 범위로 승인된 사항이 아님 |

이 문서 초안에서 제시했던 외부 채널 우선 연결은 작성 과정의 제안이며 사용자 승인 요구사항이 아니다. 기존 설정의 카카오톡 주소 연결 설계를 내부 문의 전체의 범위로 일반화하지 않는다.

## 디자인·설계 준비도

확인한 디자인은 [Mid-fi 06 문의](https://www.figma.com/design/kM8a1siXgusAVRRgyUZ15U/UMC-Mac-OS?node-id=335-845)의 [Light](https://www.figma.com/design/kM8a1siXgusAVRRgyUZ15U/UMC-Mac-OS?node-id=171-557)다. [시안 안내](https://www.figma.com/design/kM8a1siXgusAVRRgyUZ15U/UMC-Mac-OS?node-id=401-6204)는 2026.09.30 기획 개선 시안이며 인물·수치는 예시라고 설명한다. 예시 인물을 실제 문의 운영 담당으로 지정하지 않는다.

**네 요구 전체의 개발 착수 준비가 완료됐다고 보기는 어렵다.** 담당자·라벨·실시간 인기 문의는 화면과 일부 예외 상태가 구체적으로 설계돼 있다. 이를 없는 기능으로 다시 기획할 필요는 없지만, 서버 ADR에 빠진 동작과 데이터 계약을 연결해야 한다. PRODUCT 내부 팀 설명·선택은 확인한 등록 시안에서 찾지 못했다.

| 요구 | 디자인에서 확인한 내용 | 서버 설계와 차이·착수 전 결정 |
|---|---|---|
| 담당자 지정 | [Q5 운영 문의 상세](https://www.figma.com/design/kM8a1siXgusAVRRgyUZ15U/UMC-Mac-OS?node-id=409-3069): 미배정·내가 맡기·담당자 선택·변경 이력. [상태 참고](https://www.figma.com/design/kM8a1siXgusAVRRgyUZ15U/UMC-Mac-OS?node-id=409-3059): 동시 배정 충돌, 담당자 권한 만료 시 미배정. [운영 목록](https://www.figma.com/design/kM8a1siXgusAVRRgyUZ15U/UMC-Mac-OS?node-id=125-8946): 내 담당·미배정 | ADR-011은 대상 운영진 전체 열람·응답 중심. 배정·변경 권한, 담당 후보 자격, 동시 변경의 판정·오류 응답, 권한 만료 시 회수와 이력 계약 필요 |
| 라벨 | Q5에 PRODUCT 내부용 라벨·편집·복수 선택, 운영 목록에 라벨 필터 | ADR의 단일 category와 다른 기능. 라벨 목록·부착/제거·편집 권한, 일반 사용자에게 숨기는 응답 경계, 삭제된 라벨·동시 편집 규칙 필요 |
| PRODUCT 팀 설명·선택 | [Q3 문의 등록](https://www.figma.com/design/kM8a1siXgusAVRRgyUZ15U/UMC-Mac-OS?node-id=125-9094)은 카테고리를 고르고 UMC PRODUCT에 전달. 내부 팀별 성격 설명·선택은 해당 화면에서 미확인 | ADR의 CENTRAL·UMC_PRODUCT·CHAPTER·SCHOOL은 PRODUCT 내부 팀이 아님. 팀 선택이 요구사항이면 소개·선택·미선택·잘못 선택했을 때 이관, 팀별 열람·담당 후보 범위를 추가 합의 |
| 실시간 인기 문의 | [Q1 많이 묻는 질문](https://www.figma.com/design/kM8a1siXgusAVRRgyUZ15U/UMC-Mac-OS?node-id=125-8897): 최근 24시간/7일, 마지막 갱신, 문의 인원, 반복 접수 1회 집계, 새 순위 보기로 읽던 목록 보존. [상태 참고](https://www.figma.com/design/kM8a1siXgusAVRRgyUZ15U/UMC-Mac-OS?node-id=401-5915): 인기 없음·검색 없음·연결 끊김·마지막 갱신·새로고침 | ADR-011에는 인기 순위 집계 계약이 없음. 문의 묶음의 기준, 기간·시간대·중복 집계 단위, 동률, 갱신 주기·전달 방식, 공개되는 제목·인원과 개인정보 경계, 새 순위 적용 계약 필요 |

실시간 **대화**와 실시간 **인기 문의 순위**는 구분한다. [진행 중 상세](https://www.figma.com/design/kM8a1siXgusAVRRgyUZ15U/UMC-Mac-OS?node-id=125-8995)와 [종료 상세](https://www.figma.com/design/kM8a1siXgusAVRRgyUZ15U/UMC-Mac-OS?node-id=125-9044)에는 메시지·담당자 표시·재오픈 안내가 있다. ADR-011에도 대화·상태 전이·읽음·첨부·알림 설계가 있고, [ADR-026의 복구 원칙](https://github.com/UMC-PRODUCT/umc-product-server/blob/60fdadd2cb0ef7c8a252cc1903859af56ba7b015/docs/adr/026-separate-chat-engine-consumer-realtime-responsibilities.md#L262)은 메시지 중복·순서 역전·조회 backfill을 다룬다. 이를 인기 순위의 갱신 계약으로 대신하지 않는다.

문의의 최종 API/STOMP 경로·payload도 맞춰야 한다. ADR-011은 `/app/inquiry/{inquiryId}/message`와 `/topic/inquiry/{inquiryId}`를, ADR-026 예시는 `/app/inquiry/{inquiryId}/messages`와 `/topic/inquiry/{inquiryId}/messages`를 쓴다. ADR-026의 Accepted 상태는 문의 전용 계약까지 확정됐다는 뜻이 아니다. 진행·종료·재오픈 시나리오와 연결 끊김·재시도·중복 전송 시 UI를 최종 계약과 함께 확인한다.

서버 전달 전 남은 일은 새 화면을 일괄 설계하는 것이 아니라, **기존 시안의 배정·라벨·순위 동작을 ADR와 계약에 반영하고 팀 선택 요구의 빈칸을 확정**하는 것이다. 위 표는 확인된 설계와 보완점을 기록한 것으로 신규 정책을 승인하거나 구현 범위를 확장하지 않는다.

## 2. 현재 앱에서 문의가 필요한 맥락

| 진입점 | 사용자가 해결하려는 문제 | 현재 동작 | 연결 시 요구 |
|---|---|---|---|
| 로그인 선택 화면 하단 고객센터 | 계정·로그인 관련 도움 | 연결 준비 중 Alert | 로그인 없이 접근 가능 |
| 오프라인·로그인 실패 | 재시도로 해결되지 않는 접근 오류 | 연결 준비 중 Alert | 로그인 실패를 다시 요구하지 않음. 오프라인에서는 네트워크 필요 안내 |
| 업데이트 다운로드·검증·설치 실패 | 반복되는 업데이트 오류 | 연결 준비 중 Alert | 앱을 정상 이용하지 못해도 경로 확인 가능 |
| 챌린저 안내·코드 오류 | 코드 발급·등록·인증 관련 도움 | 연결 준비 중 Alert | 유효한 챌린저 등록 완료를 문의 조건으로 삼지 않음 |
| 설정 → 프로필 → 문의하기 | 이름·학교·활동 정보 정정 | 앱 정보 화면 이동 | 정정 요청의 접수처를 안내. 앱에서 자동 정정하지 않음 |
| 설정 → 활동 코드 등록 오류 → 담당 운영진에게 문의 | 코드 오류와 운영 확인 | 다이얼로그 닫기 후 앱 정보 화면 이동 | 학교별 운영진 자동 배정은 현재 없음 |
| 설정 → 앱 정보 → 문의하기(카카오톡) | 일반 도움·의견 | `준비 중` 텍스트 | 검증된 공식 주소가 있을 때 열기 제공 |

설정 검색에도 `문의하기(카카오톡)`이 등록돼 있다. 연결 변경 시 검색 결과, 프로필과 코드 오류의 경유 경로, Auth의 공통 버튼과 별도 오류 버튼을 함께 반영해야 한다.

기존 [설정 설계](../specs/설정_마이페이지와%20앱%20설정_설계.md)는 주소 확인 전 `주소 확인 중` 표시를 요구한다. 실제 UI는 현재 `준비 중`이므로 출시 연결 작업에서 문구를 통일한다. 문의 버튼을 눌렀다는 사실을 문의 접수 완료로 표시하지 않는다.

## 3. 확인한 서버 지원 상태

확인 기준은 서버 `main`의 [60fdadd2cb0ef7c8a252cc1903859af56ba7b015](https://github.com/UMC-PRODUCT/umc-product-server/tree/60fdadd2cb0ef7c8a252cc1903859af56ba7b015)이다. GitHub API로 전체 경로 목록을 조회했으며 `truncated=false`였다. 기존 로컬 서버 안내의 `src/main/java`와 달리 현재 주요 소스는 `monolith/src/main/java`에 있다.

| 확인 대상 | 확인 결과 | 앱 연동에 대한 의미 |
|---|---|---|
| 문의 도메인 | 경로 목록에서 `inquiry` 구현·Controller·DTO는 확인되지 않고 ADR-011만 확인됨 | 문의 등록·목록·메시지 API가 제공된다고 전제할 수 없음 |
| 채널 안내 API | 전용 contact/support 채널 Controller·DTO 경로를 찾지 못함 | 기존 API 재사용 가능 여부 또는 새 계약은 서버 확인 필요 |
| 시스템 상태 | `GET /api/v1/system/status`는 `@Public`. 응답은 `inMaintenance`, `current`, `upcoming` | 현재 응답을 문의 채널 응답으로 사용할 수 없음 |
| 사용자 피드백 | `UserFeedbackController`는 로그인 사용자의 만족도 설문 템플릿 조회·응답 제출 | 고객센터 문의·응답·처리 상태 API로 대체하지 않음 |

경로 검색으로 서버 전체에 같은 기능이 전혀 없다고 단정하지 않는다. 실행 환경, 다른 브랜치, 배포된 API, 외부 채널 운영 여부는 이번에 검증하지 않았다.

### ADR-011과의 관계

[ADR-011](https://github.com/UMC-PRODUCT/umc-product-server/blob/60fdadd2cb0ef7c8a252cc1903859af56ba7b015/docs/adr/011-inquiry-domain-with-websocket-stomp.md)은 `Proposed` 상태이며 다음을 기술한다. 아래 내용은 **기존 제안의 소개이며 현재 API 명세나 이번 출시 확정 요구사항이 아니다.**

- 로그인 사용자가 문의 대상을 선택하고 문의방을 만들며 운영진과 대화한다.
- 대상은 `CENTRAL`, `CHAPTER`, `SCHOOL`, `UMC_PRODUCT`이며, 상태는 `RECEIVED`, `IN_PROGRESS`, `CLOSED`다.
- REST 문의 등록·목록·상세·읽음·종료·재오픈, STOMP 메시지 전송·구독, 첨부와 알림을 제안한다.
- 작성자와 대상 운영진의 접근 권한, 운영진 미읽음·상태 필터, 메시지 수정·삭제 제한을 다룬다.
- `UMC_PRODUCT`를 중앙운영사무국 전체에 임시 매핑하는 미결정 사항이 남아 있다. UMC PRODUCT와 UMC 중앙운영사무국은 별도 조직이므로 이 임시안을 개인정보 열람·배정 정책으로 채택하지 않는다.

내부 문의방을 선택하면 실제 Controller·DTO, 대상별 열람 범위와 기수·학교·지부 판정, 운영자 배정·회수, 첨부 접근, 보존·삭제, 알림·재연결·중복 방지 계약을 먼저 확정한다. ADR 안의 경로·페이로드를 복사해 macOS API 구현을 시작하지 않는다. 기존 Chat 엔진을 쓰더라도 문의 대상과 열람 정책은 별도 소비 도메인 결정이 필요하다.

## 4. 로그인 불가 상황의 외부 채널 안내 제안

이 절은 내부 문의 설계와 별개인 보조 경로 제안이다. 아래 최소 범위·제외 사항은 외부 연결에만 적용하며 담당자·라벨 등 내부 문의의 설계를 제외하지 않는다.

### 사용자 흐름

1. 사용자가 기존 문의 진입점을 선택한다.
2. 앱이 이용 가능한 공식 접수 채널과 안내를 확인한다.
3. 유효한 채널이면 사용자가 명시적으로 선택해 외부 브라우저·앱을 연다.
4. 실제 문의 작성·답변은 해당 채널에서 진행한다. UMC Desk에는 접수번호나 완료 상태를 생성하지 않는다.

프로필·활동 정보 정정 문의도 우선 같은 안내를 재사용할 수 있다. 접수 운영자가 적절한 담당에게 연결할 수 있는지 확인해야 하며, 단순히 버튼 이름이 `담당 운영진`이라는 이유로 학교별 배정 기능이 있다고 해석하지 않는다.

### 서버가 제공할 정보

운영 주소를 앱 배포 없이 바꿀 필요가 있다면 서버가 공개 가능한 채널 설정을 조회 형태로 제공하는 방안을 제안한다. **아래는 논리 항목이며 JSON 필드명·타입·URL·HTTP 경로를 확정한 것이 아니다.** 기존 공용 설정 계약이 있다면 먼저 재사용 여부를 확인한다.

| 논리 항목 | 필요한 의미 | 최소 처리 기준 |
|---|---|---|
| 채널 구분 | 카카오톡 등 실제 접수 수단 | 기존 설정 화면의 카카오톡을 우선 확인. 이메일·웹폼 추가는 운영 필요와 합의가 있을 때 |
| 표시 이름 | 사용자가 알아볼 공식 채널명 | 운영 담당이 승인한 명칭만 사용 |
| 접수 주소 | 사용자가 직접 여는 목적지 | 카카오톡은 공식 HTTPS 웹 진입 주소 우선. 운영 소유·유효성 확인 |
| 이용 가능 상태 | 공개·사용 가능 또는 중단 | 미설정·비활성은 실행 불가. 중단 시 주소를 계속 노출할지 함께 결정 |
| 안내 문구 | 필요한 접수 안내 | 운영시간·응답 기한은 실제 합의가 있을 때만 표시. 선택값이 비어도 채널 이용 가능 |

조회는 로그인 이전에 필요하므로 공개 조회를 제안하되 **공식 접수 채널의 공개 정보만** 반환한다. 회원 ID·학교·기수로 개인화하거나 내부 담당자 목록·개인 연락처를 내려주는 기능은 외부 채널 안내에 필요하지 않다. 인증이 없는 클라이언트에 채널 설정을 수정할 권한을 주지 않는다.

서버와 합의할 계약에는 응답 envelope, 빈 목록·null·필드 누락의 의미, 미지원 채널 처리, HTTP 상태·오류 코드, 점검 중 접근 가능 여부를 포함한다. 여러 채널이 필요해졌을 때만 목록·순서 계약을 추가한다. 현재 앱은 고정 1개 채널 화면이므로 채널 선택 UI를 전제로 요구하지 않는다.

### 운영·갱신

- 실제 접수 계정의 소유자, 응답 담당, 문의를 다른 팀에 넘기는 방법을 먼저 정한다. 서버 구현 담당이 자동으로 고객센터 운영 담당이 되는 것은 아니다.
- 게시·변경·중단 권한과 검증 책임자를 지정한다. 주소 변경은 승인된 공개 목적지인지 검증하며 잘못된 URL을 저장·노출하지 않는다.
- 외부 주소 설정용 관리 화면 신설은 필수 사항이 아니다. 기존 운영 설정 수단으로 변경할 수 있는지 서버가 제안한다. 권한·변경 기록·복구 방법은 유지한다.
- 갱신 반영 시점과 캐시 정책을 계약에 적는다. 최초에는 영속 캐시 없이 조회하고 실패 시 안내하는 방식으로 시작할 수 있다. 장애 중에도 주소 제공이 필요하면 검증된 기본 주소 또는 만료 정책이 있는 캐시를 별도로 합의한다. 철회된 주소를 무기한 제공하지 않는다.

### 실패·빈값 처리와 개인정보 경계

| 상황 | 앱 동작 제안 |
|---|---|
| 미설정·빈 주소·사용 중단 | 열기 비활성, `주소 확인 중` 또는 운영 안내. 임의 채널로 대체하지 않음 |
| 조회 실패·오프라인 | 재시도 제공, 연결 상태 안내. 로그인 화면으로 강제 이동하지 않음 |
| 잘못된 URL·미지원 채널 | 실행 차단, 채널 이용 불가 안내. 서버도 등록 단계에서 검증 |
| 외부 앱·브라우저 열기 실패 | 실패 안내와 다시 시도. 접수 성공으로 처리하지 않음 |
| 채널 이름·주소 외 선택 안내 누락 | 유효한 핵심 정보가 있으면 기본 안내로 연결 |

외부 주소에는 토큰·비밀번호·활동 코드·회원 정보·진단 로그를 자동 첨부하지 않는다. 임의 scheme이나 사용자 정보가 포함된 URL을 허용하지 않으며, 허용 목적지 기준은 공식 채널 주소를 확정할 때 합의한다. 문의 내용·첨부·개인정보를 UMC 서버에 새로 저장하는 범위는 채널 안내에 포함하지 않는다.

개인정보 권리 행사·탈퇴자 문의까지 같은 채널이 받는지는 별도 운영 확인이 필요하다. [개인정보 초안](../specs/개인정보_통합%20개인정보%20처리방침_설계.md)의 담당부서·연락처 자리표시자나 Handbook의 구성원용 Discord를 앱의 공개 문의처로 대신 쓰지 않는다. 이 문서는 법률 방침의 확정이나 개인정보 책임자 지정을 수행하지 않는다.

## 5. 이번 범위와 제외 사항

이번 검토의 완료 목표는 **내부 문의 시안에 있는 동작과 서버 설계를 대조해 착수 가능한 부분·보완할 계약을 구분**하는 것이다. 문서 작성만으로 앱 기능·서버 API를 구현하거나 채널을 공개하지 않는다.

담당자·라벨·내부 문의 흐름을 외부 링크 연결 작업으로 축소하지 않는다. 신규 자동 배정·만족도 설문 통합 등 시안·합의에서 확인되지 않은 기능을 추가로 확정하지 않는다. ADR-011의 미결정 사항과 시안 대비 누락은 아래 준비도 검토를 바탕으로 보완한다.

## 6. 서버·운영 협의 요청

| 결정할 항목 | 요청 내용 |
|---|---|
| 디자인·설계 정합성 | 시안의 담당자·라벨·등록·운영 흐름을 서버 계약에 반영하고 미결정 상태·권한을 확정 |
| 공식 채널 | 카카오톡 실제 주소·표시명·운영 소유자·응답 담당·공개 가능 여부 확인 |
| 업무 라우팅 | 로그인·코드·활동 정보·일반 의견을 한 창구가 받을 수 있는지, 담당 이관 방식 확인 |
| 서버 제공 방식 | 재사용 가능한 공개 설정 API 존재 여부, 새 계약이 필요하면 경로·DTO·오류·빈값 정의 |

### 전달할 담당과 근거

2026-11-17에 Handbook [README](https://github.com/UMC-PRODUCT/umc-product-handbook/blob/33c6c467d313fb5e52e6bff3c534a18d1bf7569f/README.md)와 [Ownership Registry](https://github.com/UMC-PRODUCT/umc-product-handbook/blob/33c6c467d313fb5e52e6bff3c534a18d1bf7569f/ownership-registry.md)를 조회했다. 책임 등록은 새 작업의 수락·착수·기한을 의미하지 않는다.

| 담당 | 이번에 요청할 역할 |
|---|---|
| Mac 파일럿 — 제옹, 결과·기술 구현 책임 | 진입점·최소 출시 범위 정리, 합의된 계약의 macOS 연동 |

| Platform — 토리, 인증/인가 담당 | 공개 채널 조회와 설정 변경 권한의 경계 검토. 내부 문의방 채택 시 대상별 접근 검토 |
| Server — 박박지현, Chapter Lead | 서버 API·데이터·품질 기준 검토 및 구현 담당 연결. 이 요청은 Infrastructure DRI 역할과 구분 |
| Organization Operations — 라엘, 부총괄 | 문의 운영 소유자·현재 목적팀 담당이 불명확할 때 최신 담당 연결 |

Handbook은 기존 앱 운영 정보·승인 업무를 Operations Enablement에 두고 루씨를 Acting Lead로 기록하지만, Purpose Acting Lead 임기는 2026-11-08에 종료된다고 명시한다. 현재 문서만으로 연임이나 현 담당을 확정할 수 없으므로 활동 정보 정정의 제품 정책·접수 운영 담당은 라엘 또는 총괄단을 통해 재확인한다. 담당 팀이 불명확하면 구성원용 `총괄단-문의`·`@UMC PRODUCT 총괄단`으로 연결을 요청한다. 이 경로는 앱 사용자용 문의 채널이 아니다.

Platform 책임 경계는 [공통 엔진 가이드](https://app.notion.com/p/makeus-challenge/3f2b57f4596b806f9532f2e82f73f15c?source=copy_link)의 [저장된 복사본](../Codex/platform-domain-ownership.md)을 참고했다. Notion 최신본은 확인하지 못했으며 복사본은 2026-10-10 기준이다. 공통 전달·인증 엔진의 책임과 문의 접수·열람·응답 정책의 책임을 나누며, 책임 범위로 구현 완료를 추정하지 않는다.

## 7. 합의 후 외부 보조 경로의 수용 기준

- 모든 기존 문의 진입점이 합의된 접수 경로로 이어지고, 로그인 전·챌린저 미등록 상태에서도 필요한 안내를 볼 수 있다.
- 검증된 공식 주소만 열리며 주소 변경·중단이 합의한 시점에 반영된다.
- 미설정·조회 실패·오프라인·잘못된 URL·외부 열기 실패를 구별해 안내하고, 실패를 접수 성공으로 표시하지 않는다.
- 공개 조회에는 내부 연락처·개인정보가 없으며 URL에 인증·회원 정보를 자동 첨부하지 않는다.
- 서버의 실제 Controller·DTO와 문서가 일치하고 공개 조회·권한 없는 설정 변경 거부를 검증한다.
- 채널 운영 소유자와 응답 담당이 정해지고, 학교·활동 정보 정정 등 이관 대상의 처리 경로를 확인한다.
