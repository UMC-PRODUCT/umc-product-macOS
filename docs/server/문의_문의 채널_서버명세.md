# 문의 채널 서버 명세

작성일: 2026-09-07
작성자: 제옹(euijjang97)
대상: 서버팀
관련 문서: `docs/adr/011-inquiry-domain-with-websocket-stomp.md`, `docs/adr/026-chat-engine-consumer-separation.md`

## 0. 이 문서를 쓴 이유

ADR-011이 문의 도메인을 통째로 설계해 뒀지만 몇 군데를 비워 뒀습니다. 비운 이유가
"기획이 아직 안 정해졌다"입니다. L50은 `InquiryCategory` 목록을 기획 확정 후 바꾸겠다고 했고
L298은 `InquiryCategory.java` 옆에 `// 기획 초안 그대로 (기획 확정 후 수정)`라고 적어 뒀습니다.
L49는 `InquiryTarget.UMC_PRODUCT`에 대응하는 `ChallengerRoleType`이 없어 중앙운영사무국 전체로
임시 라우팅한다고 했고 L254에서 그게 위험하다고 스스로 적었습니다.

그 빈칸을 기획이 채워서 넘깁니다. 이 문서가 정하는 것은 셋입니다. 카테고리를 무엇으로 볼 것인가,
문의가 누구에게 가는가, 등록 폼에 무엇이 들어가는가.

맥 앱 로드맵 6단계가 이 도메인에 통째로 걸려 있습니다. iOS와 웹도 같은 계약을 씁니다.

## 1. 한 장 요약

| 항목 | 결정 |
|---|---|
| 문의 범위 | 운영 문의 + 앱/서비스 문의. 신고·제보는 1차 밖 |
| 카테고리 | enum이 아니라 테이블. 프로덕트팀이 만들고 관리한다 |
| 대상 결정 | 카테고리에 붙은 `target`이 결정한다. 클라이언트는 대상을 보내지 않는다 |
| `UMC_PRODUCT` 수신자 | 프로덕트팀. 임시 매핑(중앙운영사무국 전체)은 쓰지 않는다 |
| 방 단위 | 문의 건별. ADR의 상태 머신 그대로 |
| 등록 폼 | 제목 없음. 카테고리와 본문, 첨부뿐 |

## 2. 카테고리 — enum이 아니라 테이블

ADR은 카테고리를 enum으로 두고 추가·삭제를 Flyway 마이그레이션으로 처리하려 했습니다.
이 방식은 카테고리를 바꿀 때마다 배포가 필요합니다. 운영 첫 기수에는 목록이 자주 바뀝니다.
어떤 문의가 실제로 들어오는지 열어 보기 전에는 알 수 없기 때문입니다.

카테고리를 데이터로 내립니다. 프로덕트 관리자가 앱 안에서 만들고 고칩니다.

### 스키마

```sql
CREATE TABLE inquiry_category (
    id          BIGINT       NOT NULL AUTO_INCREMENT,
    name        VARCHAR(40)  NOT NULL,
    description VARCHAR(200) NULL,
    target      VARCHAR(20)  NOT NULL,
    active      BOOLEAN      NOT NULL DEFAULT TRUE,
    sort_order  INT          NOT NULL DEFAULT 0,
    created_at  DATETIME(6)  NOT NULL,
    updated_at  DATETIME(6)  NOT NULL,
    PRIMARY KEY (id)
);
```

- `name` — 사용자에게 그대로 보이는 이름입니다. "출석·과제"처럼 씁니다
- `description` — 등록 폼에서 이름 아래 붙는 한 줄 설명입니다. 없어도 됩니다
- `target` — `InquiryTarget` 값입니다. 이 카테고리로 들어온 문의가 어디로 갈지 정합니다
- `active` — 새 문의 접수를 받을지 여부입니다
- `sort_order` — 등록 폼 목록의 순서입니다. 값이 같으면 `id` 오름차순으로 둡니다

`inquiry` 테이블의 `category VARCHAR(40) NOT NULL`을 `category_id BIGINT NOT NULL`로 바꾸고
`inquiry_category(id)`를 참조하게 합니다. 목록 필터도 `?category=BUG_REPORT`에서
`?categoryId=3`으로 바뀝니다.

### 삭제는 없습니다

지난 문의가 카테고리를 참조하고 있으니 행을 지우면 이력이 깨집니다. `active = false`만 씁니다.
비활성 카테고리는 등록 폼에서 사라지지만 그 카테고리로 열린 기존 문의는 그대로 살아 있고
이름도 그대로 보입니다.

### 범위는 전역 하나

학교마다 다른 카테고리를 두는 구조는 1차에서 뺍니다. 전국 공통 목록 하나만 둡니다.
처음부터 조직별 목록을 관리하면 운영진마다 다른 목록을 보는 상황을 수습해야 합니다.
학교별 커스텀이 필요해지면 그때 `scope` 컬럼을 붙이는 편이 낫습니다.

### API

사용자용은 하나입니다.

```
GET /api/v1/inquiry-categories
```

인증된 사용자 전원이 부릅니다. `active = true`인 것만 `sort_order` 순으로 내려줍니다.

```json
{
  "categories": [
    { "id": 1, "name": "출석·과제", "description": "출석 인정, 과제 제출 관련" },
    { "id": 2, "name": "앱 버그 제보", "description": "앱이 멈추거나 화면이 깨질 때" }
  ]
}
```

`target`은 응답에 넣지 않습니다. 사용자가 알 필요가 없고, 알면 "중앙에 직접 넣자"는 우회가 생깁니다.

관리용은 셋입니다.

| Method | Path | 설명 |
|---|---|---|
| GET | `/api/v1/admin/inquiry-categories` | 비활성 포함 전체. `target`·`active` 포함 |
| POST | `/api/v1/admin/inquiry-categories` | 생성. `{ name, description, target, sortOrder }` |
| PATCH | `/api/v1/admin/inquiry-categories/{id}` | 수정. 부분 갱신. 비활성화도 여기서 `active: false` |

관리 권한은 프로덕트팀입니다. 3장의 `UMC_PRODUCT` 수신자와 같은 집단을 씁니다.

### 초기 데이터

아래는 시드 제안입니다. 확정 목록이 아니라 관리자가 첫 화면에서 보게 될 출발점입니다.
운영 한 기수 돌려 보고 관리 화면에서 고칩니다.

| name | target |
|---|---|
| 출석·과제 | `SCHOOL` |
| 스터디·세미나 운영 | `SCHOOL` |
| 지부 행사 | `CHAPTER` |
| 제도·규정 | `CENTRAL` |
| 회비·정산 | `CENTRAL` |
| 수료·활동 증명 | `CENTRAL` |
| 앱 버그 제보 | `UMC_PRODUCT` |
| 앱 기능 요청 | `UMC_PRODUCT` |
| 기타 | `SCHOOL` |

`UMC_PRODUCT` 두 건은 3장의 선행 과제가 끝난 뒤에 넣습니다. 그 전에는 시드에서 빼 둡니다.

## 3. 라우팅 — 클라이언트는 대상을 보내지 않는다

ADR L12는 "등록 시 사용자는 문의 대상(`InquiryTarget`)을 선택하며"로 가정했습니다. 이걸 바꿉니다.

챌린저는 자기 질문이 학교 소관인지 중앙 소관인지 모릅니다. 조직도를 아는 사람만 쓸 수 있는 폼이
됩니다. 오배송된 문의는 답할 사람이 자기 소관이 아니라며 넘기는 동안 방치됩니다.

카테고리가 대상을 정합니다. 서버가 `category_id`로 `inquiry_category.target`을 읽어
`inquiry.target`과 `target_school_id` · `target_chapter_id`를 채웁니다.

| `target` | 누가 받나 | 판정 |
|---|---|---|
| `SCHOOL` | 작성자가 속한 기수·학교의 운영진 | `isSchoolAdminInGisu(memberId, gisuId, schoolId)` |
| `CHAPTER` | 작성자가 속한 기수·지부의 지부장 | `isChapterPresidentInGisu(memberId, gisuId, chapterId)` |
| `CENTRAL` | 중앙운영사무국 멤버 전원 | `isAtLeastCentralMember()` |
| `UMC_PRODUCT` | 프로덕트팀 | 아래 참조 |

앞의 셋은 ADR이 이미 정한 판정을 그대로 씁니다. `target_school_id`와 `target_chapter_id`는
작성자의 현재 기수 소속에서 서버가 채웁니다.

### `UMC_PRODUCT`는 선행 과제가 있습니다

ADR은 대응하는 `ChallengerRoleType`이 없어 중앙운영사무국 멤버 전체로 임시 라우팅했습니다.
이 임시안은 쓰지 않습니다. 앱 버그 제보와 기능 요청이 교육국원·운영국원의 목록에 쌓이는데,
그들은 그 문의로 할 수 있는 일이 없습니다. 받은 사람이 다시 개발자에게 전달하는 단계만 늘어납니다.

프로덕트팀이 직접 받습니다. 다만 서버에 "이 사람이 프로덕트팀"을 판별할 수단이 없습니다.
ADR L237과 L593이 후속 ADR로 미뤄 둔 그 문제입니다.

**그래서 순서가 있습니다.** 프로덕트팀 판별 수단이 먼저 서고 그다음에 `target = UMC_PRODUCT`인
카테고리를 만들 수 있습니다. 판별 방식은 서버가 정합니다. ADR이 언급한
`ChallengerRole.responsiblePart == PRODUCT`든 다른 것이든, 기획이 요구하는 것은 결과 하나입니다.
앱 문의는 앱을 만드는 사람에게 간다.

이 선행 과제가 끝나기 전에도 운영 문의 세 대상은 전부 열 수 있습니다. 앱 문의만 기다립니다.

## 4. 등록 요청 — 제목을 없앱니다

사용자에게 문의는 채팅입니다. 카카오톡 비즈니스 채널에 말을 거는 감각에 가깝고
티켓 양식을 작성하는 일이 아닙니다. 제목 입력창은 그 흐름을 끊습니다.
쓸 말을 두 번 나눠 생각하게 만들고 대부분은 본문 첫 줄을 그대로 옮겨 적습니다.

지금 스펙에는 중복도 있습니다. `Inquiry.content`와 첫 `InquiryMessage`가 사실상 같은 것을 담습니다.

요청 바디를 줄입니다.

```
POST /api/v1/inquiries
{
  "categoryId": 3,
  "content": "지난주 세미나 출석이 결석으로 찍혀 있습니다. 늦게라도 참석했는데 확인 부탁드립니다.",
  "fileIds": [1024, 1025]
}
```

서버가 하는 일이 둘 늘어납니다.

- `content`를 그대로 첫 `InquiryMessage`로 저장합니다. 작성자는 `INQUIRER`입니다
- `title`은 `content` 앞 40자를 잘라 채웁니다. 40자를 넘기면 말줄임표를 붙입니다

컬럼은 그대로 둡니다. `title VARCHAR(200) NOT NULL`도, `content`도 유지합니다. 채우는 주체만
클라이언트에서 서버로 옮깁니다. 목록 화면과 FCM 알림 제목은 `title`을 그대로 씁니다.

## 5. ADR-011과 달라지는 부분

서버팀이 확인할 변경 요청 목록입니다.

| # | ADR | 이 명세 |
|---|---|---|
| 1 | `InquiryCategory` enum + Flyway 마이그레이션 (L50, L298) | `inquiry_category` 테이블 + 관리 API |
| 2 | `inquiry.category VARCHAR(40)` (L358) | `inquiry.category_id BIGINT` FK |
| 3 | 목록 필터 `?category=BUG_REPORT` (L92) | `?categoryId=3` |
| 4 | 등록 시 사용자가 `InquiryTarget` 선택 (L12) | 카테고리의 `target`으로 서버가 결정 |
| 5 | `UMC_PRODUCT` → 중앙운영사무국 전체 임시 매핑 (L49) | 프로덕트팀. 판별 수단이 선행 과제 |
| 6 | 등록 요청에 `title` 포함 | `content` 앞 40자로 서버가 생성 |

1~3번은 Phase 1(도메인·영속화) 안에서 흡수됩니다. 4·6번은 Phase 3(등록 REST)입니다.
5번만 별도 트랙입니다.

## 6. 서버갭 — ADR 밖인데 필요한 것

| 항목 | 이유 | 우선순위 |
|---|---|---|
| 목록 페이지네이션 | `GET /api/v1/inquiries`에 페이징이 없습니다. 운영진 목록은 기수가 갈수록 쌓이기만 합니다 | 필수 |
| 카테고리 CRUD | 2장 | 필수 |
| 프로덕트팀 판별 | 3장 | `UMC_PRODUCT` 카테고리 개설 전까지 |
| 문의자 측 미읽음 | ADR이 1차에서 뺐습니다. 맥 앱 사이드바 배지에 필요합니다 | 후순위 |

페이지네이션은 커서 방식을 권합니다. 메시지 목록이 이미 `?after=`를 쓰기로 했으니(L116)
같은 모양을 씁니다.

## 7. 그대로 받는 것

ADR이 정한 것 중 기획이 바꿀 이유가 없는 항목입니다. 확인만 하고 넘어갑니다.

- **상태 머신** — `RECEIVED` → `IN_PROGRESS` → `CLOSED`, 재오픈으로 `IN_PROGRESS` 복귀
- **역할** — `INQUIRER` / `RESPONDER`, 양쪽 다 해당하면 `INQUIRER` 우선
- **수정·삭제 없음** — 분쟁 처리 기록으로 쓰기 위해서입니다. 정정은 다음 메시지로 합니다
- **첨부** — `FileCategory.INQUIRY_ATTACHMENT`, 이미지·문서 허용, 최대 50MB
- **실시간** — `/app/inquiry/{inquiryId}/message` 발행, `/topic/inquiry/{inquiryId}` 구독
- **알림** — 신규 문의 등록 시 대상 운영진 전원에게 FCM
- **보관** — 종료된 문의 무기한 보관

## 8. 정하지 않은 것

1차 명세에서 뺍니다. 운영 합의가 먼저라 지금 정하면 지키지 못할 숫자만 남습니다.

- **응답 SLA** — 며칠 안에 답해야 하는가
- **미응답 문의 처리** — 오래 방치된 문의를 자동으로 올릴 것인가, 누구에게 올릴 것인가
- **스팸·악용 대응** — 같은 사람이 반복해서 여는 경우
- **학교·지부별 카테고리** — 2장에서 뺐습니다. 필요해지면 `scope` 컬럼을 붙입니다

## 9. 착수 순서 제안

ADR의 Phase 구분을 그대로 쓰되 두 군데를 끼워 넣습니다.

| 순서 | 내용 | 비고 |
|---|---|---|
| Phase 0~1 | 사전 준비, 도메인·영속화 | `inquiry_category` 테이블을 여기서 같이 만듭니다 |
| Phase 1.5 | 카테고리 관리 API | 사용자용 조회 + 관리용 CRUD |
| Phase 2~3 | 권한·접근 제어, 등록/종료/재오픈 REST | 등록에서 `target` 자동 결정과 `title` 생성 |
| Phase 4 | 메시지 송수신 REST | 여기까지면 맥 앱이 실시간 없이 화면을 열 수 있습니다 |
| Phase 5~6 | 운영진 미읽음, WebSocket·STOMP | |
| 별도 트랙 | 프로덕트팀 판별 | 끝나면 `UMC_PRODUCT` 카테고리 개설 |

맥 앱은 Phase 4가 끝나는 시점에 붙습니다. 문의는 스레드만큼 즉시성이 필요한 대화가 아니라,
열 때와 새로고침 때 받아 오는 정도로 먼저 쓸 수 있습니다.
